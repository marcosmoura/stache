# MenuAnywhere

Read when changing the MenuAnywhere runtime or checking what it does. The runtime is registered and default-disabled. Native behavior was verified manually on 2026-11-07/08 (real tap, Accessibility reads, `NSMenu` tracking and cancellation, unresponsive-app timeout, exact activation and press, reconfigure and pause/disable during tracking); see the gate evidence in the [Part 02](../specs/2026-11-03-menu-anywhere/02-native-menu.md#gate-evidence) and [Part 03](../specs/2026-11-03-menu-anywhere/03-runtime.md#gate-evidence) specs. Multi-display placement was not separately recorded.

`menuAnywhere.jsonc` (`enabled`, `modifiers`, `mouseButton`) is documented in [config.md](../architecture/config.md). When enabled and Accessibility is granted, the module subscribes one suppressing handler to the host's shared input service (no private event tap, no passive tap), reads the captured frontmost application's menu bar through public Accessibility on a dedicated owner thread and shows it as a native `NSMenu` at the click location. Choosing an item activates the captured application instance and presses the item with `AXPress`.

## Trigger

- `rightClick` is a mouse-down of button number 1; `middleClick` is button number 2 only (back, forward and any button 3 or above never match, correcting the legacy back/forward match). The macOS adapter classifies `rightMouseDown`/`otherMouseDown` into one `MouseDown` kind with the native button number and drops any event whose type contradicts its button (left is 0, right is 1, other is 2 or more), so the button number alone is sufficient and a mismatched event passes untouched.
- Modifiers compare the four supported bits (Control, Option, Command, Shift) **exactly**. An extra supported modifier rejects; unrelated flags such as Caps Lock and Fn are ignored. `[]` is valid and captures every unmodified matching click system-wide while enabled; use it with care.
- Priority is Hold-to-Quit > MenuAnywhere > Keybindings; overlap diagnostics and tap re-enable stay the shared service's job.
- The input callback reads one immutable published tuple (runtime generation, accepted revision, trigger, permission and service health) with a `try_read`, claims the single busy reservation and sends into a one-slot queue. It does no Accessibility, application, activation, logging, lifecycle or blocking work. An eligible match is consumed (suppressed): with a free reservation it becomes one request; while a popup is queued, reading, showing, invoking or cleaning up, the newest trigger is swallowed and dropped (`Coalesced`, never stacked or replayed, a legacy bug fix). An unexpectedly full queue passes the click and frees its own reservation; a disconnected worker passes the click and marks the runtime unhealthy. A trigger the callback consumed stays consumed even if capture or reading later fails; no replacement click is synthesized. A pause, disable or permission loss that lands just after the callback decided can consume that one already admitted click while its work is cancelled.

## Processing

At the first worker opportunity after admission, the worker captures the exact frontmost application instance (`FrontmostWatch::refresh`) and records trigger time, capture-start time and capture time separately (`TriggerReport`). It observes the application frontmost _at processing_, not a proven event-time snapshot; a different application that became frontmost in between is the observed target, and a request older than 2 s, or a capture hop over 2 s, is rejected. After capture it never retargets. This process is never read (`SelfTarget`). The menu is anchored at the trigger event's own Quartz point, which the tap callback copies from the tapped event (`InputEvent::location`) into the request; the pointer is never sampled again at processing time, so a later pointer move cannot shift the menu. An event without a point is a typed `PointerUnavailable` outcome. The read validates the captured instance and its activation epoch before and after (so A, B, A is stale too); a focus change before the show drops it. At action time the captured instance is targeted even if focus moved while the menu was open. The busy reservation is released exactly once by its own pass after the presentation is released.

Errors (no menu, permission denied, read timeout, stale target, show rejected, action refused or uncertain, cleanup pending) are typed, counted and logged as a short label (never menu titles) off the callback. They do not change the module lifecycle to Failed. An uncertain `AXPress` or activation is never retried.

## Lifecycle and status

Registration and construction are inert, including an enabled file. `start` acquires the application observation and frontmost watch, the menu stack and the workers, and subscribes **last**; a failure rolls everything back in reverse and reports `Failed` with the start operation and category. A missing or failed shared input service fails the start with the dependency category and is projected as `Unavailable` ("missing service `input`") on the generic `ModuleStatusView`, not as a module failure. Accessibility is a shared-input requirement: startup, enable, reload, tick and activation only check; only the explicit tray request prompts. The module reports `Disabled`, `Paused`, `WaitingForPermission` or `Running` through the generic status; a running module whose subscription went inert, or whose worker died is projected as `Unavailable` with the reason on the same generic `ModuleStatusView`. There is no new CLI, socket command or Settings surface.

The shared-service prefilter is configuration independent (mouse down of button 1 or 2, any modifiers), so a reconfigure never replaces it; the callback's published matcher-and-revision tuple is the exact authority. An enabled reconfigure stages the candidate; the config worker observes the registry's published accepted revision and publishes the new tuple, so a callback sees either the previous or the new complete tuple. A popup already shown keeps its authority and may finish; only subsequent triggers use the new trigger. Pause, disable, permission or service loss, stop and shutdown revoke eligibility and every presentation authority immediately, then unsubscribe, cancel exact tracking, release the presentation and AX owner with fresh 2 s acknowledgements and stop the observation. A tap removal the shared input service cannot acknowledge stays owned by that service as inert retained cleanup; MenuAnywhere reports it as `cleanupPending` in the status detail and the `CleanupPending` counter. A timeout is reported (stop returns an error and the run is retained and retried at the next start or at host shutdown); nothing is called released merely because cancellation was requested. A native call in flight finishes under its own AX timeout before the owner joins.

## Verification

Automated tests (`stache-menu-anywhere` `tests.rs`, the `ma_03_` cases in the app `host.rs` suite and `config_catalog.rs`) run the production worker over the shared input service's fake tap, the fake application backend, the real `MenuControl`/`AxOwner` over the Part 02 fakes and a fake clock; see [testing.md](../guides/testing.md). The manual runs (approval required for each: temporary config, exact launched test PID, effects) are listed in the [Part 03 spec](../specs/2026-11-03-menu-anywhere/03-runtime.md#per-run-approved-manual-integration-checks) and have **not** been performed. Supported tray Quit is the only teardown path claimed; Cmd-Q and logout coordination are a documented non-goal.

## Spec

The [spec](../specs/2026-11-03-menu-anywhere/00-overview.md) defines three parts: the typed configuration (Part 01), the Accessibility reader, `NSMenu` presenter and exact-instance invocation adapters (Part 02) and this runtime (Part 03). All three parts are done; native gate evidence is recorded in the Part 02 and Part 03 specs. No Settings UI, private menu API, search or menu cache is planned. The old application is archived under `_legacy/`; its behavior is not the new runtime contract.

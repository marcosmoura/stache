# Bar

Read when using or changing the status bar: its panel, data providers, click actions, weather, media or the Keep Awake indicator.

Bar is a **default-disabled module** (`stache-bar`, `src/crates/modules/bar`): set `enabled = true` in `bar.toml` and grant Accessibility (the shared launch gate) to start it. It shows one non-activating panel on the menu-bar display, below normal windows, with **no visual change from legacy Bar**: identical layout, fonts, colors, icons, hover/animation behavior, fixed-centered media and responsive/empty/error states. It ships the panel and menu-bar behavior (part 03), the ported UI (04), CPU/battery/Wi-Fi/clock and fixed clicks (05), weather (06), media (07) and the Keep Awake indicator (08) of the [Bar spec](../specs/2026-11-03-bar/00-overview.md), on top of the [Bar foundation](../specs/2026-11-08-bar-foundation/00-overview.md). Tiling's workspace/application strip ships from the [Tiling–Bar integration](../specs/2026-11-08-tiling-bar/00-overview.md) (fake-proven, native behavior unverified; live clicks/focus remain unverified, see [known gaps](#known-gaps-and-limits)): its data, click command and the ported strip UI (see [Tiling strip data](#tiling-strip-data)) and the strip is covered by the visual-parity gate. Widgets and a Settings CLI are not planned. Legacy documentation is unchanged.

Production wiring: `stache-app` `lib.rs` chains `BarFactory::production_with_media` next to Tiling (default disabled, inert at construction, with the data bridge attached). Bar reuses landed generic host facilities and imports no other module crate (`stache-bar` never imports `stache-keep-awake` or `stache-tiling`, and `stache-tiling` never imports `stache-bar`; a test checks the manifests).

## Configuration

`bar.toml` (`BarConfig`) is registered in the config catalog for schema, template, typed validation and `stache config migrate` (see [config](../architecture/config.md)):

| Key                        | Values                                                                 | Default  |
| -------------------------- | ---------------------------------------------------------------------- | -------- |
| `enabled`                  | `true` / `false`                                                       | `false`  |
| `height`                   | points; `0` runs Bar with no panel                                     | `28`     |
| `padding`                  | points                                                                 | `12`     |
| `weather.provider`         | `auto`, `visual_crossing`, `open_meteo`                                | `"auto"` |
| `weather.api_keys`         | env file holding `VISUAL_CROSSING_API_KEY` (see [Key file](#key-file)) | `""`     |
| `weather.default_location` | city name or `lat,lon`; fallback when native Location fails            | `""`     |
| `weather.precise_location` | `true` / `false`                                                       | `false`  |
| `weather.refresh_interval` | minutes, integer 5 to 1440                                             | `20`     |

Keys are snake_case. `precise_location = false` asks `CoreLocation` for an approximate fix and accepts the user's macOS approximate-location choice; `true` asks for the best accuracy. It applies at the next location read without restarting Bar; migration writes `false` because legacy has no key. `refresh_interval` outside 5 to 1440 or of another type is a configuration diagnostic at `weather.refresh_interval`; migration writes 20. A config reload reconfigures in place.

With `enabled = false` (the default) Bar owns no window, webview, topology feed, provider, location, media or bridge worker. Bar waits behind the shipped Accessibility gate like every module without needing Accessibility itself.

## Panel, reservation and menu bar

- **Panel.** `BarModule` runs on the primary display (`NSScreen.screens[0]`, the menu-bar display, never `mainScreen`) at `(padding, padding, width - 2*padding, height)` and publishes a constant top screen reservation of `height + padding` through the host screen-reservation registry; the reservation does not change while the bar slides away. The webview is hosted in a `stache-macos` `NSPanel` created non-activating at init (design and evidence in [UI architecture](../architecture/ui.md) and the [part 03 spec](../specs/2026-11-03-bar/03-panel-window.md)). The `stache-app` Bar-scoped screen-topology feed applies every attached display to the registry only while Bar runs, and an empty topology otherwise.
- **No panel.** Explicit `height = 0` or a computed width `<= 0` runs Bar with the typed status "no panel: zero size", no window and no reservation; no primary display is an explicit unavailable state. A page that does not load never blocks start or the registry: the panel fails typed while Bar stays running, with bounded backoff retry.
- **Menu-bar observation.** Visible/hidden/unknown, event driven, with a 100 ms poll only while auto-hide is on or unknown (legacy polled at 100 ms always). The reservation is unchanged in every state. The UI slides the Bar away (translateY(100%), opacity 0, 150 ms) while the host reports `menu.state === "visible"` (legacy `menuHidden` true) and returns otherwise, including for `hidden`, `unknown`, `unavailable` and `unauthorized`.
- **Data bridge.** `bar_snapshot` and the `BarChanged` event (exact decimal-string counters and a sequence ordering rule) are authorized by the live Bar window label. The `bar-window` capability (`capabilities/bar.json`) grants only `stache-bar-*` windows the six Bar commands (`allow-bar-snapshot`, `allow-bar-action`, `allow-bar-weather`, `allow-bar-media-artwork`, `allow-bar-session-action`, `allow-bar-tiling-action`, each ACL-gated in the app manifest; every command also authorizes the calling label itself) and listening for `bar-changed` (`core:event:allow-listen`/`allow-unlisten`). See [IPC](../architecture/ipc.md).

## Surface

The Bar window (`src/ui/src/shell/windows/Bar/`, `?surface=bar`) is a port of the legacy Bar UI with no visual change: the grid whose first slot holds Tiling's Spaces strip, a fixed-centered Media overlay and the Status stack in the order Weather, CPU, Battery, Keep Awake, Wi-Fi, Clock, using the legacy primitives (Surface, Button, Stack, Icon, ScrollingLabel) and the legacy root rules scoped to the Bar window. The font is the system-installed `'Maple Mono NF', 'SF Mono', monospace`; it is never bundled.

- **Clock** is UI-local: `Intl.DateTimeFormat('en-US')`, 24 hour, weekday/month/2-digit day/time with seconds, refreshed every second in the system time zone; its timer stops on unmount.
- Every other item reads host data (sections below). No native reading is fabricated and no unimplemented command is called.
- The Spaces slot renders the ported legacy strip from `BarView.tiling` (see [Tiling strip UI](#tiling-strip-ui)); while Tiling is unresolved, absent or has no workspaces it is legacy's empty `<div />`, so Media and Status never move.

## System providers

CPU, battery and Wi-Fi data come from `stache-bar` `providers/` (the Clock stays UI-local).

**Lifecycle.** The providers start and stop where the menu-bar observation does: only for an accepted, enabled, unpaused Bar **with a panel** (`providers/mod.rs` `ProviderMonitor`). Disabled, paused, zero-size, no-primary-display and failed-panel runs own no provider thread, timer, child process or native handle. One worker thread per provider means a slow or hung read of one provider never delays another provider, the host, the main thread or a bridge read. Stop cancels the shared token (wakes waits, kills the exact owned child) and joins within 2 s; a worker that cannot be joined stays owned (the same retained-owner rule as the menu monitor) and blocks the next start until it settles. A late completion cannot republish: publication is bound to an exact monitor epoch that the stop clears atomically.

**Cadences** (`next_due`: one period after the previous sample _started_, never before it _finished_; no overlap, no catch-up storm after a stall): CPU 2 s (first sample after a 250 ms warm-up, the priming measurement is discarded), battery 30 s while charging and 120 s otherwise, Wi-Fi at most 5 s. A native Wi-Fi change signal would wake the schedule through a coalescing flag (storm = one extra sample, at least 500 ms after the previous); the signal seam (`WifiSignals`) and its coalescing are tested, but **no native CoreWLAN event source is wired**, so production polls every 5 s.

**Readings** (`BarView.cpu/battery/wifi`, generated types `CpuReading`, `BatteryReading`, `WifiReading`; the legacy field spellings so the UI seam is value-identical): each sample that changes a reading bumps the bridge `sequence`; an unchanged sample emits nothing; a failed read keeps the last reading (never invents one) and records a typed, deduplicated condition in the `bar` module status (`providers`), never in the Bar visuals.

- **CPU**: usage from `sysinfo` `refresh_cpu_usage`/`global_cpu_usage` (the legacy source; the priming read is discarded), rounded to 0 to 100. Temperature is **native SMC only**, `smctemp` style, with no subprocess, no `ismc`/`smctemp`, no third-party SMC crate and no private API: `stache-macos` `system::smc` opens the `AppleSMC` service over public `IOKit` (`IOServiceOpen`) and reads keys with `IOConnectCallStructMethod` (the `SMCKeyData` protocol of smcFanControl/`smctemp`/Stats: key info, then bytes), decoding `flt `, `sp78` and the other `spXY`/`fpXY` fixed-point types (including `fpe2`), `ui8/16/32/64` and `si8/16`; the connection is cached and closed on drop. Keys come from the detected chip (`machdep.cpu.brand_string`): Intel `TC0C..TC9C` (fallback `TC0D/TC0E/TC0F/TC0P/TCAD`), Apple M1 to M5 CPU core lists (the union of `narugit/smctemp` `smctemp.cc` and `exelban/stats` `values.swift`; M1 auxiliary `Tc0a/b/x/z`), an unknown Apple generation uses the union of all Apple lists; a key the machine lacks is skipped. Valid keys (`0 < t < 150`, finite) are averaged; when none is valid the group is re-read up to 3 more times in the same sample (the `smctemp` M2 instability handling); then the last valid value is repeated for at most 3 samples; then the temperature is unknown. A failed open or no keys is unknown, never a made-up number, and never makes Bar unavailable. Live evidence: usage and temperature matched Activity Monitor (see [Live verification](#live-verification)).
- **Battery**: `starship-battery` (legacy source), percentage rounded and clamped to 0 to 100, legacy states `Unknown/Charging/Discharging/Empty/Full`. A machine without a battery has no reading, which hides the component. `Full` renders `100%` and the compact label at `<= 2036px` are UI rules unchanged from the legacy UI.
- **Wi-Fi**: `CoreWLAN` interface names, power and RSSI only (`stache-macos` `system::wifi`). The macOS SDK header documents that `ssid`, `bssid`, the country code and scan results need Location Services authorization while `interfaceName`, `powerOn` and `rssiValue` do not; the adapter reads only the latter, never requests Location, never touches `CLLocationManager` and uses no private Apple80211 API. The live run on macOS 27.0 showed state and signal with no prompt. Status keeps legacy `Unknown/Off/Disconnected/Connected` and the -60/-70/-80 thresholds (UI). Without the SSID the network name is `null`; a missing or redacted name never implies disconnected. Legacy's `networksetup`/`ifconfig` discovery is replaced by the `CoreWLAN` names.
- **SSID path (on by default).** The only SSID source is `ipconfig getsummary <interface>` (fixed `/usr/sbin/ipconfig`, validated interface identity, bounded and sanitized output, `<redacted>` and control characters dropped; a redacted or missing SSID is null and never implies disconnected). It runs while the typed `SsidGate` is `On`, which is the default: a user-approved feasibility run on macOS 27.0 (2026-11-10) showed the network name from `ipconfig getsummary en0` with no Location or other permission prompt (macOS 27 evidence satisfies the macOS 26+ gate by user decision, 2026-11-10; macOS 26 itself was not separately verified). `STACHE_BAR_WIFI_SSID_SUMMARY=0` is a diagnostic off-switch (any other value or unset leaves it on); with it no `ipconfig` child is ever spawned and the name stays null. One bounded child runs per Wi-Fi sample per interface. Location is never requested and no Apple80211 API is used.

## Click actions

Clicking the CPU, Clock, Battery, Wi-Fi, Weather or Media component calls the generated command `bar_action(action)` with a closed enum (`cpu`, `clock`, `battery`, `wifi`, `weather`, `media`). The host maps it to a fixed target and accepts no name, path, URL or argument. Keep Awake's click is a separate session action ([below](#keep-awake-session-click)). The look is unchanged (the parity gate passes without edits) and an outcome produces no UI: the Bar only logs non-`completed` outcomes with `console.debug`.

| Action    | Target                                                               | How it opens                                                                                                    |
| --------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `cpu`     | Activity Monitor, `com.apple.ActivityMonitor`                        | `ApplicationControl`: bundle id to installed path (`application_path`), then `open` through the issuance permit |
| `clock`   | Calendar, `com.apple.iCal`                                           | the same path                                                                                                   |
| `weather` | Weather, `com.apple.weather`                                         | the same path                                                                                                   |
| `media`   | the published player, if known (see [Media click](#media-data-path)) | the same path                                                                                                   |
| `battery` | `x-apple.systempreferences:com.apple.Battery-Settings.extension`     | `stache-macos` `settings::open_battery_settings`, main-thread `NSWorkspace openURL:`                            |
| `wifi`    | `x-apple.systempreferences:com.apple.wifi-settings-extension`        | `settings::open_wifi_settings`, the same                                                                        |

There is no shell `open`, no new launcher and no arbitrary-URL function. The `x-apple.systempreferences` scheme is undocumented by Apple; both panes opened in the live run on macOS 27.0 (it can break in a later release).

**Outcome** (`BarActionOutcome`, command result data tagged by `kind`, never an error string): `completed` (issued and macOS reported it done: the open completion for an application, `AppKit` accepting the URL for a pane; it is **not** proof that a window is visible), `stale` (the Bar was stopped, restarted or its panel replaced before the send; nothing sent), `notIssued` (cancelled or rejected before issuance; nothing sent), `refused` (macOS or the adapter refused; `detail` is diagnostic), `notInstalled`, `timedOutBeforeIssuance` (an acknowledgement missed its bound before the request could issue; the abandoned job can never send), `uncertainAfterIssuance` (the request was **issued** but no confirmation arrived inside the bound; it may still complete and is never retried), `notAttempted` (unknown or absent media player), `busy`, `unauthorized` and `unavailable` (`reason` as for `bar_snapshot`).

**Rules.** The caller is authorized exactly like `bar_snapshot` (the actual webview label must be the live Bar panel; Bar-shaped labels while Bar is not running get `unavailable`). The command runs the bounded native sequence on the blocking pool, never on the main thread, so it never delays a bridge read or shutdown. The click's application observation lives for that one click (a disabled Bar owns none). When the Bar runtime stops or restarts, a status notification cancels the install and invalidates the observation, so the issuance permit refuses the send and the click returns `stale`; the pane opener rechecks authorization and generation on the main thread right before `openURL`. A click already sent finishes inert. **Busy rule:** one action is in flight at a time; a click while another is in flight returns `busy` immediately and is dropped, never queued, so rapid clicks cannot stack work. The in-flight bound is the application control's acknowledgement budget (2 s per hop) plus 5 s for the open completion; a pane open waits 2 s per hop.

## Weather

There is **no Rust weather timer or worker** and no Rust HTTP client. The Bar UI calls `bar_weather()` once per refresh to get its inputs (provider, key, location) and fetches the provider itself with the webview `fetch`.

### Location adapter and consent

- **Adapter.** `stache_macos::location` (`LocationSource`, `SystemLocation`, fake `FakeLocationSource`) does one bounded read (10 s default) on a worker thread. The manager and delegate exist on the main thread for that read only; delegate callbacks just dispatch an event and a generation check drops late ones. Outcomes are typed (`Located`, or `Unavailable` as `Denied`, `Restricted`, `ServicesDisabled`, `NotDeterminedTimeout`, `Timeout`, `Error`, `NoUsageDescription`, `Unavailable`); `Debug`/`Display` redact coordinates. The module documentation records the authorization choice (`requestWhenInUseAuthorization`, once per process and only while `notDetermined`) and the accuracy constants (`kCLLocationAccuracyReduced` versus `kCLLocationAccuracyBest`, one-time temporary full accuracy only with the declared purpose key). `default_location` is the fallback when native Location is unavailable, denied or times out.
- **Info.plist.** `src/crates/app/Info.plist` holds only `NSLocationWhenInUseUsageDescription` and the `NSLocationTemporaryUsageDescriptionDictionary` purpose `StacheWeatherPreciseLocation`; no `LSUIElement` (the tray-only identity is the runtime `Accessory` policy). Tauri looks for an `Info.plist` next to `tauri.conf.json` (the CLI schema documents it) and merges it into the bundle, so no `bundle.macOS.infoPlist` entry is needed. Debug (`dev`) builds embed that file too: `generate_context!` writes it, with `CFBundleName` and version keys, into the binary's `__TEXT,__info_plist` section (verified with `otool` on `target/debug/stache`). Without that embedding, or without the key, the adapter returns `NoUsageDescription` and never calls `CoreLocation`. `tauri build` merges it into the bundle (verified in the live run).
- **Entitlement.** `src/crates/app/Entitlements.plist` (referenced by `bundle.macOS.entitlements`) grants only `com.apple.security.personal-information.location`, which the hardened-runtime signature needs before macOS will show the prompt.
- **Live consent** (2026-11-10, user-approved, diagnostics since removed): `locationd` and `CoreLocationAgent` logs showed two blockers. The unbundled dev binary has no bundle (`bundleId` null), so `CoreLocationAgent` logs "client bundle is NULL. Skip showing AuthPrompt": **`bun run tauri:dev` never shows the prompt** and falls back to `default_location` after the 10 s wait. The bundled `.app` is signed with the hardened runtime, and without the location entitlement `locationd` logs "Client has supported the hardened runtime but doesn't have the entitlement, not sending #AuthPrompt". With the entitlement a debug bundle launched through Launch Services showed the prompt, the user approved, the status became authorized with full accuracy, `requestLocation` delivered a fix and `bar_weather` answered `coreLocation`. The prompt is approved behavior; it appears only for a bundled `.app` (the `Accessory` app gets it once it carries the entitlement).
- **Late consent.** A consent left open longer than the 10 s read falls back to `default_location` for that answer and never blocks the UI, but the adapter keeps its single manager and delegate alive only to observe `locationManagerDidChangeAuthorization:` (a consent watcher: no re-request, no `requestLocation`). When the user decides (authorized, denied or restricted) it releases the manager and notifies once; the weather service drops its 60 s cached outcome and bumps `BarView.weatherEpoch` (a decimal-string counter, no coordinate or key), Bar emits a `BarChanged`, and the UI refetches immediately (the epoch is part of the non-secret query key; the previous reading stays shown until the new one arrives). The watcher is cancelled (manager released, nothing notified) when Bar stops, pauses, is disabled or fails, or the runtime generation changes, and a decision arriving after that bumps nothing.

### Weather data path

The UI calls the generated command `bar_weather()` once per weather refresh (every `weather.refresh_interval` minutes, default 20, and on reconnect). The command is authorized exactly like `bar_snapshot`/`bar_action` (the actual calling webview label must be the live Bar panel; `unauthorized` for test/access/shell/forged/stale labels) and is ACL-gated in the app manifest and granted only by `capabilities/bar.json` (`allow-bar-weather`). A Bar that is not running, or is running without a panel (zero size, no primary display, failed panel), answers `unavailable` with the reason before anything is read. The blocking work runs on the blocking pool, never the main thread and never under a registry, module or status lock, so a hung location read cannot delay `bar_snapshot` or shutdown.

**Response** (`BarWeatherOutcome`, tagged by `kind`): `ready` with `weather`, `unavailable` (`reason`, `detail`), `unauthorized`, or `stale` (Bar stopped, restarted or its accepted config changed during the read; the UI just calls again). `weather` is `{ configRevision, provider, apiKey, location, refreshIntervalMinutes }`: `refreshIntervalMinutes` is the non-secret `weather.refresh_interval` of the same accepted config snapshot as `configRevision`; `provider` is the configured mode (`auto`, `visualCrossing`, `openMeteo`); `apiKey` is the trimmed `VISUAL_CROSSING_API_KEY` or `null` (missing, empty, unreadable, or provider `openMeteo`, which never reads the file); `location` is tagged by `source`: `coreLocation { latitude, longitude, reducedAccuracy }`, `defaultLocation { query }` (the trimmed `default_location`; the UI parses coordinates or geocodes a city) or `none` (no fix and an empty `default_location`). Provider availability (`auto` uses Visual Crossing only with a non-empty key and otherwise Open Meteo; `visualCrossing` without a key is unconfigured; `openMeteo` needs none) is decided by the UI from `provider` and `apiKey`, preserving the legacy UI `isProviderAvailable` semantics; the legacy Rust `is_enabled` comments contradict them and are wrong.

**Location resolver** (`stache-bar` `weather`, behind the `LocationSource` trait). Per call it reads the currently accepted config (so `precise_location` applies at the next read without restarting Bar), then at most one location read runs at a time (single flight). Concurrent calls for the same run and config revision share the in-flight read, waiting at most the 10 s read timeout plus a 2 s margin; they never start a second read, even when the first hangs. A read outcome (a fix or the reason there was none) is reused for 60 s for the same (runtime generation, config revision), so a double mount does not read twice; a new revision or a restart reads again. Any unavailable reason (denied, restricted, services off, undetermined after the timeout, timeout, error, no usage description, unavailable) falls back to `default_location` (or `none`) with the typed diagnostic, never a bogus coordinate. After the read the run generation and revision are checked again; a change returns `stale` and records nothing. Nothing exists between calls except a pending consent watcher: no worker, timer or observer.

**Injection.** `BarFactory::with_weather(WeatherParts)` takes the location source, the home and configuration directories and a clock. Production passes `SystemLocation`, `AppEnvironment` home and `ConfigPaths::directory()`; app tests pass `FakeLocationSource`-backed fakes. The factory builds one `WeatherService` over the Bar status cell and hands it to the bridge.

### Key file

`weather.api_keys` is resolved with `WeatherConfig::api_keys_path` (trim; `~`/`~/x` against the injected home; absolute as written; anything else against the configuration directory) and read on every call (no watcher, no process-environment mutation, no read at all for an empty value). The parser is `dotenvy` 0.15.7, the same as legacy, so quotes, comments, `export`, escapes, multi-line quoted values, skipped malformed lines and "last duplicate wins" are unchanged. Legacy behaviors worth knowing: a UTF-8 byte order mark hides the first entry (legacy never stripped it), an unterminated quote swallows the rest of the file, and `$NAME`/`${NAME}` in unquoted and double-quoted values is substituted from earlier entries and then the process environment (read only; the legacy doc comment claiming expansion is disabled is wrong; single-quote a key that contains `$`). Differences from legacy: the file is read through a 64 KiB cap and must be a regular file (a symlink to one is followed, as legacy did; a directory, FIFO or device is refused before opening); the value is trimmed and an empty value is no key; failures are the typed redacted diagnostics below instead of a `tracing::warn!` with the parser error text.

**CWD fallback removed and the migration ambiguity.** Legacy `config/env.rs` resolved a relative `api_keys` against the directory passed in, which for the bar is the directory of the loaded config file; only `weather.rs` `get_weather_config` fell back to `.` (the process working directory) when it knew no config path. That fallback is gone: a relative path resolves only against the Next configuration directory. Because `stache config migrate` writes `bar.toml` into the Next configuration directory, which can differ from the directory of the legacy config the value was written for, a relative `api_keys` may point somewhere else after migration. The migration note on relative `api_keys` already says so; rebase the value (or use an absolute or `~/` path) when the file is not found. The key diagnostic `missing` names the exact path that was tried.

### Weather UI

Code: `src/ui/src/shell/windows/Bar/Weather/` (`Weather.query.ts` the React Query hook, `Weather.api.ts` providers, location parsing and normalization, `Weather.codes.ts` icon maps) and `Bar.tsx`, which feeds `BarData.weather` from the hook only for production data (fixture data from `BarDataProvider` never runs it). There is no Tauri HTTP plugin or permission. The component, its label (`Math.ceil(feelslike || 0)°C`, `Loading...` without current data) and its styles are unchanged.

- **Refresh.** One query `['bar','weather',<configRevision>]` calls `bar_weather` and then the provider in a single `queryFn`. `staleTime: Infinity`, `retry: false`, `refetchOnMount`/`refetchOnWindowFocus: false`, `refetchIntervalInBackground: true` and a `refetchInterval` of the configured `refresh_interval` minutes (the `refreshIntervalMinutes` of the last `ready` answer stored in the query result; 20 minutes until one is known, none once `unconfigured`) follow the legacy defaults. A config reload is a new revision and so a new query, so the new cadence applies without restarting Bar; the Rust 60 s outcome reuse window is unchanged. Legacy asked for refetch on reconnect but its `staleTime: Infinity` meant a reconnect never actually refetched; the new hook uses `refetchOnReconnect: 'always'` so a reconnect really refreshes. It runs only while Bar serves a view (the `configRevision` comes from the `available` bridge snapshot), so a disabled, paused, failed or zero-size Bar issues no call. A new accepted revision is a new query key: it refetches, and the previous revision's in-flight request is aborted and can never replace the new answer. An answer whose `configRevision` is older than the bridge's is discarded and read again. `stale` is asked once more promptly (twice in total, then the loading branch until the next refresh). `unavailable` and `unauthorized` are the unconfigured branch (component hidden) and stop the interval; no fake data is shown. Unmount and StrictMode disposal abort the in-flight fetch through the query signal.
- **Providers** (ported from legacy `WeatherStore/providers`). `auto`: Visual Crossing with a non-empty trimmed key, otherwise Open Meteo; `visualCrossing` without a key: unconfigured (hidden); `openMeteo`: never uses a key. The provider is never switched silently after a failure. Visual Crossing: `https://weather.visualcrossing.com/VisualCrossingWebServices/rest/services/timeline/<encoded location>/next5days` with `key`, `unitGroup=metric`, the legacy `elements` list, `include=current,hours,days`, `iconSet=icons2`, `contentType=json`; the icon name maps through the legacy `icons2` table. Open Meteo: `https://api.open-meteo.com/v1/forecast` with the legacy `current`/`hourly`/`daily` lists, `timezone=auto`, `forecast_days=5`, and the legacy WMO code to icon table (night variants when `is_day` is not 1). Only `feelslike`/`apparent_temperature` and the icon are read from the response; a `null` feels-like renders `0°C`. A non-OK status, malformed JSON, a wrong shape or a 15 s timeout (one bounded, abortable request) leaves the item in the legacy "configured, no conditions" state (`Loading...`) with a fixed error message that holds no URL, key or coordinate. There are no retries.
- **Location.** `coreLocation` uses the native latitude/longitude directly (Visual Crossing gets `lat,lon`). `defaultLocation { query }`: a `lat,lon` text (decimal degrees in range) is parsed into numbers; Open Meteo uses them directly and Visual Crossing receives the text as typed; any other text is a place name, sent as typed to Visual Crossing and geocoded by Open Meteo through `https://geocoding-api.open-meteo.com/v1/search?name=…&count=1&language=en&format=json` (first result; empty, HTTP error or malformed answers are an error). Legacy never parsed a configured default as coordinates (only its browser fix was coordinates), so an Open Meteo default of `lat,lon` text failed to geocode there; parsing it is a deliberate fix. `none` (no fix and an empty default) makes no request and stays in the `Loading...` state; legacy would have sent an empty location and failed the same way. There is no `navigator.geolocation`, no ipapi.co or ipinfo.io and no reverse geocoding.
- **Click.** The Weather item calls `bar_action('weather')` (Apple Weather) through the same `barClick` helper as the other components; the legacy item toggled a widget and was already a button, so hover/active are the same clickable styles the parity gate covers. Outcomes change no UI.

### Secret and coordinate boundary

The key and the coordinates exist only in the `bar_weather` response and, in the UI, only in the `queryFn` closure. They are never in `BarView`, `BarChanged`, `BarRuntimeStatus`, the `bar` overlay of `host_status`/`StatusChanged`, logs, errors or `Debug` output (hand-written redacting `Debug`). Query keys hold the non-secret revision, the cache holds only the rendered subset (`feelslike`, `icon`) and a `{ configured }` flag, nothing is persisted, synced across windows, put in zustand or logged, and errors are fixed strings. Tests assert sentinel values never reach query keys, cache entries, storage, console output or rendered text. The host status gets typed diagnostics only: `bar.weather.location` (`located`, `denied`, `restricted`, `servicesDisabled`, `notDeterminedTimeout`, `timeout`, `error`, `noUsageDescription`, `unavailable`) and `bar.weather.apiKey` (`problem`: `unresolvable`, `missing`, `notAFile`, `unreadable`, `tooLarge`, `keyAbsent`, plus the resolved path, never a value). Recording them changes no Bar view and no sequence, and a stop clears them.

## Media

**Private API disclosure:** the media adapter uses Apple's private `MediaRemote` framework through a vendored perl adapter; Apple can break it in any macOS release. It is **arm64 only**, was verified on macOS 27.0 only (macOS 27 evidence satisfies the macOS 26+ gate by user decision, 2026-11-10; macOS 26 itself was not separately verified) and any failure hides Media without taking Bar down.

### Media adapter packaging

- **Vendored, never from `_legacy`.** `src/crates/app/resources/media-control/` holds `mediaremote-adapter.pl`, `MediaRemoteAdapterTestClient` and `MediaRemoteAdapter.framework` (upstream `mediaremote-adapter` by Jonas van den Berg, BSD 3-Clause, **arm64 only**). They are the files of the Homebrew `media-control 0.7.7` `arm64_tahoe` bottle byte for byte (no relocation, no re-sign), and both Mach-O files have `minos 26.0`. The upstream `LICENSE` ships next to them; `PROVENANCE.md` records the source chain and history. `scripts/media-control/manifest.json` pins the bottle digest, upstream revisions, every file's hash, mode and symlink. `bun run vendor:media-control -- --check` (offline, in `test:scripts`) compares the directory with the manifest and `-- --verify-upstream` (network, CI) compares it with the bottle and upstream. The formatter ignores `src/crates/app/resources/**`.
- **Bundle.** `bundle.resources` maps `resources/media-control/` to `Contents/Resources/media-control/`. A release `bun run tauri:build` on 2026-11-11 (macOS 27.0) produced a bundle whose adapter files match `scripts/media-control/manifest.json` byte for byte, with their executable bits and the `LICENSE`. `codesign --verify --deep --strict` passes on the app, which is ad-hoc signed with the hardened runtime and seals the adapter files as resources; the framework on its own still fails `codesign --verify`, as in the bottle. Tauri **flattens the framework symlinks**: `Versions/Current` and the top-level `Resources` link are absent and the top-level `MediaRemoteAdapter` becomes a regular copy of the binary. The adapter only loads `<framework>/MediaRemoteAdapter`, so the layout is sufficient, and the resolver follows symlinks. The adapter's `test` and `stream --no-diff` ran from the bundled copy on that date; macOS 26 itself is not verified.
- **Resolution.** `stache_app::media_resources::MediaResources::resolve(resource_dir)` returns absolute paths for the script, framework and test client, or a typed `MediaUnavailable` (`UnsupportedArchitecture` on non-arm64 hosts without touching the disk, `NoResourceDirectory`, `NotAbsolute`, `Missing`, `WrongType`, `NotExecutable`). It uses Tauri's resource directory when `media-control/` exists there and otherwise, in debug builds only, the in-repo copy through `CARGO_MANIFEST_DIR`. Release builds never fall back to a source path and nothing reads `_legacy`.
- **Feasibility (BAR-07-01 evidence).** See [07-media](../specs/2026-11-03-bar/07-media.md#feasibility-evidence-2026-11-10): the adapter streamed on macOS 27.0 arm64 with no prompt and no descendant; absolute paths are mandatory.
- **Streaming primitive.** `CommandExecutor::open_line_stream` in the SDK (see [sdk.md](../architecture/sdk.md)) is the bounded line reader and exact-child stopper. An idle stream waits with `poll(2)` on the child's pipes plus a cancel wake fd and no timeout, so a silent adapter causes zero wakeups. Default checks spawn no adapter, perl or media process.

### Media data path

- **Lifecycle.** One `stache-bar-media` worker (plus a `stache-bar-media-art` decode thread) lives inside the `ProviderMonitor`, so it exists only for an enabled, unpaused Bar with a panel. Disabled, paused, failed, gated and zero-size runs own no media thread and no child. The command is `/usr/bin/perl <script> <framework> <test client> stream --no-diff` with absolute vendored paths, one exact owned child, spawned through `CommandExecutor::open_line_stream` with a 24 MiB line cap and an 8 KiB stderr tail. Resources resolve on the worker (`MediaResources::resolve(app.path().resource_dir())`); unavailable resources (missing files, not arm64) spawn nothing, publish an `unavailable` status and are re-checked only when Bar restarts.
- **Parsing.** `{type,payload}` lines; only `type == "data"` with an object payload is used, everything else (bad JSON, other types, non-object payload, nesting past serde_json's limit of 128, oversized, unterminated or non-UTF-8 frames) is ignored and leaves the state unchanged. With `--no-diff` each line **replaces the whole state**. Unknown keys are ignored, wrong-typed optional fields count as missing, title/artist/album are trimmed and capped at 1024 characters, bundle identifier and media type at 256. Identical published states are coalesced (no sequence bump).
- **Absent state.** A payload **without a title** (and an empty payload) is the absent state: `media: None`. A missing artist is `""` (label is the title alone), a missing `playing` is paused (`Paused: ` prefix), a missing bundle identifier is `""` (unknown icon, inert click). **Approved deviations from legacy:** legacy emitted nothing for an empty payload, so its UI kept showing the previous track after playback stopped; here an empty payload hides Media (user, 2026-11-10). A title-less payload with an artist hides Media; legacy rendered ` - Artist` (user, 2026-11-10).
- **Published shape.** `BarView.media: MediaReading | null` = `{ title, artist, album, bundleIdentifier, mediaType, playing, artworkId }` (camelCase; `artworkId` is `null` while decoding or when the current state carries no usable artwork). The condition lives in `BarRuntimeStatus.media` = `{ state: running | restarting | unavailable, reason, stderrTail }` (sanitized: control characters removed, base64-looking runs dropped, last 512 characters; never artwork bytes), and changing it does bump the Bar sequence because the providers' state is part of the observable cell.
- **Artwork.** The bytes never travel in `BarView`/`BarChanged`. The decode thread (single slot, newest wins, older pending decode dropped, results for a superseded track discarded) ports the legacy pipeline: reject a `<` placeholder, MIME to PNG/JPEG/WebP/GIF/BMP, encoded 16 MiB, decoded 12 MiB, 8192 per axis and 16 Mi pixels (checked from the header before the pixel decode, plus a decoder allocation limit), center-crop, Lanczos3 to 128x128, PNG. The id is the lowercase hex SHA-256 of the final PNG (content addressed, so equal art shares a file and title/artist can no longer collide). **Retained art:** a payload without usable artwork (the first line of every track change, a bad image, a placeholder) publishes `artworkId: null`, exactly like legacy omitted `artwork`; the legacy hook kept its previous loaded image in that case (it only changed `loadedArtwork` on a new image load or error), and the UI keeps doing so. A repeated or recently seen image is recognized by fingerprint and not decoded again.
- **`bar_media_artwork(id)`** returns `BarArtworkOutcome` (`ready { artwork }` base64 PNG text, `missing`, `unauthorized`, `unavailable { reason, detail }`). Authorized exactly like `bar_weather` (live Bar window label; unavailable while Bar is not running or has no panel), ACL-gated (`allow-bar-media-artwork` in `capabilities/bar.json`). The id must be 64 lowercase hex digits or the answer is `missing` before any filesystem access. Runs on the blocking pool.
- **Cache.** `<app cache dir>/media-artwork/<id>.txt` where the app cache dir is Tauri's for `com.marcosmoura.stache.next` (`~/Library/Caches/com.marcosmoura.stache.next/`), base64 text as in legacy. Directory `0700`, files `0600`, atomic write (temp file in the same directory, `O_NOFOLLOW`, rename), a symlinked directory or entry is never followed, reads are bounded (512 KiB) and verified against the id, at most 64 entries are kept (oldest pruned) and four live in memory. The legacy cache (`media_artwork`) is never read or reused. All cache I/O runs on the decode thread or the blocking pool.
- **Restart.** A child that exits, crashes, closes stdout or fails reading is restarted after 1, 2, 5, 10, 30 and then 60 s per consecutive failure (cancellation-wakeable, never a spin); a run that streamed for at least 60 s resets the count. While restarting Media is hidden (`restarting`); from the third consecutive failure the status is `unavailable` until the next valid line. After 8 consecutive failures (5 more after it became `unavailable`; backoffs 1, 2, 5, 10, 30, 60, 60 s, 168 s in all) the adapter gives up (status `unavailable` with a "keeps failing; not restarted until Bar restarts" reason): no further child is spawned and Media stays hidden until the next Bar start or resume (a plain config reload keeps the same run and does not restart it; use Pause then Resume). Bar stays Running throughout.
- **Stop.** Stopping first invalidates the media (nothing is published afterwards, a late line, exit or decode cannot reach a successor), then `LineStream::stop` sends SIGTERM to the exact child, escalates to SIGKILL after the grace and reaps it. A child that cannot be confirmed gone stays retained by the media executor: the worker rechecks a bounded number of times, never starts a second child, and the monitor stays unsettled (Bar reports cleanup pending) until a later sweep reaps it.
- **Media click.** `bar_action("media")` carries no identifier. The host reads the currently published bundle identifier and maps exactly `com.spotify.client` (Spotify), `com.microsoft.edgemac.Dev` (Microsoft Edge Dev), `com.tidal.desktop` (Tidal) and `org.jeffvli.feishin` (Feishin) to the same application path as the other clicks. Unknown or absent media answers `notAttempted` and launches nothing.

### Media UI

- **Data.** `barDataFromOutcome` maps `BarView.media` to `BarData.media` (`MediaPayload`: title, artist, album, bundle identifier, media type, playing; no artwork). `null` hides Media, so the empty/stopped state, a restarting or unavailable adapter and an `unavailable` snapshot all show the legacy absent state. Label, `Paused: ` prefix, scrolling, icon map and styles are the ones already parity-tested; nothing visual changed.
- **Artwork by id.** `BridgeBarData` (never run for fixture data) calls `useMediaArtwork(artworkId)` (`Media/Media.artwork.ts`): a React Query keyed by the id (a non-secret content hash), `staleTime: Infinity`, `gcTime` 60 s, no retry, calling `bar_media_artwork(id)`. `ready` yields the base64 PNG, which `useMedia` preloads exactly as before (`data:image/png;base64,`, allowed by the CSP's `img-src 'self' data:`). `missing` is cached as no artwork; `unavailable`, `unauthorized` and a rejection are query errors; none adds placeholder styling. The same id is fetched once; a new id fetches again.
- **Retained artwork (legacy behavior).** `useMedia` only changes the displayed image on a successful new image load (set) or an image error (cleared), as legacy did. A payload with `artworkId: null` (the first line of every track change), a pending fetch or a failed fetch leaves `artwork` unset, so the previous image stays. A response for an older id lives under the older key and can never be shown for a newer id. When media becomes `null`, Media hides; the hook state (and so the last image) survives for the next track, as in legacy.
- **Click.** Media's click is `barClick('media')` (`bar_action('media')`, no identifier). The host maps the published player and answers `notAttempted` for an unknown one; no outcome changes the DOM (only `console.debug` for non-`completed`). The unknown-player look is the legacy PlayCircle02 icon. Legacy Media was clickable and its `Button` look is unchanged.

## Keep Awake indicator

### Keep Awake indicator data

`BarView.keepAwake` is `KeepAwakeIndicator | null` (`{ active, paused, enabled }`, camelCase). The UI maps it into `BarData.keepAwake` in the bridge data path only (`null`/absent becomes `undefined`, `{ active }` becomes the boolean), so the component and its fixtures are unchanged. There is no Keep Awake-specific command; the click uses the generic session action (below). Keep Awake absence, disablement or failure never stops Bar.

- **Source.** Keep Awake publishes its original `KeepAwakeRuntimeStatus` through the SDK published-state channel (schema `keepAwakeStatus` v1, see [Keep Awake](keep-awake.md#published-state)). Bar lists `keepAwake` in `ModuleDescriptor::observes` (optional: no `requires`). The app (`bar_keep_awake.rs`) observes the channel, combines it with the registry's `enabled`/`paused`/status for `keepAwake`, and projects the view; the bridge adds the projection's change counter to Bar's own sequence so a Keep Awake change is a newer `BarChanged` through the same worker.
- **`null`** only until the first observation resolves (Keep Awake enabled, not paused and not started yet); it never returns to `null`. The UI renders nothing for it (legacy loading branch).
- **`active: true`** only for the current, available state of the accepted generation with a confirmed adopted `active` assertion and an unlocked screen while the module is Running and not paused. Every other case is `active: false`: locked, unknown lock, acquiring, releasePending, paused, disabled, absent, failed, tombstone, wrongly versioned or malformed payload. Bar never probes the lock and never infers active/inactive from lifecycle alone.
- **`paused` / `enabled`** are the registry's session pause flag and accepted `enabled` flag (the facts the click is based on), never inferred from colour. A rejected `keepAwake.toml` (malformed, wrong boolean, deleted) keeps the last accepted state and revision, so the view does not change; identical-good repair changes nothing.
- **Recovery.** Reads sample the state cell and registry snapshot (in memory only). A late write or tombstone of an older generation and a backwards sequence are ignored; a new generation resets the sequence. The cell coalesces (no queue to overflow) and a large sequence gap makes the bridge send a `resnapshot`. One watcher thread starts when Bar first runs (a disabled Bar owns none) and waits on the published-state cell with **no timeout** (a change, registry close or shutdown cancellation are its only wake-ups); it joins at shutdown. Pause/enable flags of a provider that is not running do not move the cell, so the **host status sink** (`HostUi::status`, called on every host lifecycle or session publication) calls `BarBridge::host_changed`, which only pokes the bridge worker; the worker re-samples the projection and emits a `BarChanged` only for a real change. There is no timer: an idle Bar performs zero Keep Awake wake-ups (a test counts them).

### Keep Awake session click

Clicking the Keep Awake indicator calls the generated command `bar_session_action(module, action)`, the minimal **generic** host session action: `module` is a string validated strictly and `action` is the closed enum `pause | resume` (`enable`, `disable`, `retry` or anything else cannot deserialize). It is not a `BarAction` variant because the action is not a fixed target launch and the Rust core is generic (any module id, Pause/Resume through the existing `ModuleControl`); the **Bar capability** may only request Pause/Resume of `keepAwake`.

- **Authorization.** The actual calling webview must be the live Bar panel (like `bar_action`): test/access/shell/forged/stale labels, any other module and any other action are `unauthorized` before anything reaches the host; a Bar that is not running is `unavailable{notRunning}`. The command is ACL-gated in `build.rs` and granted only by `capabilities/bar.json` (`allow-bar-session-action`).
- **Execution.** `HostHandle::session_action` sends the request to the host runner thread, which executes it in command order (serialized with tray pauses, reloads and shutdown) through the same `ModuleControl::pause/resume` the tray uses, then publishes the host status. It never enables, disables, retries, edits configuration or acquires anything. The reply is the **actual** result, not a queue acknowledgement.
- **Stale-click rule.** The UI sends the action implied by the `paused` flag of the view it rendered (`pause` while not paused, `resume` while paused; never the colour). At execution the host rechecks the current session metadata and never inverts the request: pausing an already paused module, or resuming one that is not paused, is `stale`. A duplicate click, a second window or a racing tray pause therefore cannot undo a newer decision.
- **Outcomes** (tagged by `kind`, concrete data): `applied`, `notApplied{reason: refused|notReflected}`, `stale`, `disabled`, `unavailable{reason: failed|unavailable|waitingForPermission|releasePending|shuttingDown|notRunning}`, `busy`, `uncertain`, `unauthorized`. Running (locked or not, acquiring) pauses; paused and enabled resumes; disabled or absent is `disabled` (inert, zero configuration writes, no Enable); failed, unavailable or release-pending is a typed non-success with no new acquisition or retry. One request is in flight at a time (`busy` otherwise, never queued), the wait is bounded (15 s) and a shutdown wakes the waiter (`uncertain` once the runner started the request, `unavailable{shuttingDown}` before).
- **UI.** `KeepAwake` uses `keepAwakeClick(session)` (`Bar.actions.ts`), like `barClick`. The outcome produces no UI (only `console.debug` for non-`applied`); the indicator changes solely through the next `BarChanged`. The two visuals are unchanged: no pending/error colour, badge, tooltip, opacity or cursor. An unresolved (`null`) Keep Awake renders nothing and sends nothing.

## Tiling strip data

The data and the click command below are tested end to end with the real Tiling runtime over fakes; the UI that renders them is described in [Tiling strip UI](#tiling-strip-ui).

- **Source.** Tiling publishes its display DTO through the SDK published-state channel (schema `tilingState` v1, see [Tiling](tiling.md)). Bar lists `tiling` in `ModuleDescriptor::observes` (optional: no `requires`) by identifier only. The app (`bar_tiling.rs`) observes the channel, combines it with the registry's status, `enabled` and `paused` for `tiling` and the actor's health, and projects `BarView.tiling`. The projection owns a change counter that never resets (the SDK sequence restarts per generation); the bridge adds it to Bar's sequence with Keep Awake's, so a Tiling change is a newer `BarChanged` through the same worker.
- **States.** `BarView.tiling` is `TilingStripView | null`, tagged by `kind`:
  - `null` only until the first observation resolves (Tiling enabled, not paused and not started yet); it never returns to `null`.
  - `loading`: Tiling is Running, healthy and not paused, and its current generation has not published yet.
  - `available { generation, sequence, workspaces, apps, focusedApp, focusedWorkspace }`: a current, decodable state of the running generation while the registry reports Tiling Running, enabled and not paused and the actor reports healthy. `generation` and `sequence` are decimal strings. `workspaces` is every workspace `{ name, focused }` in Tiling's order (the UI sorts them). `apps` (`{ key, appName, title }`) are the windows of the globally focused workspace that are not minimized, not hidden and the active tab of their native tab group, in Tiling's order. `focusedApp` is the focused window looked up among all published windows (`null` if none); `focusedWorkspace` is the focused workspace name. Titles are carried unchanged.
  - `absent`: everything else: not registered, disabled, paused, stopping, failed, quarantined, unavailable, unhealthy (a caught actor panic, unwind builds only; release builds abort), every tombstone, a schema or version mismatch and a malformed payload. A stale provider is never shown as available.
- **Recovery and wake-ups.** As for Keep Awake: reads sample the state cell, the registry snapshot and the actor's health cell in memory; a late write or tombstone of an older generation and a backwards sequence are ignored. One watcher thread starts when Bar first runs (none for a disabled Bar), waits on the cell with **no timeout** and joins at shutdown; registry lifecycle changes arrive through `BarBridge::host_changed`. Tiling publishes only when its DTO changes, so window moves, resizes and other frame-only activity cause zero watcher wake-ups and zero `BarChanged` (a test counts them). A caught actor panic (unwind builds only; release builds abort) does not move the cell; it reads as `absent` at the next re-sample of the view.
- **Click command.** `bar_tiling_action(request)` with `request = { generation, sequence, action }`, where `action` is the closed enum `{ kind: "focusWorkspace", name } | { kind: "focusWindow", window }` (`window` is the opaque key). Unknown kinds or fields do not deserialize. ACL-gated in `build.rs`, granted only by `capabilities/bar.json` (`allow-bar-tiling-action`).
  - **Authorization.** The actual calling webview must be the live Bar panel: test/access/shell/forged/stale labels are `unauthorized` before anything reaches Tiling; a Bar that is not running is `unavailable{barNotRunning}`.
  - **Validation.** A generation or sequence that is not an exact decimal `u64` (sign, leading zero, overflow) is `invalid`. Tiling's availability is checked next from the same registry and runtime facts as its socket handler. Then the rendered `generation` must equal the current published one and the rendered `sequence` must not be ahead of it, otherwise `stale`.
  - **Execution.** Tiling's own typed path (`TilingFocus`, sharing the socket handler's action lane, bounded record wait, cancellation and settling) resolves the window key against the live runtime snapshot (`stale` if no current window carries it) or checks the workspace name exists (`stale`), and submits `FocusWorkspace(name)` or `FocusWindow(Window(token))`; the actor revalidates at issuance. A click never enables, resumes or reconfigures Tiling and never queues behind another action.
  - **Outcomes** (tagged by `kind`): `applied`, `noOp` (already focused), `stale`, `unavailable{reason: barNotRunning|notRunning|disabled|paused|cleanupPending|shuttingDown|unhealthy}`, `busy` (another Tiling action holds the lane or the queue is full; nothing sent), `uncertain` (sent, but the wait ended first, for example at shutdown; never retried), `refused` (the actor refused for another reason), `failed` (Tiling's mailbox is closed or the admission budget was spent), `invalid`, `unauthorized`. No outcome produces UI; the strip changes only through the next `BarChanged`.
- **Independence.** Tiling absent, disabled, paused or failed only makes the field `absent`: Bar and its other components (Keep Awake included) keep running. Tiling never reads Bar's configuration; it follows the host screen reservation, so a disabled Bar leaves Tiling managing windows without the inset.

### Tiling strip UI

`src/ui/src/shell/windows/Bar/Spaces/` is legacy `Spaces/**` ported unchanged (Spaces, WorkspaceList, Workspace, AppList, App, constants, styles, motion: `LayoutGroup`/`AnimatePresence`, the `workspace-indicator` `layoutId` with a spring of bounce 0 over `durationSlower`, the app reveal width `0`↔`auto` / opacity `0`↔`1` with a label-length-scaled duration and the design-system ease; legacy has no `MotionConfig`, so reduced-motion preferences do not change it).

Nothing is sent while the strip is not `available`. Every outcome other than `applied` (including `noOp`) and a rejected call only reach `console.debug`; nothing is drawn.

- **Icons.** `@hugeicons/core-free-icons` 4.4.0 (with `@icons-pack/react-simple-icons` for Proton VPN, TIDAL and Transmission). `workspaceIcons` is legacy verbatim. `appIcons` keeps every legacy entry, including the `\u200EWhatsApp` key (WhatsApp's bundle name starts with an invisible U+200E) next to plain `WhatsApp`, `Microsoft Edge Dev` and the `DashboardCircleIcon` fallback for unknown (trimmed) names, plus the 2026-11-10 approved entries keyed by exact `CFBundleName`: `Zed` → `CodeSquareIcon`, `Aside` → `AiBrowserIcon`, `Herdr` → `CommandLineIcon`, `DeviceHub` → `SmartPhone01Icon`, `AIOStreams` → `PlayListIcon`, `Nuvio` → `Tv01Icon`, `FigCraft` → `PaintBoardIcon`.
- **Unknown workspace.** A workspace name with no entry in the workspace icon map (for example `workspace-1` from an empty `tiling.toml`) renders its button and focus indicator without an icon. Legacy passed `undefined` to `Icon` there, which throws in `HugeiconsIcon` and replaced the whole Bar with `QueryErrorFallback`; that crash is not kept (approved deviation, 2026-11-10). There is no fallback workspace icon.

## Content Security Policy

`src/crates/app/tauri.conf.json` `csp` is `default-src 'self'; object-src 'none'; base-uri 'none'; connect-src ipc: http://ipc.localhost https://weather.visualcrossing.com https://api.open-meteo.com https://geocoding-api.open-meteo.com; style-src 'self' 'unsafe-inline'; img-src 'self' data:`. `devCsp` is the same with `http://localhost:1420 ws://localhost:1420` added to `connect-src`. `connect-src` admits exactly the three weather hosts; `img-src 'self' data:` admits the media artwork `data:` URLs (legacy allowed `img-src 'self' data: blob:`; `blob:` is not needed). No wildcard, remote script or `unsafe-eval`; `host_policy.rs` asserts the exact host set and the absence of ipapi/ipinfo. Tauri does not enforce the CSP under `bun run tauri:dev`, so the dev live runs could not prove it; artwork under the real CSP in a bundle is **unverified**.

## Known gaps and limits

- **Verified in the release `.app` (2026-11-10):** media from the bundled adapter with artwork under the production CSP, and the Keep Awake pause/resume click.
- **Unverified live:** the Edge Dev, Tidal and Feishin clicks; Visual Crossing (needs a key) and Open-Meteo geocoding (only used for a city-name `default_location`); the Weather click; display hotplug on a real desktop; which menu-bar signal path (notifications or the layer-25 window-list fallback) delivered the observed auto-hide.
- **Performance (BAR-05-04).** Measured 2026-11-10 with `bun run measure:bar` (release `.app`, M1 Pro, Bar 28/14, auto-hide on): Bar adds +0.59 % of one core on average (0.14 → 0.73 %) and +0.39 idle wakeups/s (0.60 → 1.00); see [the report](../specs/2026-11-03-bar/measurements/2026-11-10T19-33-59-056Z/report.md). The relative budget against legacy stays unverified (no trustworthy legacy sample).
- **Menu-bar poll.** While auto-hide is on (or unknown) the menu worker samples every 100 ms; the user decided (2026-11-10) to evaluate it after `bun run measure:bar`.
- **No native Wi-Fi events.** No CoreWLAN event source is wired; Wi-Fi polls every 5 s (the signal seam is fake-tested only).
- **Private API.** Media depends on private `MediaRemote` through the vendored adapter, arm64 only.
- **Tiling strip.** Clicks and focus on a real desktop are **unverified live** (fake-proven only, see [Tiling strip data](#tiling-strip-data)). A caught Tiling actor panic reads as `absent` only in builds that unwind; release builds abort on panic, so that path is dev-only. Post-integration [`measure:bar`](../specs/2026-11-03-bar/measurements/2026-11-11T00-25-13-045Z/report.md): +0.58 % of one core and +0.44 idle wakeups/s Bar on−off (2026-11-11, matching the 2026-11-10 baseline +0.59 %/+0.39/s; one off trial was quit from the tray, so the tool marks the run failed with 4 valid off launches; accepted by the user).
- **Dev consent.** `bun run tauri:dev` never shows the Location prompt and always uses `default_location`.

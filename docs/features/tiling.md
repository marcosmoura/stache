# Tiling (core and virtual workspaces; default disabled)

Read when using or changing the Tiling module. Tiling is a **default-disabled module**: set `enabled = true` in `tiling.toml` and grant Accessibility to start it. It ships the core runtime, virtual workspaces and the `stache tiling` CLI with its socket methods ([CLI](#cli)). Native tabs (a shared tab bar identity, see [Native tabs](#native-tabs)) and passive drag (part 08) ship fake-proven and native-unverified; opt-in animation (part 08: per-application AX threads, display-clock pacing, the Enhanced UI lease, an instant fallback and per-application metrics) ships the same way; opt-in borders drawn by Stache itself ([Borders](#borders)) ship the same way; the Bar workspace strip (part 10, [Tiling–Bar integration](../specs/2026-11-08-tiling-bar/00-overview.md)) ships fake-proven and native-unverified (see [Tiling strip UI](bar.md#tiling-strip-ui)). Native behavior is fake-proven; real AX, hide/unhide, activation and display behavior is **unverified** until a per-run approved live check.

## What works when enabled

- **Windows and workspaces.** The runtime follows windows through per-application AX shard threads and arranges them in virtual workspaces (not macOS Spaces): one visible workspace per display, one global focused workspace with focus history, stable window order, and eight layouts (`dwindle`, `split`, `split_vertical`, `split_horizontal`, `monocle`, `master`, `grid`, `floating`). An empty config creates one default workspace per display; configured workspaces match `main`, `primary`, `secondary` or a display name, fall back to main when their display is missing and return when it returns. New windows go to the first workspace whose rules match, else the focused workspace on their display. Ignore rules, system components, Picture-in-Picture windows and Stache itself are never managed. Grid tiles at most ten windows and leaves extras floating. Accepted config reloads update the running workspaces and windows without a restart, and a rejected candidate changes nothing (see [Reloading workspaces](#reloading-workspaces)).
- **Placement.** Frames come from the display's visible frame, the host's screen-reservation insets (for example the Bar) and the configured gaps, written position then size and accepted only after a readback. A refusing or unresizable application yields a partial or uncertain outcome, never a guaranteed geometry. The status counts windows whose latest placement is partial, uncertain or refused.
- **Application-level hide and unhide.** Inactive-workspace windows are hidden by hiding their application, which cannot isolate windows of one application across workspaces: a visible workspace that needs the application wins, other windows of it stay visible and the status counts the partial-isolation conflict. Only exact applications the runtime itself hid are tracked as owned; prehidden or externally hidden applications are never owned. Stop and disable restore only still-alive, runtime-owned exact instances. An unhide that fails stays owed and quarantines the stop for retry; a hide whose attribution is ambiguous (a show was observed while our hide may have landed) is retained, reported in `ambiguousVisibility` as `Name (bundle id, pid N): reason` (display-only facts with fallbacks when unknown; the opaque id is never shown) and never unhidden automatically, because recovery needs explicit approval. Ambiguous records survive stop and start (they are merged by exact application within a run and by live process across runs, because application ids are run-scoped; the process id only keeps or drops a diagnostic record and never authorizes an action; they are never forgotten and never seeded into a new ledger as owned) and stay in `ambiguousVisibility` while Tiling runs; one is dropped only when its process is proven gone at a later start or stop. During a restore, a public `unhide` that the system accepted counts as cleared, since that path has no confirming readback; the `AXHidden` fallback counts only with a confirming readback. The target applies the write asynchronously, so when the immediate readback is not `false` the restore re-reads `AXHidden` for every such application together (every 25 ms, one shared 250 ms window that never passes the restore's own hop, cancellable, never on the main thread, no lock held); a confirming `false` clears the record, a readback still `true` or unreadable at the end leaves the unhide owed with its reason. Runtime (non-restore) unhides do not re-read.
- **Layout slots of runtime-hidden applications.** The windows of an application Stache itself hid (a ledger record that is `Confirmed`, `PendingIssued` or `PendingPossible`, including one whose unhide is in flight and until it reads shown) keep their layout slot while their workspace is visible: the actor copies the owned set into the pure state before each transition, so siblings are planned around the slot at once and never widen to a full-width intermediate while the unhide lands. Nothing is written to such a window while its application reads hidden; it is written once it reads visible. Only an application hidden by someone else (never owned) is excluded from the layout, and it is never unhidden.
- **Focus.** Focus intents (issued by `stache tiling window --focus` and `workspace --focus`) unhide an owned-hidden application before activating it through the one exact activation path and raising the window.
- **Empty workspaces and Finder.** macOS does not hide the last visible regular application, so a switch to an empty workspace can hide the previous workspace's frontmost application only while something else stays visible. Finder hosts the desktop: Finder without a tracked window is shown whoever hid it, since showing it shows no window (only the desktop icons, which a hidden Finder also hides, come back): once per run after startup has tried every listed application (an earlier run may have hidden it; `AXHidden` is read first and nothing is sent when it is visible), when its last tracked window closes while Stache holds it hidden, and when it is observed hidden in a turn that hides something (a switch needs it; otherwise a Finder the user hid is left alone). The once-per-run check is spent when startup completes, even if Finder had windows then. While its un-hide is in flight Finder briefly appears among the applications Stache hid in `query status`. Every other application, and a Finder with tracked windows, is never unhidden unless Stache hid it. Every planned unhide is sent before the hides of the same turn. Stache never activates Finder; macOS makes it the active application when the last other one hides, so the menu bar shows Finder while an empty workspace is focused. Focusing a workspace with windows then shows and focuses its window as usual, and a windowless Finder stays shown. When Finder has tracked windows only on hidden workspaces it stays hidden and cannot host, so a switch that leaves no application needed on any visible workspace picks another running application with no window that Stache has listed as host: no tracked window and no window its listing returned (an ignored or excluded window counts as a window), never Stache or a non-regular application. The active one is preferred, then one that is not hidden, then the lowest application id. Stache shows it if it is hidden (the same ownership rules as for Finder: one someone else hid is shown only in a switch that needs it), activates it through the exact activation path, and sends the hides only once it is active (at most one second, or at once if the activation is refused), because macOS would otherwise activate and show a hidden application with windows instead. It logs one line, for example `tiling: desktop host Live (com.ableton.live)`, and the menu bar shows the host's name while the empty workspace is focused. The host then simply stays shown: focusing a workspace with windows shows and focuses its window as usual, and the host is hidden only if it gains tracked windows on a hidden workspace (a window it opens while hosting follows the rules of any new window). Known limit: when Finder has tracked windows only on hidden workspaces and every other running application has windows, the last visible application cannot be hidden. When Stache knows this in advance (the frontmost application would be the last visible one: every other application was reported hidden, is held hidden by Stache or is being hidden), it does not send that hide, because macOS would only deactivate the application; it logs `tiling: cannot show an empty desktop: …` once. The decision is re-evaluated on every turn, not only at the next switch: for example, a windowless application that launches becomes host and the hide goes out. While an application is kept, the Bar and the published state show the empty workspace as focused although the kept application's windows, which belong to a hidden workspace, are still on screen. When another application's visibility is unknown, the hide is sent; if macOS refuses it, it is abandoned with a log line saying so (`… and no windowless application was available as host either`) and retried at the next switch. Another known limit: the accessibility listing returns only windows of the current Space, so an application whose windows are all on another Space or in a native fullscreen Space looks windowless unless Stache listed or saw one of them focused earlier; a Space change re-lists only applications with tracked windows that left the listing, not such an application. Chosen as host, its activation can make macOS switch to that Space.
- **Inactive workspaces.** A workspace is inactive when no live window is assigned to it (a minimized or hidden window counts, a closing one does not), it is not visible on its display and Stache cannot show it as an empty desktop. It can, once startup has tried every listed application, when a workspace visible on another display has a window, when Finder runs without a tracked window (it hosts the desktop) or, while Finder is running, when the desktop-host selection above finds a running application with no listed window (Stache uses such a host only while Finder is held hidden, so without a running Finder it does not count); until startup completes only the other-display rule applies. Focusing an inactive workspace (`workspace --focus`, a key binding through the same intent or a Bar click) is refused: nothing changes and nothing native is sent, so the previous application is never left on screen under an empty workspace. The CLI answers `Workspace is inactive` (exit 1, later actions skipped, like `Workspace not found`); a Bar click answers `refused`. The refusal shows in the intent log line and the state keeps the last one (the workspace and a counter that increases on every refusal, starting again in a new run), which is published (`refusedFocus`). The workspace cycle steps over inactive workspaces (with fewer than two left on the display it does nothing). Sending a window to an inactive workspace and a rule that places a new window there work as before, after which it is no longer inactive. The visible workspace is never inactive, even when it is empty. One pure function decides (`workspaces::unreachable`); the focus intent, the cycle and the published flag all use it. The kept-last fallback and the abandoned-hide retry below still apply when the focused workspace empties by another route (its last window closes or is sent away).
- **Reservations and displays.** The module consumes the host's screen reservations from its first write and observes native displays itself (a main-thread observer that only enqueues a hint, a worker that queries the layout, the initial layout delivered before the first frame). Tiling never applies a screen topology to the host registry; Bar owns that.
- **No persistence.** Workspace state lives in memory only; a fully stopped and restarted runtime starts from the config, with no cross-restart recovery.
- **Lifecycle.** Disabling, pausing or losing Accessibility stops Tiling and leaves other modules running. A stop that cannot finish is quarantined with the owed stages visible in the status (`owed`), is never force-cleared, and a restart retries only those stages.
- **Status.** `ModuleStatusView.tiling` carries the lifecycle state (`inactive`, `running`, `stopping`, `quarantined`), the adopted config revision, plan sequence, health, owed stages, `diagnostics`, `ambiguousVisibility`, `partialOutcomes` and `visibilityConflicts`. Missing Accessibility is the registry's `waitingForPermission`; an unhealthy actor shows `unavailable`.
- **Published state.** Each run publishes `TilingPublishedState` (provider `tiling`, schema `tilingState` v1, `published.rs`) through the SDK published-state channel: every workspace (`name`, `screen` as the decimal `CGDirectDisplayID`, `screenName`, `visible`, `focused`, `order`, `inactive`, see Inactive workspaces), every managed window (`key`, `appName`, `title`, `workspace`, `minimized`, `hidden` for the window or its application, `tabActive` false for an inactive native tab) in workspace then stable layout order, `focus` (`workspace`, `window` key) and `refusedFocus` (`{ workspace, serial }` of the last focus refused because the workspace was inactive; absent when there is none or that workspace no longer exists; each new `serial` is a publication). `inactive` and `refusedFocus` were added with defaults, so the schema stays `tilingState` v1. A window key is an opaque decimal string, `(backend epoch << 64) | serial`, never reused within a run and never valid in a later run; `resolve_window_key` maps it back to the exact current window (unknown, destroyed, malformed, non-canonical or ambiguous keys resolve to nothing). The actor publishes only after a configuration is applied and only when this projection changes, labelled with the revision the actor applied; moves, resizes, drags and admission accounting publish nothing. Stop, pause, disable and failure leave the registry's exact-generation tombstone; after a caught actor panic (unwind builds only; release builds abort) nothing more is published. The app's Bar projection observes it (`BarView.tiling`, see [Tiling strip data](bar.md#tiling-strip-data)); the Bar-only `bar_tiling_action` click focuses a workspace or window through Tiling's own typed `TilingFocus` path (same availability rules, action lane, bounded wait and cancellation as the socket's `workspace --focus` / `window --focus`, submitting `FocusWorkspace` or `FocusWindow(Window(token))` after resolving the key against the live snapshot). The Bar renders it as the ported legacy strip ([Tiling strip UI](bar.md#tiling-strip-ui)).

## Reloading workspaces

An accepted `tiling.toml` reload is applied to the running state; a rejected candidate changes nothing.

- **Workspaces.** The live workspaces are the configured ones, in configuration order, everywhere they appear (`stache tiling query workspaces` and the published `tilingState` strip). The workspace name is the identity: a workspace with the same name keeps its windows, focus, user layout and ratios (a changed configured layout replaces the layout; a default-layout edit reaches only workspaces that follow the default). A renamed workspace is a removed one plus a new one. A `screen` edit moves the workspace with its windows to the new display.
- **When windows are re-evaluated.** Only when the workspace names, their order or any workspace's `rules` change (a workspace added, removed, renamed or reordered, or a rule edited). A reload that changes only a workspace's `layout` or `screen`, or any other key, re-evaluates no window, so a manual `send-to-workspace` is kept.
- **How windows are re-evaluated.** Every managed window goes through the startup assignment again. A window that matches a rule goes to that rule's workspace (a new workspace included, and also when it was sent elsewhere by hand). A window that matches no rule stays in its workspace when that still exists, else takes the startup fallback: the focused, else visible, else first workspace of its own display. Windows a workspace receives are appended in their previous order. Floating and minimized state are kept; a moved window loses its pinned floating frame, as with `send-to-workspace`. When the window that leaves was its workspace's focused window, the most recently focused window still there takes over (none when there is no focus history for it).
- **Focus.** The focused workspace stays focused when it still exists; otherwise the workspace now visible on its display takes the focus (with the window that kept the native focus there), else the visible workspace of the main display, else any visible one. When the focused window moves to a visible workspace (for example on another display), it keeps the focus and its workspace becomes the focused one; no native focus request is sent. When it moves to a hidden workspace, the focused workspace keeps the focus and its next window (most recently focused, else first) is focused, natively too, as `send-to-workspace` does.
- **Effects.** Visibility, layout and publication follow from the new assignment through the usual pipeline: a window moved to a hidden workspace is hidden unless its application still has a window on a visible workspace, and the visible workspaces are laid out.

This supersedes the earlier rule of the archived virtual-workspaces spec ([06-virtual-workspaces](../specs/2026-11-03-tiling/06-virtual-workspaces.md)) that a rule edit reassigns no existing window.

## CLI

`stache tiling` talks to a **running** Stache host over the control socket; it
never starts the desktop, the Accessibility owner or the module. The host must use
the same configuration directory (`-c/--config DIR` stays a directory, before or
after any subcommand); a different directory is refused before any request.
Enable the module (`enabled = true`) and grant Accessibility first.

```sh
stache tiling pause                       # waits for the stop acknowledgement
stache tiling resume
stache tiling query screens               # tables; add -j/--json for the whole array
stache tiling query workspaces --focused-screen
stache tiling query -d windows --workspace coding
stache tiling query apps --json
stache tiling query status               # why windows are or are not laid out (phase, failed apps, faults)
stache tiling window --focus left --resize width 100 --resize height -50
stache tiling window --focus 1234         # a numeric window id (shown by `query windows`)
stache tiling window --swap next --toggle-floating --send-to-workspace web
stache tiling workspace --focus web --layout grid --balance --send-to-screen main
```

- **Queries** (`screens`, `workspaces`, `windows`, `apps`) read one snapshot in
  actor order. `query` alone prints its help. `--screen` accepts `main`,
  `primary`, `secondary` or an exact name; `--workspace` is an exact name; the
  focused filters conflict with explicit ones as the help states (conflicts exit
  2). Tables use the legacy rounded layout, `✓`/`✗`, `WxH @ x, y` frames,
  `(no title)` for empty titles and truncation by character count with `…`;
  titles and names print control characters as visible escapes. `--json` prints
  the whole pretty array in a frozen key order (`id, name, ...` as documented in
  [ipc.md](../architecture/ipc.md#tiling-methods)); `-d` adds window columns
  and never changes JSON or apps. Colors appear only on a terminal.
- **Actions** run in a fixed order whatever the flag order: window focus, swap,
  toggle-floating, preset, each `--resize` pair as supplied, send-to-screen,
  send-to-workspace; workspace focus, layout, balance, send-to-screen. The first
  reported failure stops the rest; actions already admitted are **not rolled
  back**. A resize dimension/amount is validated when its pair executes, so
  earlier actions may already have run. `--preset` applies only in a Floating
  workspace and is a silent admitted no-op elsewhere. Swap accepts only the
  exact lowercase values. `--layout` takes the snake_case names (`split_vertical`,
  `split_horizontal`); the old kebab spellings `split-vertical` and
  `split-horizontal` stay as CLI-only aliases, while the socket and query results
  use snake_case only; focus accepts directions case-insensitively
  (`prev` aliases `previous`) or a numeric window id (an unknown id is
  `Window {id} not found`; an id is resolved once and never re-targeted).
- **Exit 0 means admission, not native success.** A mutation the actor admitted
  (`enqueued`) or whose scope is confirmed (`applied`) is silent with exit 0; it
  does not prove that a window moved, and later native results only show up in the
  status and queries. A `partial` or `uncertain` outcome prints `Tiling operation
  partially applied.` / `Tiling operation outcome is uncertain; it may already have
  taken effect.` on stderr with exit 1 and is never retried. `pause` succeeds only
  after the stop is acknowledged. A `pause` or `resume` that arrives while another one is still in flight is not started and reports the same uncertain error.
- **Errors.** Parse errors (unknown flag, bad arity, invalid swap/layout value or a
  flag conflict) exit 2. Semantic and action failures exit 1 on stderr as `stache:
  IPC error: {body}` (for example `Tiling is disabled`, `Tiling is paused`, `Tiling
  cleanup is pending`, `Tiling is not initialized`, `Workspace not found`,
  `Workspace is inactive` (see Inactive workspaces), `No focused window`); the empty-request and resize validation bodies keep the legacy
  `stache: {body}` form. With the host absent, mutations fail with `stache: IPC
  error: Stache app is not running`. Queries print their failure on **stdout** and
  exit 1: `Stache app is not running.` (table) or `{"error":"..."}` (JSON, safely
  escaped) when offline and `Error: {body}` otherwise.
- **Intentional differences from the legacy CLI:** a failed query exits 1 (legacy
  exited 0); a failure JSON is serde-escaped (never interpolated); `partial` and
  `uncertain` are explicit non-zero results; a numeric `--focus` works (legacy
  advertised but rejected it); titles cannot inject terminal escapes. Successful
  commands, flags, JSON and tables are otherwise unchanged. Native effects are
  fake-proven. A real-desktop run on 2026-11-09 confirmed workspace switching,
  CLI focus, queries and the master layout; the formal per-run native gates
  (`validation.md`) have still not run, so the remaining real AX behavior stays
  unverified.

## Diagnosing a quiet desktop

`stache tiling query status` (add `-j` for one JSON object) is read-only and also answers while the runtime is still initializing. It lists the phase (`initializing`, `reconciling`, `complete`, `incomplete`), the global faults that hold every frame write back (no display, missing Accessibility permission, an overloaded event stream, a failed actor), every application that failed to track or whose enumeration was truncated (with the backend outcome and the retries spent), displays that produced no frames and why, applications Stache hid, the applications that move without animation (the [instant fallback](#animation): one `no animation for moves|resizes: <name> (<bundle id>): <reason>; <when>` line each, where `<when>` is `animates again after <n>s`, `animates again on its next layout change` or `for this run`; in JSON the additive `animationFallbacks` array of `{name, bundleId, kind, reason, retryInMs}`, `retryInMs` null for a reason that lasts the run, counted from when the state was last published), the latest intent and its outcome, and every tracked window with its application, subrole, frame and workspace plus every excluded window and the exclusion reason.

**Failures are per application.** The phase is `incomplete` only for a global fault. An application that fails to track, whose enumeration aborts or is truncated, or that is being reconciled holds back only its own windows: layout still runs for every other application and workspace, and a window is never written while its own application is unconfirmed. A failed application is retried only when it is activated or its launch is reported (a routine application list does not retry it), at most three times, and stays in the status until it recovers. A failure that is plausibly transient (the application's accessibility is not ready yet, as right after a launch: `CannotComplete`, another AX failure, or no acknowledgement; never missing permission) is also retried on a time backoff of the actor clock (100 ms, 250 ms, 500 ms, 1 s, 2 s, then it stops and logs a warning), so a freshly launched application is tracked without being activated; the actor wakes for each deadline. A long application list is queued, never failed. Startup (`initializing`) ends once every listed application has been tried, whatever the outcome.

**Which windows are tiled** matches the legacy rules: only regular applications (accessory and background agents such as `MenuBarAgent` are never listed or tracked); system components, Stache itself, Picture-in-Picture windows, Finder "... Info" windows and configured `ignore` rules are never managed; when a window is adopted, sheets, drawers and `AXUnknown` panels are refused, an `AXDialog` must be at least 400x300 and every other window at least 200x150 (an unread frame is judged by its next snapshot, and a layout that later shrinks a tile never untracks it).

**Focus and workspaces follow the user.** The module watches application lifecycle (launch, terminate, hide, unhide) and the frontmost application. The frontmost application at startup, and every later activation (a native Cmd-Tab), reads the application's real `AXFocusedWindow` on the application's AX shard (bounded by the element timeout) and makes that window's workspace the visible one; the windows of other workspaces are then hidden. Until the read answers, only a window already on a visible workspace is focused provisionally, and a workspace is never switched on a guess: an application whose focused window cannot be read leaves the focus alone. An application-level AX focus notification is resolved to its real window the same way. **The window focused when Stache starts stays focused.** While startup is still listing windows, and while a focused-window read of the frontmost application has not answered, that application is never hidden: hiding it makes the system activate another application, and an unhide never gives the focus back. During the startup listing the frontmost application's first listed window takes the focus provisionally (also from a default pointing at another application's window), and once every listed application has been tried its real `AXFocusedWindow` is read once more, so the window the user is on wins over the listing order. If that read cannot be answered the provisional choice stays. A window newly adopted while its application is frontmost (a creation, a single read, or a listing after startup) takes the focus when its own focus notification arrived first (buffered per application, one entry, latest wins, 256 transitions), else the application's real focused window is read once; an application-level focus notification of the frontmost application also reads it. Direction swaps and focus follow legacy: a spatial direction with no window that way does nothing, next/previous wrap. An activation of an application whose hide is still unsettled (the system activates another application when the frontmost one is hidden) is ignored. An activation naming an application that was never listed (no pid yet, not regular then, or launched before the watches were live) asks for one more application list, once per such application, and the watches ask for one when they finish installing.

**Hide/unhide never gets stuck.** The visibility ledger waits for the system's hidden/shown notification for one second of the actor clock (the actor wakes for the deadline, so a lost notification resolves on an idle desktop): an unhide that is never confirmed is released when the application reads visible, retried otherwise (at most three failed unhides, reset when the application is no longer needed), an `Ambiguous` record of an application that is visible is dropped and the application is not hidden again until a workspace needs it (the show may have been the user's), and a hide that did not land is re-sent a bounded number of times (never one whose `AXHidden` readback said hidden: an application that already was hidden refuses the hide and sends no hidden notification, so its stale visible state is not a failed hide); once the retries are spent the hide is abandoned, logged once (`hide abandoned: still visible after every retry`, with the likely cause) and kept as the application's reason. The next intent of any kind (not only a workspace one) or activation gives every abandoned hide one more bounded round, sent at once; a hide still in its last confirmation wait, or an ambiguous record, is not re-armed. Duplicate or late notifications cannot wedge an application hidden or visible.

**Logs.** Through the host logger (stderr in `tauri:dev`): phase changes (a routine `reconciling` to `complete` flip is debug), global faults, application failures and recoveries, displays without frames, intents with their outcome, and every hide or unhide request (info); frame writes that were not applied, lifecycle and activation events, timed track retries, and ledger decisions (debug). The latency-relevant debug lines (activation, hide/unhide plans and reports, lifecycle, frame writes, borders sends) start with `[t+<ms>ms]`, milliseconds since the runtime started, from one shared reference for the actor, the visibility ledger and the borders runner.

## Native tabs

Apps with native tabs (Finder, Ghostty, most AppKit apps) show a whole tab group through **one** window at a time. Tiling keeps one tile and one slot per group by following the group's shared tab bar. The behavior is fake-proven; the AX facts below come from approved read-only probes of Finder on macOS 26. The single-tab transitions below come from an approved read-only probe of Ghostty; the full behavior is fake-proven and **unverified** on the real desktop.

**What AX reports** (probed in Finder):

- `AXWindows` lists only the selected tab's window of each group. Inactive tabs are separate windows that exist only in `CGWindowList`; AX never lists them and no parent or association link exists (`_AXUIElementGetWindow` on a tab button returns the container's id, `SLSWindowIteratorGetParentID` is 0).
- Opening, switching to and closing a tab replaces the window (and its `CGWindowID`) that represents the group. A new tab sends `AXWindowCreated`; selecting an existing tab sends **no** creation; a closed tab sends `AXUIElementDestroyed`; the previously selected window leaves `AXWindows` without being destroyed. During a close or switch the group passes through transient states: a listed window whose `_AXUIElementGetWindow` fails and whose tab bar cannot be read yet.
- AppKit uses **one shared tab bar** that moves into the newly selected window. Each visible tabbed window holds an `AXTabGroup` (a direct child in Finder; searched up to 7 levels in general), and the group element in the new window is `CFEqual` to the one in the old window. This is the continuity key.
- **Single-tab window** (probed in Ghostty): while a window has one tab macOS hides the tab bar, so there is no shared bar to follow. Command-T on window 30 makes window 30 **leave `AXWindows` while it stays alive** (its retained element still reads `AXRole = AXWindow` and `_AXUIElementGetWindow` is still 30, no `AXUIElementDestroyed`), and a new window 1549 appears with `AXWindowCreated` carrying an `AXTabGroup` of two tabs. Command-W on 1549 destroys it and lists the same window 30 again.
- Finder windows report `AXSubrole = AXDialog` with `AXMain`; the admission rule keeps dialogs of at least 400x300.

**Identity (owner side).** On adoption and on every refresh listing, the application's AX shard thread searches the window for its `AXTabGroup` (breadth first, at most 7 levels, 64 children per element and 96 role reads, every read bounded by the 0.5 s element timeout), reads the number of `AXTabs` and the selected one, and retains the group element, owner-confined like every other element. It mints an opaque `TabBarId` per application: a window gets an existing id exactly when its group element is `CFEqual` to a retained one (`stache_macos::windows::TabBarRead`, `TabBar`). Nothing is derived from a frame, a title or a `CGWindowID`, and Tiling can only compare ids for equality. Geometry reads reuse the cached bar (no tree search for a position read); a window known to have no bar is not searched again. At most 16 bars are held per application; a bar no tracked window carries ages out after three settled listings (long enough for the successor of a closed tab to be recognized) and everything is released with the application or at stop.

**Transients.** A listed window that has no readable id **and** whose bar cannot be read is not adopted: no token is minted, its registrations are removed, and the owner reports `EnumerationUnsettled` (alone for a creation, before `EnumerationComplete` for a listing). It is never treated as destroyed.

**Suspended windows (owner side).** A tracked window that is absent from a complete, fresh `AXWindows` listing (a refresh, a creation notification or a command revalidation) is not retired when its element is still alive: a bounded read of its `AXRole` succeeds and `_AXUIElementGetWindow` still returns its id. It is **suspended**: the owner reports `WindowChange::Suspended` once, keeps the element and its observer registrations retained, and answers actions and snapshot queries for it with `StaleReason::Suspended`. When it is listed again (`CFEqual` to the retained element, so the same token) it is reported with a snapshot; a creation notification naming it does the same. A suspended window is retired (`Destroyed`) only when its element dies: an `AXUIElementDestroyed` (a closed inactive tab) or a later listing that finds the element dead or answering for another window id. At most 32 windows stay suspended per application; the oldest beyond that are retired. A truncated, failed, cancelled or unsettled listing never suspends or retires anything. When a creation notification arrives, windows that the listing no longer holds but whose elements are alive are suspended before the new window's snapshot, so the consumer sees the old window leave first.

**Continuity (Tiling side).** A newly seen window that carries the tab bar of exactly one tracked window of the same application replaces it: same workspace, same position in the workspace order, same floating flags, same focus and focus-history entries and the same frame record (an attempt still in flight is dropped, its late acknowledgement is stale). No other window is relaid out, no extra tile appears and nothing is written unless the new window is off its slot. The new window has a new exact token; the old token is tombstoned and never authorizes anything again. The replaced window is not forgotten when it is alive (a tab switch): it stays tracked as a suspended member of the slot, so selecting it again finds it by element identity. It is dropped (and tombstoned) only when it was already destroyed. A window with no bar, an unreadable bar or a different bar is an ordinary new window, and two windows that merely share a frame are never merged.

**Slots and suspended members.** A slot is the tile a group holds: one **active** member (the tile) and any number of **suspended** members (inactive tabs, `WindowState.suspended`), all of the same exact application and tied by an opaque `tab_group` id, never by frame, title or geometry. A suspended member keeps its token but is not a tile, takes no focus, gets no frame write and no snapshot read, is not listed by `query windows` (status shows the count as `suspendedWindows`, and not in `windows`), and is destroyed silently (no layout change) when its element dies.

- **One tab to two (Ghostty, Command-T).** The active window becoming suspended keeps holding its tile (`slot_held`) while the listing settles, so nothing reflows. When exactly one such window and exactly one new window of the same application carrying a tab bar of two or more tabs exist, in either order, the new window becomes the active member of that slot: same workspace, order position, flags, focus, focus history and frame record, no relayout, and no write unless it is off its target. Any other combination (no or several suspensions, no or several tabbed arrivals) hands nothing over: the arrival is an ordinary new window, and when the listing has settled a slot whose active member was suspended without a replacement releases its tile and the layout reflows (debug log). The arrivals are matched as they are seen, so two tabbed arrivals for one suspension are resolved in arrival order (the first claims it).
- **Two tabs to one (Command-W) and switching.** A suspended member that is listed again (`Adopted::Existing`, same token) becomes the active member of its slot, replacing the previous active member when that one was closed (held back) or suspended in the same listing; a single read outside a listing waits for the settle when the slot's active member still looks alive. Switching among tabs works the same way: the previously active member becomes suspended (alive, unlisted) and returns by identity. If the slot has no active member any more (it was released or its window closed), the returning window is an ordinary new tile; if an alive active member remains it is an ordinary new tile of its own.
- Closing the active tab of a slot with suspended members holds the slot like a tab of a bar until the next listing; closing the last window reflows at once.

- **Destroy of a group window.** A window whose bar has two or more tabs is not removed at once on `Destroyed`: it keeps its slot as _departing_ (`WindowState.departing`, never written to) until the settled listing either brings a successor with the same bar or finds none (the last tab closed: a normal close and reflow). A one-tab window is removed at once.
- **Settle.** A creation, a destroy, a window-level or application-level focus or main-window change, for an application with a tracked tabbed window, asks the actor shell for **one** coalesced application listing after `TAB_SETTLE_DELAY` (150 ms on the actor clock; further events inside the delay join it). It is issued through the ordinary reconcile path (`Cause::TabSettle`). A listing that skipped transient windows is repeated after the same delay up to `MAX_TAB_SETTLE_RETRIES` (4) times; then the departing windows are closed for real. Departing windows are only closed by a listing requested after their destroy, and never by a listing that skipped a transient window.
- **Diagnostics.** `diagnostics.tab_handovers`, `tab_departures_held` and `tab_departures_closed` count handovers and held and finished closes; `tab_suspensions`, `tab_returns`, `tab_single_handovers` and `tab_slots_released` count suspensions, returns of suspended windows, single-tab handovers and released tiles. Each handover (old and new token), suspension, return, release and settle retry is logged at debug.

**Limits.**

- Inactive tabs that were never listed (they exist only in `CGWindowList`) are not tracked; inactive tabs that were once listed stay tracked as suspended members for as long as their elements live (at most 32 per application).
- Apps without an AX tab bar, such as custom tab UIs, are ordinary windows. A browser window with its own tab strip carries a bar no other window shares, so it is its own group.
- An app that hides the tab bar while a window has a single tab (Ghostty by default, Finder by default) has no bar on that window. The 1 to 2 and 2 to 1 transitions are followed through the suspended old window (above) instead of a bar; they rely on the old window's element staying alive, as probed in Ghostty. An app whose old window dies instead is an ordinary close and open (a reflow).
- A window that is merely unlisted for another reason while alive (for example on another Space) is also suspended instead of retired; its slot is released when the listing settles and it is tiled again when listed.
- Timing of the transients, the order of `AXWindowCreated` and the departure of the old window, and the depth of Ghostty's `AXTabGroup` are unverified.

**Legacy member reads stay off.** The `CGWindowID`-keyed registry (`tabs.rs`, `state/tab_sync.rs`, `AdapterOptions.read_tabs`, `TabMember`) remains in the tree, fake-proven and unused in production (`read_tabs` is false in `TilingFactory::production`): its mapping from tab buttons to window ids is proven wrong on a real desktop (tab buttons answer the container's id). Status keeps reporting `native tabs are not read ...`.

## Passive drag

Dragging or resizing a tiled window with the mouse is observed, never intercepted. Drag has **no configuration flag** (legacy had none): it runs whenever Tiling runs and the shared input service can install its listen-only tap.

- **Observation.** `drag.rs` subscribes one `InputObserver` (left and right button, down and up, with the event location) through `ModuleContext::input()` as start stage 9, after the authority is published. It uses only the service's **listen-only** tap, which always passes: Tiling cannot suppress, intercept or inject an event or change HQ > MA > KB priority, and a press that an interception consumer suppressed is still seen. The tap exists only while a passive subscriber does and closes with the last one; stop removes the observer first (`Teardown::Drag`). The callback only builds a pure `DragSignal` and calls `Ingress::submit`; it reads no window and runs no AX. Moved and dragged events are not observed. Input Monitoring is not a typed permission, and Tiling's permission requirement is unchanged (Accessibility, user-only).
- **Degraded, not failed.** If the service is not attached or the tap cannot be installed, Tiling still runs healthy and `status.diagnostics` says `drag is unavailable ...` (naming Input Monitoring when the install failed). Only drag is off.
- **Bounded lane.** Signals go through a 32-entry drag lane. A full lane drops the new signal, discards what was queued and delivers one `Lost(Overflow)`; nothing is replayed.
- **Gesture.** A down captures the focused workspace's tiled, non-floating windows (exact tokens, stable order, frames) off the callback. While the gesture lasts the planner writes nothing, so the user is not fought and no external-change attempt is spent. A write of ours that completes meanwhile moves that window's baseline to its readback, so a layout echo is never mistaken for the user. The up of the last held button asks for one fresh read per captured window (on the effect worker) and then commits. A gesture older than 60 s, or any lost observation (overflow, a listen-only discontinuity, an input epoch that differs between down and up, Accessibility loss, stop, a down of an already held button) cancels it, reconciles the affected applications once and never invents an up or replays a click.
- **Commit** revalidates the registry, workspace, layout, configuration revision and the exact tile list (stale: no swap, no ratio, plain replan). Then, in order: **resize** when a window's width plus height changed by more than 5 points (legacy `find_resized_window`), mapped onto the workspace ratios as legacy `on_user_resize_completed` (usable area instead of the screen's visible frame, one ratio per layout; Monocle and Floating only replan); else **swap** when the window with the greatest centre travel strictly above 50 points (exactly 50 is not a drag) has its centre inside the first original frame, in stable order and inclusive of the edges, of another tile; else one **snap-back** plan for windows that left their planned frame. Floating windows are never captured, targeted or pulled back.
- **Limits.** The captured workspace is the focused one, so the first press on another display only focuses it. A second down while the first up is still being read cancels that gesture. An already queued read of a window may satisfy its slot before the final one. A busy subscriber snapshot in the input service drops an event silently (counted there as contention); the epoch check catches only disables. All of this is **native-unverified**: no real tap, mouse event or window was involved.

## Animation

Off by default (`animations.enabled = false`, `duration = 200`, `easing = "ease_out"`). When enabled, a frame plan that moves a window by at least 5 points is written as a sequence of eased frames instead of one jump. The curves are the legacy ones (`linear`, `ease_in`, `ease_out`, `ease_in_out`, `ease_out_expo` and a damped spring). The configured duration is clamped to 100–1000 ms and applies from 500 points of travel; shorter moves scale it by the square root of the distance down to 50 ms at 20 points or less. A spring never passes its target (progress is clamped) and ends at the exact target. The duration is scaled **per window** from that window's own travel (legacy scaled it once per batch), so windows moved by one relayout can finish at different times.

- **One owned coordinator.** The `stache-tiling-animation` thread exists only while `animations.enabled` is true; a disabled Tiling (and a default configuration) owns no animation thread, timer or allocation. A configuration reload that enables or disables animation starts or retires it live through the same accepted-revision path; a duration or easing change keeps it. It is never a global or immortal worker. It is a coordinator, not a writer: it computes frames and reads acknowledgements, and every native call happens on the application's own AX thread.
- **Not on a workspace switch.** Animation is only for layout changes inside an already visible workspace (layout, ratio, swap, resize, a new or closed window, the snap-back after a drag). A workspace that becomes visible on its display (`workspace --focus`, native Cmd-Tab or focus switching, send-workspace-to-screen, a returning display, startup) has its windows written directly (`animate: false`), including the later write of a window that only became visible as part of that switch (the application's unhide lands after the layout). The planner marks the windows of a just-revealed workspace until their first write or until they are found already at their target; no timer is involved.
- **Latest plan only.** The coordinator has a bounded mailbox (16 windows). Per window the newest plan replaces an older pending one. A plan that arrives while a window is moving ends the old job as a typed "not sent" for its own plan sequence only (so an A, B, A history can never mark the successor applied) and starts the new job from one bounded readback taken at retarget time; if that read fails or is late (two frame periods) the new job starts from the interrupted job's last acknowledged written frame, else from the planner's frame, never from the old destination. The cap counts every window the coordinator holds (pending, running or settling): a window beyond it, or any window when the coordinator is unavailable, is refused and the caller writes its exact target directly, so no window is ever dropped. A newer plan for a window it already holds is always accepted. Should a job still reach a full coordinator it is sent as one final frame, never a silent no-send.
- **Display-link pacing.** Each tick is a display refresh, not a timer: while a display has running animations the coordinator owns one frame clock for it (`CVDisplayLink`, created on the display's first job and stopped when it has none, so idle and disabled Tiling own **no** clock). The clock's callback only stores a timestamp into a latest-wins slot and wakes the coordinator, so a late coordinator computes one frame for the newest tick, never a burst to catch up. Every job on a ticked display computes its frame for that tick's timestamp and all of them go out as one batch per application in that tick. A display whose clock cannot be created (or whose target display is unknown) is paced by the deadline timer at the clamped refresh rate, and status `diagnostics` say so (`animation pacing: display <id> uses a timer: <reason>`; the note clears when a clock for that display later works). A clock that stops ticking cannot strand an animation: after four frame periods without a tick the job is paced by its deadline timer at the normal frame period (not slower) until a tick arrives again, and is attributed as timer-paced (a fallback it then causes reads `its display has no frame clock and it cannot keep up`). The callback holds only the wake-only mailbox core, never anything that owns a clock, so a CoreVideo thread can never tear a clock down. The display link is deprecated in recent SDKs and its availability and cadence on macOS 26 are **unverified**. Stopping a clock waits (bounded) for a callback in flight; a clock that will not stop is kept, never freed or detached, and `frame clock` stays owed until a later stop releases it.
- **Size animates with the position.** While the plan wants a size and the size changes, every first and intermediate frame writes the interpolated size together with the interpolated position, so a window grows or shrinks smoothly instead of sliding at its old size and snapping at the end. A move that keeps the size writes the position only until the final frame. The final frame always writes the exact target (position, plus size whenever the plan wanted it) with no already-written skip, so a replaced frame or a size an application rounded never leaves the window off its target. A move to another display follows the same rule and is paced by the target display's clock. Pacing is unchanged: the display's native refresh, latest frame wins. An instant move and a direct write are unchanged. A size the application refuses (an unresizable window) ends the animation with that outcome as before.
- **One batch per application, latest frame wins.** Each tick the coordinator computes the next frame of every running window and sends **one batch per application** to that application's AX thread; it never waits for a write. Every AX thread keeps at most one pending frame per window: a newer frame of the same plan replaces the pending one (a dropped frame, counted per animation as scheduled, written and dropped), so a slow application skips frames instead of queueing them while other applications animate on time.
- **Pacing.** Frames follow the target display's refresh rate with the same rule as geometry coalescing (unknown or invalid is 60 Hz, otherwise clamped to 30–360 Hz), ticked by the display clock above, or by the deadline timer where that clock is unavailable. Waits wake on a new plan, an acknowledgement, cancellation or stop; no lock is held across a native call, a submission or a completion.
- **Every frame is gated, write-only and read back once.** Each first, intermediate and final write is the existing gated frame write: generation, accepted revision, exact window token, plan sequence, the plan deadline and the seal are re-checked at the native send. There is no second write path and no per-frame readback. `AXWindows` membership is revalidated at the first and the final frame of an animation only; intermediate frames check the retained element, the destroy-notification invalidation and the gate, and an invalid element ends the animation as `stale`.
- **Outcomes.** An intermediate frame is acknowledged with its write status only; an applied write keeps the window animating. The final frame is the exact target: after a 50 ms settle one bounded readback is taken and that readback alone decides `applied`, `partial` or `failed` (a readback that cannot be taken reports the final write without it, as unconfirmed). A refused, partial, uncertain, unresizable, stale, expired or unauthorized frame ends that window's animation with that outcome at once: there is no final snap and no retry loop (a minimum-size inference still happens from the final outcome as for direct writes). A job that ends (superseded, closed or sealed) while one of its frames is still inside a native call completes only when that frame answers, and reports it if it was issued, so a completion is never reported before the window is known to have stopped moving.
- **Echo suppression.** While a window is animated its attempt stays in flight, so its own move echoes plan nothing, and a window in motion is never assumed to have arrived (an A, B, A plan writes it again). Without a per-frame readback the suppression rests on the in-flight attempt; after the final write the window gets the 50 ms settle, one readback is taken and reported, and at most two later reads that still show a position from the motion are ignored (counted in the diagnostics).
- **Direct writes are asynchronous.** A write that is not animated (a workspace switch, an instant move, a refused or full coordinator) is submitted to the same per-application mailbox without waiting: the effect worker never blocks on a native frame write, the completion is posted from the AX thread when it answers, and the outcome and its single readback are as before.
- **Drag.** No animation starts while a drag gesture is active (plans write nothing), and a gesture start cancels a running animation. The snap-back plan after a drag may animate.
- **Stop.** Stop seals the authority first. The order is sealed, drag observer removed, frame writes drained, **animation coordinator closed and joined**, **enhanced UI leases restored**, restore of runtime-hidden applications, watcher, display observer, backend epoch, actor, effect worker. Frames submitted after the seal are inert on the AX thread; the drain returns only once every issued write has answered, and the coordinator outlives its close until every in-flight frame has answered. An AX thread stuck in a native send leaves `frame drain` and `animation worker` (and a display clock that will not stop leaves `frame clock`; a lease that cannot be written back leaves `enhanced ui restore`) owed (and the restore waiting), the module quarantined and a restart refused until a later stop retries exactly those stages. No frame is written after the seal. **Backend epoch:** an observer registration whose removal fails is quarantined (`backend epoch` owed) and retried by a later stop; registrations of an application whose process has exited are dropped, not owed (they died with it). At process exit, registrations a live but unresponsive application still refuses are only a note: the system releases them with Stache's process.
- **Enhanced UI lease.** Applications with `AXEnhancedUserInterface` on animate every geometry write themselves and lag by about 250 ms, so the application's AX thread suppresses it around frame writes. The lease wraps **every frame write path**: animated first, intermediate and final frames, direct writes (layout, preset, floating centering, the snap-back after a drag) and the fallback-to-instant write. `Raise`, hide/unhide and reads take none. Before the first frame write of a burst the shard reads the attribute on the application element once; if it is on, the shard sets it off and holds a lease owned by this runtime epoch and that exact application instance; if it is off (or the application lacks the attribute) nothing is ever written to it. The lease stays open while the application has pending frames or wrote within a **50 ms idle grace** (`LEASE_IDLE_GRACE`), so chained batches and A, B, A plans reuse it and the attribute toggles once per burst (the toggle is costly in Chromium-based applications); after the grace the shard writes `true` back. It restores **only what Stache changed**: only a lease this epoch took, only to `true`, only on the same application instance; a terminated application drops its lease with no write. A third party that turns the attribute back on during a lease is **detected once** (the shard re-reads it after the final or direct write, and a restore that finds it already on counts the same way), counted, and **not fought**: no second set-off inside the burst, the lease closes without a write and the next burst may take a new lease. An application that does this in two consecutive bursts moves without animation from then on (see **Instant fallback**). A failed read or set means the batch is written without a lease. A failed restore keeps the lease as owned cleanup, retried by the epoch stop and `retry_cleanup` and counted in the quarantine. **VoiceOver:** while VoiceOver is running no lease is taken and the attribute is neither read nor written (the probe reads `voiceOverOnOffKey` of `com.apple.universalaccess` through `CFPreferences`, cached for one second, never on the main thread; it is **native-unverified**). Status `diagnostics` show failures, re-enables and VoiceOver skips as `enhanced ui: <name> (<bundle id>): <note>`; plain leases and restores only update per-application counters. **Known limit:** a hard kill (SIGKILL or a crash) of Stache during a lease leaves `AXEnhancedUserInterface` off for that application until it relaunches; no journal is kept. Whether the target applications ship the attribute on, the latency gain and whether the restore causes a visible jump are **unverified** until a live check.
- **SkyLight batching: not used.** The animation pipeline does not use SkyLight or any other private window-server call to move several windows in one transaction. The batching part of the [animation pipeline spec](../specs/2026-11-09-tiling-animation/05-skylight-batching.md) was skipped by decision, so every frame is a public Accessibility write on the application's own AX thread, and no capability probe or fallback for it exists.
- **Instant fallback.** An application moves without animation (one direct write per window per plan, the same write as with animations off) for one **kind** of layout change when any of these holds, and status `diagnostics` say so as `animation: <name> (<bundle id>) moves without animation for <kinds>: <reason>` (one line per application and reason; `<kinds>` is `moves`, `resizes` or `moves and resizes`). The two kinds are kept apart: a **move** (position only) and a **resize** (the plan wants a size for the window: its size changes). The kind is decided per window write, so an application that cannot animate resizes still animates moves (for example `aligned-left` to `aligned-right` presets of the same size) and the reverse; the metrics history, the 2-of-3 decision, the set and the cool-down are all per application and kind:
  - in 2 of its last 3 layout changes its effective rate was below **15 written frames per second** (`writes fewer than 15 frames per second in 2 of its last 3 layout changes`), or it ended more than **250 ms** after its scheduled end (`ends more than 250 ms late in 2 of its last 3 layout changes`). The thresholds are absolute, not relative to the refresh rate: pacing still targets the display's native refresh, and a 120 Hz display whose application writes about 70 frames per second (dropping the rest, latest wins) still moves smoothly. The thresholds are a last resort for clearly broken applications: a healthy application that writes 20 to 30 frames per second per window with about 100 ms of end lag keeps animating. One record is one layout change per application: the windows of one application in one plan are folded into it (slowest rate, largest latency and end lag, summed frames), so a plan with several windows counts once; the scheduled end is the display tick that produced the job's final frame (a tick is always at or after the configured duration), or for a timer-paced job the timer deadline the final frame was computed at, so the end lag measures only how long after its due tick or deadline the final write was acknowledged (coordinator wake, shard write and acknowledgement) and the phase of the ticks relative to the animation's start is not counted as lateness;
  - the Enhanced UI lease cannot be held: it turned `AXEnhancedUserInterface` back on in two consecutive bursts (`turns Enhanced UI back on`), or the attribute was on and could not be turned off (`Enhanced UI could not be turned off`); the actor decides this when it records the lease note;
  - it shares the overflow AX thread and fails the rate or lag criterion (`shares the overflow AX thread and cannot keep up`);
  - its display is paced by the deadline timer (no frame clock) and it fails the rate or lag criterion (`its display has no frame clock and it cannot keep up`).

  A coordinator that refuses a job because it is full is not a fallback: it is per job and the caller writes that one target directly. **Recovery:** a rate or lag fallback (including the overflow and no-frame-clock variants) ends after a cool-down on the actor clock: 60 s the first time, doubling each time the application re-enters for that kind without a healthy animation of that kind in between, at most 10 minutes; a healthy animation record (neither below the rate nor late) resets the next cool-down to 60 s. No timer exists for it: the cool-down is checked when the actor next handles an input (so before the next plan for the application), and on leaving, that kind's history is cleared, so it takes two new bad records of its next three to fall back again. The Enhanced UI reasons apply to both kinds and stay **sticky for the exact application instance** for the runtime epoch (one of them replaces a recoverable entry). A relaunch (a new instance), a terminated application, a configuration reload that turns animations off (turning them on again starts fresh, history and cool-downs included), and a Tiling restart clear everything. The log gets one info line when an application enters (`tiling: animation: <name> (<bundle id>) moves without animation for moves|resizes (until a cool-down passes|for this run): <reason>`) and one when it leaves (`tiling: animation: <name> (<bundle id>) animates moves|resizes again (its cool-down passed): <reason>`). It never affects another application, never changes the configuration and never turns animations off globally. The actor copies the application ids and kinds of the set into the pure state before each transition and the planner sets `animate` to false for a window whose application is in the set for the kind of that write; the `revealed` rule and workspace-switch behavior are unchanged. When an application enters the set during an animation, each of its running windows of that kind sends one exact final write at the next coordinator tick and no further intermediate frames, then settles as usual. After a plan's final write and its settle readback there is no further write for that plan; a readback that differs from the target is reported and never retried.

- **Metrics.** For every animation that ran to its final write the coordinator records, per exact application, kind and layout change (the windows of one application and kind in one plan are folded into one record: slowest rate, largest latency and end lag, summed frames), the frames scheduled, written (acknowledged `Applied`) and dropped (replaced in the shard mailbox), the effective rate (written frames over the time from the first frame to the final acknowledgement), the per-write latency (submission to acknowledgement, kept in a fixed 64-sample ring per animation and reduced to p50 and p95 at the end) and the end lag. It keeps the last 8 records of at most 64 applications (the least recently recorded application is evicted; a terminated one is dropped), writes them only when an animation ends, and makes no AX call and no per-frame allocation for it. A cut-short animation (fallback switch, supersede, failure) is not measured. Status `diagnostics` show one line per application with data: `animation metrics: <name> (<bundle id>): <n> animations, rate p50 <hz> Hz, dropped <d>, write p95 <ms> ms, end lag p95 <ms> ms`. The rate is measured at AX acknowledgement, not at on-screen presentation, which cannot be observed without Screen Recording.
- **Unverified natively.** Everything above is proven with fakes (fake clock and sink for the coordinator, a fake shard backend that holds, refuses, partially applies or delays writes per application, the real sharded adapter over a fake AX arena for the end-to-end scenarios). Real AX write latency, achieved frame rates (the measurement method is in [performance](../guides/performance.md#animation-measurement-method); no approved native run has been recorded), whether the instant fallback triggers for the target applications, visual smoothness, overshoot-free spring behavior on real applications and the smoothness of resizes are **unverified** until a per-run approved live check. AX has no atomic frame write, so a moving window can flicker between its position and size halves.

## Borders

Off by default (`borders.enabled = false`). With `borders.enabled = true` **Stache draws the borders itself**: one transparent, click-through overlay window per bordered window, owned by the main thread and drawn with Core Animation layers. Nothing external is started, changed or left behind, and nothing native (no window, thread, observer or symbol lookup) exists while borders are disabled. Borders follow live configuration reloads; disabling them removes every border.

- **Coexistence with JankyBorders.** Stache never looks up, starts, stops, resets or configures a JankyBorders service. You may keep running it yourself, independently of Stache; to avoid double borders, turn one of them off (Stache's `borders.enabled` or your JankyBorders).
- **Who gets a border.** A tracked, managed (tiled or floating) window on a visible workspace that is not minimized, fullscreen, hidden, an inactive tab or a suspended slot member, has a known window id and a frame with an area, and whose state draws something. Windows matching the tiling `ignore` rules, `borders.ignore`, the system skip lists or Stache itself never get one. Ignore entries match the application's **bundle id** (`app_id`, case-insensitive exact) or its **localized name** (`app_name`, case-insensitive substring), never the executable or process name (unlike JankyBorders' process-name blacklist); `app_id` and `app_name` of one entry are alternatives, and a title-only entry adds nothing.
- **Which state.** The focused window uses `floating` (floating layout or floating window) while that state is enabled, else the workspace layout's override (`dwindle`, `master`, `grid`, `split`, `split_vertical`, `split_horizontal`, `monocle`) when present and enabled, else `focused`. Every other bordered window uses `unfocused`; `unfocused = false` borders only the focused window. A state is `false`, solid (`color`), gradient (`gradient` `from`/`to`/`angle`, optional `animation`) or glow (`glow`). Colors are hex (3, 4, 6 or 8 digits) or `rgb()`/`rgba()`, read as sRGB; an unparsable color draws a transparent border.
- **Width.** Every border uses one width: the active (focused) state's `width`, so focus changes never resize borders (except the width grow and shrink of `unfocused = false` with a `transition`, below). Five sixths of that width is visible outside the window (calibrated by eye against JankyBorders in native runs 1–3); the remaining sixth sits under the window edge. Borders are always round: the corner radius at the window edge is the window's radius plus 1 pt with `order = "below"` and plus 2 pt with `order = "above"` (user decision, native run 11), and the outer radius adds the visible width. The window radius is each window's real corner radius (on macOS 26 it differs per application), read from the window server through a private `SkyLight` window query resolved at runtime; it is cached per window, re-read when a border is re-ordered or shown for a new handle, and **native-unverified**. When the query is unavailable (a missing symbol) or answers no plausible value (not finite or outside 0–64 pt) the 16 pt macOS 26 fallback is used, and status says so when the symbols are missing. `STACHE_BORDER_RADIUS_DEBUG=1` prints each raw value to standard error for a native check. There is no `style` key any more (square corners are not supported); an old `style` entry loads as an unknown-key warning. `hidpi` (default `true`) sets each overlay layer's `contentsScale` to the display's backing scale (crisp on Retina); `false` draws at scale 1.
- **Gradient angle.** `angle` is in degrees, 0 is left to right, 90 bottom to top (default 90), at any value and on any window shape (the direction is corrected for the window's aspect ratio). This replaces JankyBorders' two diagonal buckets (`top_right`/`top_left`), so a gradient may look different from before for the same angle.
- **Glow.** A soft band of light with no hard line anywhere: brightest at the window edge and fading outward over about the configured width, transparent by about twice the width. Stache renders it as shadow only into a bitmap that is the contents of a dedicated layer (the ring layer stays hidden): a rounded core reaching half the width past the window edge is drawn outside the bitmap twice under a same-colored Core Graphics shadow (blur 1.5 times the width, at the display scale) whose offset brings only the blurred light back, clipped so nothing draws over the window. The bitmap is a small 9-slice tile (both corners' band plus a short straight edge, transparent inside the window edge) that the layer stretches over the whole overlay with `contentsCenter`, so its size does not depend on the window; it is re-rendered only when the scale, width, radius or color changes, never when the window moves or resizes (a window smaller than the tile interior, a few times the width plus the corner radius, renders at the overlay's size instead). (Native run 11 showed that the earlier Core Animation layer shadow drew nothing; native run 12 replaced the crisp ring and halo with the band.) Changes to and from glow cross-fade the band's opacity; a glow-to-glow color change fades the new band in.
- **Placement.** `order = "below"` (default) orders the border directly below its window, so the window covers the inner part and a click on the application never flips it; `order = "above"` orders it directly above, entirely outside the window frame. On a focus change the focused border is re-ordered once. With `above` the border is then kept on top by reacting to the window server's reorder notification for its window (live follow's private event, native-unverified): each one re-orders that border above its window once, coalesced per window per display frame and capped at 4 per window per second (a feedback-loop guard; further ones are dropped with a debug diagnostic); there is no timer re-order, because a timed re-order raced the application's own raise on a click and flickered. To shorten the gap between the window server's raise and that main-thread re-order, the live-follow owner thread first re-stacks the panel itself with a private `SkyLight` order call (`SLSOrderWindow`, resolved at runtime, signature native-unverified) on Stache's own connection, as soon as it drains the notification: only for a border that is `above`, shown under a known and open Space gate and whose panel number is known, at most 4 per window per second, and never for a panel the main thread has ordered out or is ordering out (it never shows a hidden border); the main-thread re-order still follows. A missing symbol or a refused call turns this fast path off for the run with one log line, and the main-thread path alone applies. When live follow is unavailable (its private symbols are missing) a timer fallback applies: one more re-order about 80 ms (plus a display frame) after a focus change, and the same re-assert (one order now, one settle order) after a mouse up while a bordered window is focused and after the activation of the focused window's application without a focus change; events within one settle share a single settle order, and nothing repeats. `below` never reacts to reorder notifications. a recolor or width change never re-orders a visible border. Overlays are set to ignore mouse events and never become key or main (click-through is unverified natively), are excluded from screenshots and screen sharing (`sharingType = none`), and are never tracked by Tiling.
- **Animations.** A gradient state's `animation` has `style`, `duration` (ms; below 16 is 16) and `easing`. `style = "ping_pong"` (the default, so existing configurations keep their meaning) swaps the two colors back and forth, one `duration` per leg, on the focused window only; `once` turns the gradient angle 360 degrees once on each focus; `loop` turns it forever. `transition` (`duration` ms, 0 or omitted is instant, `easing`) cross-fades a border's colors when its state changes (focus in or out). With `unfocused = false` and a `transition`, a focus change instead grows the new window's border from width 0 to its width and shrinks the old one back to 0 before it hides (a glow's band fades in and out instead); an application hide, workspace switch, Mission Control or Space change still hides a shrinking border at once (native-unverified). Every animation runs on the render server: Stache schedules no timer or per-frame work for it.

  ```toml
  [borders]
  enabled = true
  order = "below"
  transition = { duration = 200, easing = "ease_out" }
  unfocused = false
  
  [borders.focused]
  width = 6
  gradient = { from = "#b4befe", to = "#cba6f7", angle = 45 }
  animation = { style = "loop", duration = 4000, easing = "linear" }
  
  [[borders.ignore]]
  app_id = "com.apple.systempreferences"
  ```

- **Blink-free ordering.** Before Tiling hides an application (workspace switch, ⌘H by Tiling), its borders are ordered out first; the effects thread waits at most a short bound for the main thread and never delays the hide further. A border appears only after its window was observed visible and one display frame has passed at the confirmed frame (the frame Tiling wrote, or for a window Tiling does not write, such as a floating one, the frame it reads), and it is re-ordered with its window on focus. An application hidden by someone else (⌘H, another tool) is hidden as soon as Tiling observes it, so its border can lag the hide by that observation.
- **Spaces and Mission Control.** Overlays are `transient` windows on their target's Space: Mission Control, App Exposé and Show Desktop never show them, and a border never appears on another Space. This structural guarantee is the cover that holds on macOS 26 (the resolved open question B of the [spec](../specs/2026-11-09-tiling-borders/05-spaces-mission-control.md)): the Dock's Exposé notifications registered but never fired in native runs, and the private Space-change event fires only about 1 ms before completion. Stache still hides every border on any Space, Mission Control, display-layout or fullscreen fact it receives and shows them again only after its gate is confirmed. A display-layout fact means the displays or their geometry (position, size, pixel size) changed: macOS also posts its screen-parameters notification many times a second while a display's HDR headroom follows brightness, and those are ignored (a change of scale alone, with the same geometry, is not detected); when a source is missing or a query fails the gate **fails closed** (borders stay hidden) and status names the cause. A window entering native fullscreen loses its border; after the exit Tiling re-reads the window, lays it out again and its border returns.
- **Following Tiling's writes.** A border moves with each frame its window **reached**: for an animation, on the acknowledgement of each written frame (a frame the application's AX thread replaced, latest wins, was never reached and moves nothing), then to the settled or read-back frame; for a direct write, when the write answers (the frame read back, else the target of an applied write), never at dispatch. Moves merge latest-wins into at most one pending main-thread job, so the border is at most one written frame behind its window, never ahead of it, and ends exactly on the target. While a Tiling write is in flight and has reported a frame, the window's observed frame (a coalesced read from the motion) does not move the border, and live window-server samples wait (Tiling's frames take precedence). A frame of a superseded plan acknowledged after the new plan started is dropped as stale, so a retarget can skip that one frame. Proven with fakes only; how closely the border tracks a real animated window on screen is **unverified natively**.
- **Live follow.** While a window is dragged or resized by the user, a dedicated owner thread (`stache-tiling-borders-events`) reads the window's bounds from window-server move/resize notifications (private SkyLight symbols resolved at start) at most once per display frame and moves the border without involving Tiling; Tiling's own writes always take precedence. **Fallback:** when the symbols are missing or registration is refused, status shows one `borders: live follow unavailable (<reason>); borders hide while a window moves` line and a border hides from the first external move until the gesture ends and the frame stayed quiet for 100 ms. Borders trail a fast drag by a few pixels.
- **Lifecycle.** Enabling borders starts the Spaces owner (`stache-tiling-borders-spaces`) and the live-follow owner; overlays are created lazily on the main thread (at most 64, with a bounded reuse pool). Disabling borders, a stop, pause or reload stops both owners, releases every overlay on the main thread and compares the acknowledged count with the engine's ledger; a stop waits at most 500 ms (off the main thread) for that acknowledgement. A runtime stop with something missing is owed as `borders overlays` and quarantined until a later stop retries it; at process exit a missing acknowledgement is only a note (the window server removes an exiting process's windows). In unwinding (debug and test) builds a panic in the border engine turns borders off for the run and Tiling keeps running; a release build aborts ([Release panics](../architecture/sdk.md#release-panics)).
- **Diagnostics.** Border problems are status `diagnostics` only; Tiling's health is unaffected: `borders: main thread busy` (a batch unacknowledged for 250 ms; later batches merge), the Spaces gate's fail-closed cause, live follow unavailable, the corner-radius fallback, a release count mismatch, an owner that did not stop, the engine panic, and `borders: enabled, but this host composed no border overlays; nothing is drawn` for a host without the overlay control.
- **Verified natively and not.** Native runs on one display (macOS 26) confirmed: borders around focused and unfocused windows, below placement and the 5/6 width, gradient directions 0, 45, 90 and 270, no blink on workspace switches and ⌘H/Cmd-Tab, live drag follow, borders absent in Mission Control, Exposé, Show Desktop and Space switches (by direct observation, no frame recording), borders returning after fullscreen exit, absence from screenshots, and clean teardown on quit. **Unverified natively:** the configured animations (`ping_pong`, `once`, `loop`) and `transition`, the rendered glow band (its look, extent and strength), `order = "above"` and its +2 pt radius, click-through, the CPU/wakeup/memory budget and repeated enable/disable cycles, two displays, forced-unavailable sources, and the private event ids and signatures recorded in the spec.
- **Limits.** Round borders use each window's real corner radius through a private `SkyLight` window query (looked up lazily, when an overlay first asks for a radius); it is **native-unverified** and falls back to 16 pt when the symbols are missing or the answer is implausible. An application unhidden without a later `Shown` observation keeps its borders hidden; there is no timeout. Each `HideApp` may wait up to 32 ms for its border hide, sequentially per application. A window the active-Space check could not confirm one frame after its reveal stays hidden until its next confirming event (a settled or read-back frame, a completed reveal write, or its application shown again), which retries the check once; nothing polls.
- **Sources.** The approach (not the code) was studied from JankyBorders (`src/border.c`, `src/events.c`, `src/windows.c`, `src/animation.c`, `src/misc/drawing.h`, `src/misc/window.h`) and Hyprland's `border`/`borderangle` animations, as inspiration only. Source comments refer to it as "the reference border tool".

## Optional features not supported yet

Every optional feature in the configuration now has a runtime, so no requested feature is listed as unsupported. Tabs: see [Native tabs](#native-tabs). `preset_on_open` stays inert.

**Configuration:** `tiling.toml` is a registered catalog document (`TilingConfig`, schema, template, `config migrate` validation) that keeps every legacy shape and default. See [config.md](../architecture/config.md).

**Pure library:** the `stache-tiling` crate also holds pure, deterministic layout, rule, preset and minimum-size code: usable-area math (full logical bounds, native visible-frame insets and generic host reservation insets, per-edge `max` then the display's own outer gap once; top 24 native / 40 reserved / 6 gap gives 46), the eight layout algorithms, gap resolution, rule matching with the `app_id` fallback fixed, the Grid ten-tile cap with `GridOverflow` identities and stable promotion, the one-shot floating `default_position` policy, preset frame math and bounded minimum-size redistribution. Every input window is accounted for in a typed `LayoutPlan`; infeasible geometry is an explicit outcome, never a NaN frame. `preset_on_open` stays inert. See [testing](../guides/testing.md).

**Native adapters:** `stache-macos` holds neutral AX queries/writes, an `AxObserver` wrapper, a `windows` ownership adapter (a router over per-application Tiling AX shard threads, exact window tokens, a gated frame write and `AXRaise`, chunked enumeration, quarantined cleanup), application hide/unhide and lifecycle, and display adapters; `stache-tiling` has a `WindowBackend` seam with a fake. Capability limits: native behavior is **unverified** (no real AX run), AX has no atomic frame write (separate position and size calls, see the write order above; partial results are reported), `CGWindowID` depends on a private symbol that may be absent, native tabs follow the shared tab bar and are Finder-probed only, a timeout after a send is `Uncertain`, and raising does not activate an application. Every application has its own AX thread (up to 32; further applications share one overflow thread, which the instant fallback names when it cannot keep up). The enabled Tiling module starts them. See [architecture](../architecture/overview.md) and [testing](../guides/testing.md).

**Lifecycle:** `stache-tiling` has a `Module` implementation and the `stache-app` `TilingFactory`, registered default disabled in the production composition. They give Tiling a staged start with exact rollback, observed-revision reconfigure and a sealed, quarantined stop. See [architecture](../architecture/sdk.md).

**Tracking actor:** `stache-tiling` also holds a single-writer actor (`state/`, `actor/`, `events/`, `tracking.rs`) that follows windows and issues every window effect through gated effects. Pure transitions `(state, input) -> (state', effects)` own screens, workspaces, windows, focus, stable layout order, focus history and the runtime-owned visibility ledger; its effects are read requests (`track`, `refresh`, snapshot reads, `untrack`, an application list), gated frame writes, application visibility requests and publication. Inputs are epoch- and registry-tagged: backend window events, application lifecycle, display layouts, accepted configuration and effect completions; a late completion or event from an old registry or epoch is dropped and counted. A semantic queue (1024) keeps create/destroy/focus/lifecycle/topology/config in order; moved/resized samples are coalesced latest-per-exact-token per display and flushed at the display refresh rate (unknown, `NaN`, infinite, zero or negative rates use 60 Hz; any other rate is clamped to 30-360 Hz), with destroy and membership changes invalidating or flushing older samples for that token and hotplug retiming remapping pending samples by token. A full queue, a dropped backend event, a sequence gap or an observer overflow never silently loses a destroy or focus: the affected application (or everything) becomes unconfirmed, its windows are not written, and one bounded refresh per application repairs it. A refresh re-lists the application: the owner reports every listed window again (same tokens, fresh facts) and, only when the listing completed untruncated and without error, destroys tracked windows absent from it (releasing their observer registrations, or keeping a failed removal for cleanup); a truncated, cancelled or failed listing destroys nothing, and Tiling's scan repair runs only after an untruncated completion. This is fake-proven; real AX listing and destroy semantics are unverified; a permanently overloaded stream stays bounded and reports `overloaded`. Startup installs observers (`track`) before chunked asynchronous enumeration, closes create/destroy-while-scanning races with a sequence floor and destroy tombstones, and publishes a phase (initializing, reconciling, complete, incomplete; `incomplete` only for a global fault, see [Diagnosing a quiet desktop](#diagnosing-a-quiet-desktop)) with desired state (workspace and order) separate from observed state (title, frame, fullscreen, minimized, hidden, tabs). A window observed in native fullscreen is out of the layout. Native fullscreen always enters or leaves a Space, and nothing else reliably reports its end (`AXFullScreen` can flip after the last window notification, and an application such as Ghostty drops the window from `AXWindows` and lists it again without any notification), so on each active Space change (`NSWorkspaceActiveSpaceDidChangeNotification`, observed with the application lifecycle) the actor re-reads every window observed fullscreen and lists again every application holding a window that left `AXWindows` with nothing taking its slot (never for an inactive native tab, whose slot another member holds); activating such an application lists it again too, in case a Space change was missed. The window can rejoin `AXWindows` only after the Space change completed, so the application is listed again after the tab settle delay until the window returns (at most 20 times). A window still missing when such a series runs out, and not observed fullscreen, is taken to be on another macOS Space: later activations list its application once each, never a new series, while each later Space change starts a full bounded series again (the window may rejoin `AXWindows` only after the change); a fresh suspension of the window starts over. The returned window takes its slot back and is laid out again (when its slot had been released, the frontmost application's real focused window is read again, since no activation follows); when the listing that finds it still reads it fullscreen, the application is listed again after the tab settle delay until it reads windowed (at most 20 times, about 3 s). Otherwise nothing polls while a window is fullscreen. Queries read one immutable `Arc` snapshot. Disconnects and (unwind builds only) a caught panic become health facts; after a panic the last published snapshot stays and a restart is required. Window effects (frame writes, application hide/unhide, activation and raise) are issued only through the gated, sealed paths described above; the `tiling` socket methods and CLI only submit typed intents to this actor. New windows go to the first workspace whose rules match, else the focused workspace (legacy); non-Grid layouts insert after the focused window, Grid appends. Ignore rules, system components, Picture-in-Picture windows and Stache itself are never managed, identically at startup and on events. See [testing](../guides/testing.md).

The [draft overview](../specs/2026-11-03-tiling/00-overview.md) divides implementation into nine separately approved parts. Parts 01–09 are implemented; 01–04 ran in parallel with [Bar foundation](../specs/2026-11-08-bar-foundation/00-overview.md), which has since merged, and parts 05–09 build on its published-state channel and screen reservations (part 05 consumes the reservations). The workspace strip is part 10 in the [Tiling–Bar integration](../specs/2026-11-08-tiling-bar/00-overview.md) spec; it ran last, after Bar 03–08, which have merged, and is implemented; live clicks/focus remain unverified. Main's noTunes applications identity, catalog migration hook, accepted-config watch, shared input, SDK published-state channel and host screen reservations ship; Tiling consumes the host screen reservations and publishes `tilingState` v1 to the channel ([Published state](#what-works-when-enabled)); the Bar projection, the `bar_tiling_action` click command and the strip UI ship.

Grid alone tiles at most ten eligible windows and leaves tracked extras floating without automatic centering; new ordinary floating windows honor the advertised `default_position` once.

Minimum sizes follow the legacy rules: a reported `AXMinimumSize` wins, otherwise a minimum is inferred when a window reads back larger than its planned size, and the next plan redistributes ratios around it for Split, Dwindle and Master. Intentional deviation from legacy: Grid cells stay fixed (an inferred minimum never reshapes the grid); a window that refuses its cell overflows it and is not re-written. A direct or final frame write that moves and resizes a window is written size, position, size, as legacy did (if the first size step times out, the application is taken to be hung and the position and second size steps are skipped; a failed second size step after an accepted first one reports the size as written, for the readback to decide, unless it failed for missing permission, a timeout or a gone element, which is reported as the failure); the first and intermediate frames of an animation are written position then size. A readback after such a write, or after an animation, can show a transient size, so it teaches nothing by itself: at most one direct (never animated) size-only re-write of the same target is sent, and only a size the window still refuses then is learned; the window is then left alone until its target changes. A native fullscreen frame never teaches a minimum. A window that took its size and later grows past it on its own (outside a gesture) is re-asserting its minimum: that is learned too and the window is not written back to the rejected size. Such growth teaches nothing while the passive drag observer is unavailable (a user resize would be invisible; this is known only when the observer cannot be installed at start, since the observer reports no permanent loss later, only transient discontinuities), and nothing at or above the usable area of the window's display in either dimension (a zoom or maximize is not a minimum). A write that was provably never sent (for example `NotIssued` after a reload changed the revision) is retried under the new plan even when a learned minimum exceeds the cell. Inferences stay bounded per window until `balance` or a user relayout.

The workspace/app strip UI is the Bar's Spaces widget (see [Bar](bar.md#tiling-strip-ui)); the published strip data in `BarView.tiling` is unchanged. Data uses optional typed published state; reserved screen area comes from the host registry, not Bar configuration or circular module dependencies. Borders are drawn by Stache itself (see [Borders](#borders)). All live native effects/tests need per-run approval; none ran.

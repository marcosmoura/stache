# Tiling (core and virtual workspaces; default disabled)

Read when using or changing the Tiling module. Tiling is a **default-disabled module**: set `enabled: true` in `tiling.jsonc` and grant Accessibility to start it. It ships the core runtime, virtual workspaces and the `stache tiling` CLI with its socket methods ([CLI](#cli)). Tabs and passive drag (part 08) ship fake-proven and native-unverified; opt-in animation (part 08) ships the same way; opt-in borders over an external JankyBorders service (part 09) ship the same way; the Bar workspace strip (part 10) is **planned, not shipped**. Native behavior is fake-proven; real AX, hide/unhide, activation and display behavior is **unverified** until a per-run approved live check.

## What works when enabled

- **Windows and workspaces.** The runtime follows windows through an AX owner thread and arranges them in virtual workspaces (not macOS Spaces): one visible workspace per display, one global focused workspace with focus history, stable window order, and eight layouts (`dwindle`, `split`, `split-vertical`, `split-horizontal`, `monocle`, `master`, `grid`, `floating`). An empty config creates one default workspace per display; configured workspaces match `main`, `primary`, `secondary` or a display name, fall back to main when their display is missing and return when it returns. New windows go to the first workspace whose rules match, else the focused workspace on their display. Ignore rules, system components, Picture-in-Picture windows and Stache itself are never managed. Grid tiles at most ten windows and leaves extras floating. Structural config reloads keep compatible workspace state (see the workspace rules in [config.md](../architecture/config.md)); a rejected candidate changes nothing.
- **Placement.** Frames come from the display's visible frame, the host's screen-reservation insets (for example the Bar) and the configured gaps, written position then size and accepted only after a readback. A refusing or unresizable application yields a partial or uncertain outcome, never a guaranteed geometry. The status counts windows whose latest placement is partial, uncertain or refused.
- **Application-level hide and unhide.** Inactive-workspace windows are hidden by hiding their application, which cannot isolate windows of one application across workspaces: a visible workspace that needs the application wins, other windows of it stay visible and the status counts the partial-isolation conflict. Only exact applications the runtime itself hid are tracked as owned; prehidden or externally hidden applications are never owned. Stop and disable restore only still-alive, runtime-owned exact instances. An unhide that fails stays owed and quarantines the stop for retry; a hide whose attribution is ambiguous (a show was observed while our hide may have landed) is retained, reported in `ambiguousVisibility` as `Name (bundle id, pid N): reason` (display-only facts with fallbacks when unknown; the opaque id is never shown) and never unhidden automatically, because recovery needs explicit approval. Ambiguous records survive stop and start (they are merged by exact application within a run and by live process across runs, because application ids are run-scoped; the process id only keeps or drops a diagnostic record and never authorizes an action; they are never forgotten and never seeded into a new ledger as owned) and stay in `ambiguousVisibility` while Tiling runs; one is dropped only when its process is proven gone at a later start or stop. During a restore, a public `unhide` that the system accepted counts as cleared, since that path has no confirming readback; the `AXHidden` fallback counts only with a confirming readback, otherwise the unhide stays owed with its reason.
- **Focus.** Focus intents (issued by `stache tiling window --focus` and `workspace --focus`) unhide an owned-hidden application before activating it through the one exact activation path and raising the window.
- **Reservations and displays.** The module consumes the host's screen reservations from its first write and observes native displays itself (a main-thread observer that only enqueues a hint, a worker that queries the layout, the initial layout delivered before the first frame). Tiling never applies a screen topology to the host registry; Bar owns that.
- **No persistence.** Workspace state lives in memory only; a fully stopped and restarted runtime starts from the config, with no cross-restart recovery.
- **Lifecycle.** Disabling, pausing or losing Accessibility stops Tiling and leaves other modules running. A stop that cannot finish is quarantined with the owed stages visible in the status (`owed`), is never force-cleared, and a restart retries only those stages.
- **Status.** `ModuleStatusView.tiling` carries the lifecycle state (`inactive`, `running`, `stopping`, `quarantined`), the adopted config revision, plan sequence, health, owed stages, `diagnostics`, `ambiguousVisibility`, `partialOutcomes` and `visibilityConflicts`. Missing Accessibility is the registry's `waitingForPermission`; an unhealthy actor shows `unavailable`.

## CLI

`stache tiling` talks to a **running** Stache host over the control socket; it
never starts the desktop, the Accessibility owner or the module. The host must use
the same configuration directory (`-c/--config DIR` stays a directory, before or
after any subcommand); a different directory is refused before any request.
Enable the module (`enabled: true`) and grant Accessibility first.

```sh
stache tiling pause                       # waits for the stop acknowledgement
stache tiling resume
stache tiling query screens               # tables; add -j/--json for the whole array
stache tiling query workspaces --focused-screen
stache tiling query -d windows --workspace coding
stache tiling query apps --json
stache tiling window --focus left --resize width 100 --resize height -50
stache tiling window --focus 1234         # a numeric window id (shown by `query windows`)
stache tiling window --swap next --toggle-floating --send-to-workspace web
stache tiling workspace --focus web --layout grid --balance --send-to-screen main
```

- **Queries** (`screens`, `workspaces`, `windows`, `apps`) read one snapshot in
  actor order. `query` alone prints its help. `--screen` accepts `main`,
  `primary`, `secondary` or an exact name; `--workspace` is an exact name; the
  focused filters conflict with explicit ones as the help states (conflicts exit
  2). Tables use the legacy rounded layout, `✓`/`✗`, `WxH @ x, y` frames,
  `(no title)` for empty titles and truncation by character count with `…`;
  titles and names print control characters as visible escapes. `--json` prints
  the whole pretty array in a frozen key order (`id, name, ...` as documented in
  [ipc.md](../architecture/ipc.md#tiling-methods)); `-d` adds window columns
  and never changes JSON or apps. Colors appear only on a terminal.
- **Actions** run in a fixed order whatever the flag order: window focus, swap,
  toggle-floating, preset, each `--resize` pair as supplied, send-to-screen,
  send-to-workspace; workspace focus, layout, balance, send-to-screen. The first
  reported failure stops the rest; actions already admitted are **not rolled
  back**. A resize dimension/amount is validated when its pair executes, so
  earlier actions may already have run. `--preset` applies only in a Floating
  workspace and is a silent admitted no-op elsewhere. Swap and `--layout` accept
  only the exact lowercase values; focus accepts directions case-insensitively
  (`prev` aliases `previous`) or a numeric window id (an unknown id is
  `Window {id} not found`; an id is resolved once and never re-targeted).
- **Exit 0 means admission, not native success.** A mutation the actor admitted
  (`enqueued`) or whose scope is confirmed (`applied`) is silent with exit 0; it
  does not prove that a window moved, and later native results only show up in the
  status and queries. A `partial` or `uncertain` outcome prints `Tiling operation
  partially applied.` / `Tiling operation outcome is uncertain; it may already have
  taken effect.` on stderr with exit 1 and is never retried. `pause` succeeds only
  after the stop is acknowledged. A `pause` or `resume` that arrives while another one is still in flight is not started and reports the same uncertain error.
- **Errors.** Parse errors (unknown flag, bad arity, invalid swap/layout value or a
  flag conflict) exit 2. Semantic and action failures exit 1 on stderr as `stache:
  IPC error: {body}` (for example `Tiling is disabled`, `Tiling is paused`, `Tiling
  cleanup is pending`, `Tiling is not initialized`, `Workspace not found`, `No
  focused window`); the empty-request and resize validation bodies keep the legacy
  `stache: {body}` form. With the host absent, mutations fail with `stache: IPC
  error: Stache app is not running`. Queries print their failure on **stdout** and
  exit 1: `Stache app is not running.` (table) or `{"error":"..."}` (JSON, safely
  escaped) when offline and `Error: {body}` otherwise.
- **Intentional differences from the legacy CLI:** a failed query exits 1 (legacy
  exited 0); a failure JSON is serde-escaped (never interpolated); `partial` and
  `uncertain` are explicit non-zero results; a numeric `--focus` works (legacy
  advertised but rejected it); titles cannot inject terminal escapes. Successful
  commands, flags, JSON and tables are otherwise unchanged. Native effects are
  fake-proven only; real AX behavior stays unverified.

## Native tabs

A runtime-owned, pure tab group registry (`stache-tiling` `tabs.rs`, held in the actor state; no process-global and no `CGWindowID`-only cache) tracks native tab groups. A snapshot of a window with a tab strip carries each member's `CGWindowID` and selected flag (`stache_macos::windows::TabMember`, read from `AXTabGroup`/`AXTabs`/`AXValue`, bounded to 32 members and 0.5 s per element). The group is keyed by the exact reporter window token, scoped to its application, replaced atomically by the reporter's next snapshot (a newer reporter naming the same ids replaces the stale one), and members are matched to tracked windows of the same application only at query time, so a reused id never matches a stale member.

- **One tile per group.** The selected member is the only tile; unselected members are tracked (`WindowState.inactive_tab`, still in the stable order) but never tiles.
- **No relayout for tab-only changes.** Layout is a function of the windows and their flags, so creating or destroying an inactive member changes no tile and produces no new plan or frame write. Switching the selected tab flips two flags: the newly selected window takes the previous one's order slot (same workspace) and therefore its frame, and only that window is written.
- **Reconcile.** The initial scan is the application's first complete enumeration (once per application, counted in `tabs.stats.initial_scans`); a focus or main-window change of a tracked window re-reads that one window while reads are on (never a whole-application refresh).
- **Never exclude on doubt.** A strip with no or several selected members, a selected member that is not a tracked window of the application, or an unselected member whose flag or id is unknown excludes nothing. A failed read drops the reporter's group and is reported as unavailable; a destroyed reporter drops its group (its members become tiles); a destroyed window's id is removed from the groups of its application.
- **Status.** With reads off the status lists `native tabs are not read ...`; with reads on and failing reads it lists `native tab information is unavailable for N application(s)`. Ordinary windows are always tiled.

**Production keeps tab reads off** (`AdapterOptions.read_tabs` false in `TilingFactory::production`): the read path, registry and policy are fake-proven only. No real `AXTabs` tree, the private `_AXUIElementGetWindow` on tab elements, or the selected-tab `AXValue` has been verified, and a wrong match could hide an ordinary window, so reads stay off until a per-run approved native check. No tab suppression is claimed. Missing evidence: how macOS reports inactive tab windows in `AXWindows`, and whether tab elements yield window ids.

## Passive drag

Dragging or resizing a tiled window with the mouse is observed, never intercepted. Drag has **no configuration flag** (legacy had none): it runs whenever Tiling runs and the shared input service can install its listen-only tap.

- **Observation.** `drag.rs` subscribes one `InputObserver` (left and right button, down and up, with the event location) through `ModuleContext::input()` as start stage 9, after the authority is published. It uses only the service's **listen-only** tap, which always passes: Tiling cannot suppress, intercept or inject an event or change HQ > MA > KB priority, and a press that an interception consumer suppressed is still seen. The tap exists only while a passive subscriber does and closes with the last one; stop removes the observer first (`Teardown::Drag`). The callback only builds a pure `DragSignal` and calls `Ingress::submit`; it reads no window and runs no AX. Moved and dragged events are not observed. Input Monitoring is not a typed permission, and Tiling's permission requirement is unchanged (Accessibility, user-only).
- **Degraded, not failed.** If the service is not attached or the tap cannot be installed, Tiling still runs healthy and `status.diagnostics` says `drag is unavailable ...` (naming Input Monitoring when the install failed). Only drag is off.
- **Bounded lane.** Signals go through a 32-entry drag lane. A full lane drops the new signal, discards what was queued and delivers one `Lost(Overflow)`; nothing is replayed.
- **Gesture.** A down captures the focused workspace's tiled, non-floating windows (exact tokens, stable order, frames) off the callback. While the gesture lasts the planner writes nothing, so the user is not fought and no external-change attempt is spent. A write of ours that completes meanwhile moves that window's baseline to its readback, so a layout echo is never mistaken for the user. The up of the last held button asks for one fresh read per captured window (on the effect worker) and then commits. A gesture older than 60 s, or any lost observation (overflow, a listen-only discontinuity, an input epoch that differs between down and up, Accessibility loss, stop, a down of an already held button) cancels it, reconciles the affected applications once and never invents an up or replays a click.
- **Commit** revalidates the registry, workspace, layout, configuration revision and the exact tile list (stale: no swap, no ratio, plain replan). Then, in order: **resize** when a window's width plus height changed by more than 5 points (legacy `find_resized_window`), mapped onto the workspace ratios as legacy `on_user_resize_completed` (usable area instead of the screen's visible frame, one ratio per layout; Monocle and Floating only replan); else **swap** when the window with the greatest centre travel strictly above 50 points (exactly 50 is not a drag) has its centre inside the first original frame, in stable order and inclusive of the edges, of another tile; else one **snap-back** plan for windows that left their planned frame. Floating windows are never captured, targeted or pulled back.
- **Limits.** The captured workspace is the focused one, so the first press on another display only focuses it. A second down while the first up is still being read cancels that gesture. An already queued read of a window may satisfy its slot before the final one. A busy subscriber snapshot in the input service drops an event silently (counted there as contention); the epoch check catches only disables. All of this is **native-unverified**: no real tap, mouse event or window was involved.

## Animation

Off by default (`animations.enabled: false`, `duration: 200`, `easing: ease-out`). When enabled, a frame plan that moves a window by at least 5 points is written as a sequence of eased frames instead of one jump. The curves are the legacy ones (`linear`, `ease-in`, `ease-out`, `ease-in-out`, `ease-out-expo` and a damped spring). The configured duration is clamped to 100–1000 ms and applies from 500 points of travel; shorter moves scale it by the square root of the distance down to 50 ms at 20 points or less. A spring never passes its target (progress is clamped) and ends at the exact target. The duration is scaled **per window** from that window's own travel (legacy scaled it once per batch), so windows moved by one relayout can finish at different times.

- **One owned worker.** The worker thread exists only while `animations.enabled` is true; a disabled Tiling (and a default configuration) owns no animation thread, timer or allocation. A configuration reload that enables or disables animation starts or retires the worker live through the same accepted-revision path; a duration or easing change keeps the worker. It is never a global or immortal worker.
- **Latest plan only.** The worker has a bounded mailbox (16 windows). Per window the newest plan replaces an older pending one, and a plan that arrives while a window is moving retargets from the **confirmed** position (the last readback of the interrupted animation), not from the planner's stale belief or the old destination. A replaced or interrupted plan is acknowledged as a typed "not sent" for its own plan sequence only, so an A, B, A history can never mark the successor applied. The cap counts every window the worker holds (pending, running or settling): a window beyond it, or any window when the worker is unavailable, is refused by the worker and the caller writes its exact target directly, so no window is ever dropped. A newer plan for a window the worker already holds is always accepted. Should a job still reach a full stepper it receives one direct final write, never a silent no-send.
- **Pacing.** Frames follow the target display's refresh rate with the same rule as geometry coalescing (unknown or invalid is 60 Hz, otherwise clamped to 30–360 Hz). Sleeps wake on a new plan, cancellation or stop; no lock is held across a sleep or a native write.
- **Every frame is gated.** Each intermediate and the final write is the existing gated frame write: generation, accepted revision, exact window token, plan sequence, the plan deadline and the seal are re-checked at the native send. There is no second write path.
- **Outcomes.** The final frame is the exact target and its readback decides `applied`, `partial` or `failed`. A refused, partial, uncertain, unresizable (the readback does not follow the asked size), stale, expired or unauthorized frame stops animating that window at once: there is no final snap and no retry loop (a minimum-size inference still happens from the final outcome as for direct writes).
- **Echo suppression.** While a window is animated its attempt stays in flight, so its own move echoes plan nothing, and a window in motion is never assumed to have arrived (an A, B, A plan writes it again). After the final write the window gets a 50 ms settle, one bounded readback is taken and reported, and at most two later reads that still show a position from the motion are ignored (counted in the diagnostics).
- **Drag.** No animation starts while a drag gesture is active (plans write nothing), and a gesture start cancels a running animation. The snap-back plan after a drag may animate.
- **Stop.** Stop seals the authority first. The order is sealed, drag observer removed, frame writes drained, **animation worker closed and joined**, restore of runtime-hidden applications, watcher, display observer, backend epoch, actor, effect worker. A worker stuck in a native send leaves `frame drain` and `animation worker` owed (and the restore waiting), the module quarantined and a restart refused until a later stop retries exactly those stages. No frame is written after the seal.
- **Planned, not shipped.** A faster pipeline (per-application AX threads, latest-frame mailboxes, display pacing, position-only frames, an Enhanced UI lease and an instant fallback for slow applications) is drafted in the [animation pipeline spec](../specs/2026-11-09-tiling-animation/00-overview.md).
- **Unverified natively.** Everything above is proven with fakes (fake clock and writer for the stepper, the fake window backend for the integrated runs). Real AX write latency, achieved frame rates, visual smoothness, overshoot-free spring behavior on real applications and the smoothness of resizes are **unverified** until a per-run approved live check. AX has no atomic frame write, so a moving window can flicker between its position and size halves.

## Borders

Off by default (`borders.enabled: false`). Borders are drawn by the **external JankyBorders service** (`git.felix.borders`); Stache only tells it what to draw. Nothing is looked up, sent, spawned or allocated while borders are disabled.

- **Planned, not shipped.** Tiling-owned native borders that replace JankyBorders (same configuration, blink-free hide/show ordering, live drag follow) are drafted in the [native borders spec](../specs/2026-11-09-tiling-borders/00-overview.md).

- **Consent.** Setting `borders.enabled: true` is the explicit opt-in. It lets Stache **overwrite the shared JankyBorders settings** `width`, `style`, `hidpi`, `active_color`, `inactive_color` and `blacklist`. Their previous values are **not read and not restored**; if you also run JankyBorders yourself, Stache's values replace yours. There is no other setting for this: the schema description of `enabled` says the same.
- **Never launched, left on stop.** Stache never starts, restarts or kills a borders service. Every attempt first looks `git.felix.borders` up. If it is absent, status `diagnostics` say so (`borders: the JankyBorders service git.felix.borders is not running ...`), **nothing is sent and no CLI is run**; the module stays `running` and healthy and only borders are degraded. Start the service yourself; the next focus or configuration change sends again. Stop, pause, disabling Tiling and reloading to `borders.enabled: false` cancel Stache's own animation and release its connection but send **no** command (no `width=0`, no transparent pause): JankyBorders **keeps the last settings Stache sent**, and the stopped status says so.
- **What is sent.** One base batch (`width`, `style` `r|s`, `hidpi` `on|off`, `active_color`, `inactive_color`, `blacklist`) when borders start or the borders configuration changes, then `width`, `active_color`, `inactive_color` when the focused window's state changes. Colors are `0xAARRGGBB`; a gradient is `gradient(top_right=..,bottom_left=..)` for normalized angles in `[0,90)` and `[180,270)` and `gradient(top_left=..,bottom_right=..)` otherwise; glow is `glow(0x..)`; a disabled state is transparent with width 0. `rgb()`/`rgba()` colors, which the config validates, are honored. This is an **intentional correction** of legacy, which turned them transparent. The active state is `floating` for a floating layout or window while it is enabled, else the layout's override when present and enabled, else `focused`. The blacklist is the system skip bundle ids and names, the tiling `ignore` rules and the `borders.ignore` rules. The runtime reads the focus, workspace layout and floating flag from the actor's published snapshot as plain values; no AX call is made for borders.
- **Delivery.** One owned runner thread (spawned only while enabled) creates, uses and drops the Mach connection and owns the helper CLI executor. Only the **newest** pending update is kept. A send over Mach has a 0.5 s deadline. Only a send **proven not enqueued by message validation** (for example too large or invalid data) is retried once over the `borders` CLI, and only after the lookup of the same attempt succeeded and a fresh lookup just before the CLI still finds the service (otherwise it is a missing service and no CLI runs); the CLI child lives at most 2 s, gets another 2 s for cancel and reap, and its output is capped at 64 KiB. A dead destination (`MACH_SEND_INVALID_DEST`/`INVALID_RIGHT`) is a missing service: it is diagnosed, the right is released and the CLI is never run, since running it could start the service. A timeout or any ambiguous Mach result is never retried or sent over the CLI. A failed send is not remembered as delivered; the next **new** update (or an explicit retry) sends again, and there are no autonomous retry loops. The service can still exit between that last lookup and the CLI invocation; this narrower race is documented, not prevented.
- **Animation.** A gradient state with `animation` ping-pongs its colors at no more than **8 frames per second** (`JankyBorders` has a FIFO Mach queue), Mach only, with cancellation-wakeable waits. Every new update bumps a monotonic epoch, so a frame belonging to a superseded focus is never sent after the newer base command; frames come from the same single sender, so they cannot be reordered behind it. A failed frame stops the animation until the next update.
- **Diagnostics.** Status `diagnostics` carry a typed delivery problem: missing service, no authority (a host that composed none), timeout, protocol (kernel or CLI rejection, unsafe arguments, unexpected exit), cleanup (a runner or helper child that could not be released) or a runner that could not start. These degrade borders only; layout, commands and other modules keep running.
- **Stop.** The borders runner is closed right after the drag observer and before the frame drain. A runner blocked in a send leaves `borders runner` owed (join bounded by 0.5 s send, 2 s CLI and 2 s reap), the module quarantined and a restart refused until a later stop retries exactly that stage; a helper child that cannot be reaped is retained, never detached. Enabling borders again while a previous runner has not ended reports a cleanup diagnostic instead of starting a second runner.
- **Unverified.** Everything above is proven with fakes. Compatibility with any real JankyBorders version or protocol, the real Mach lookup and send, and the real CLI are **unverified** until a per-run approved manual check records the binary and version, service identity, expected argv and the acknowledgement limits. A `Sent` result means the kernel queued the message, not that JankyBorders applied it.

## Optional features not supported yet

Every optional feature in the configuration now has a runtime, so no requested feature is listed as unsupported. Tabs: see [Native tabs](#native-tabs). `preset-on-open` stays inert.

**Configuration:** `tiling.jsonc` is a registered catalog document (`TilingConfig`, schema, template, `config migrate` validation) that keeps every legacy shape and default. See [config.md](../architecture/config.md).

**Pure library:** the `stache-tiling` crate also holds pure, deterministic layout, rule, preset and minimum-size code: usable-area math (full logical bounds, native visible-frame insets and generic host reservation insets, per-edge `max` then the display's own outer gap once; top 24 native / 40 reserved / 6 gap gives 46), the eight layout algorithms, gap resolution, rule matching with the `appId` fallback fixed, the Grid ten-tile cap with `GridOverflow` identities and stable promotion, the one-shot floating `defaultPosition` policy, preset frame math and bounded minimum-size redistribution. Every input window is accounted for in a typed `LayoutPlan`; infeasible geometry is an explicit outcome, never a NaN frame. `preset-on-open` stays inert. See [testing](../guides/testing.md).

**Native adapters:** `stache-macos` holds neutral AX queries/writes, an `AxObserver` wrapper, a `windows` ownership adapter (a dedicated Tiling AX owner thread, exact window tokens, a gated frame write and `AXRaise`, chunked enumeration, quarantined cleanup), application hide/unhide and lifecycle, and display adapters; `stache-tiling` has a `WindowBackend` seam with a fake. Capability limits: native behavior is **unverified** (no real AX run), AX has no atomic frame write (position then size, partial results are reported), `CGWindowID` depends on a private symbol that may be absent, tabs are not claimed supported, a timeout after a send is `Uncertain`, and raising does not activate an application. The enabled Tiling module starts them. See [architecture](../architecture/overview.md) and [testing](../guides/testing.md).

**Lifecycle:** `stache-tiling` has a `Module` implementation and the `stache-app` `TilingFactory`, registered default disabled in the production composition. They give Tiling a staged start with exact rollback, observed-revision reconfigure and a sealed, quarantined stop. See [architecture](../architecture/sdk.md).

**Tracking actor:** `stache-tiling` also holds a single-writer actor (`state/`, `actor/`, `events/`, `tracking.rs`) that follows windows and issues every window effect through gated effects. Pure transitions `(state, input) -> (state', effects)` own screens, workspaces, windows, focus, stable layout order, focus history and the runtime-owned visibility ledger; its effects are read requests (`track`, `refresh`, snapshot reads, `untrack`, an application list), gated frame writes, application visibility requests and publication. Inputs are epoch- and registry-tagged: backend window events, application lifecycle, display layouts, accepted configuration and effect completions; a late completion or event from an old registry or epoch is dropped and counted. A semantic queue (1024) keeps create/destroy/focus/lifecycle/topology/config in order; moved/resized samples are coalesced latest-per-exact-token per display and flushed at the display refresh rate (unknown, `NaN`, infinite, zero or negative rates use 60 Hz; any other rate is clamped to 30-360 Hz), with destroy and membership changes invalidating or flushing older samples for that token and hotplug retiming remapping pending samples by token. A full queue, a dropped backend event, a sequence gap or an observer overflow never silently loses a destroy or focus: the affected application (or everything) becomes unconfirmed, actions are not allowed, and one bounded refresh per application repairs it. A refresh re-lists the application: the owner reports every listed window again (same tokens, fresh facts) and, only when the listing completed untruncated and without error, destroys tracked windows absent from it (releasing their observer registrations, or keeping a failed removal for cleanup); a truncated, cancelled or failed listing destroys nothing, and Tiling's scan repair runs only after an untruncated completion. This is fake-proven; real AX listing and destroy semantics are unverified; a permanently overloaded stream stays bounded and reports `overloaded`. Startup installs observers (`track`) before chunked asynchronous enumeration, closes create/destroy-while-scanning races with a sequence floor and destroy tombstones, and publishes a phase (initializing, reconciling, complete, incomplete) with desired state (workspace and order) separate from observed state (title, frame, fullscreen, minimized, hidden, tabs). Queries read one immutable `Arc` snapshot. Disconnects and (unwind builds only) a caught panic become health facts; after a panic the last published snapshot stays and a restart is required. Window effects (frame writes, application hide/unhide, activation and raise) are issued only through the gated, sealed paths described above; the `tiling` socket methods and CLI only submit typed intents to this actor. New windows go to the first workspace whose rules match, else the focused workspace (legacy); non-Grid layouts insert after the focused window, Grid appends. Ignore rules, system components, Picture-in-Picture windows and Stache itself are never managed, identically at startup and on events. See [testing](../guides/testing.md).

The [draft overview](../specs/2026-11-03-tiling/00-overview.md) divides implementation into nine separately approved parts. Parts 01–07 are implemented; 01–04 ran in parallel with [Bar foundation](../specs/2026-11-08-bar-foundation/00-overview.md), which has since merged; `feat/tiling` is rebased onto it and parts 05–09 build on its published-state channel and screen reservations (part 05 consumes the reservations). The workspace strip is part 10 in the [Tiling–Bar integration](../specs/2026-11-08-tiling-bar/00-overview.md) spec, which runs last, after Bar 03–08. Main's noTunes applications identity, catalog migration hook, accepted-config watch, shared input, SDK published-state channel and host screen reservations ship; Tiling consumes the host screen reservations; it does not yet publish state to the channel (part 10).

Grid alone tiles at most ten eligible windows and leaves tracked extras floating without automatic centering; new ordinary floating windows honor the advertised `defaultPosition` once.

The final workspace/app strip will be visually identical to legacy in the approved Bar slot. Data uses optional typed published state; reserved screen area comes from the host registry, not Bar configuration or circular module dependencies. JankyBorders stays an optional external integration whose authority is the `borders.enabled` consent, with the non-restorability limits above. All live native effects/tests need per-run approval; none ran.

Lasting shipped behavior replaces only completed slices of this notice during implementation. Historical evidence remains in [legacy tiling docs](../../_legacy/docs/features/tiling.md); they do not describe current Next capabilities.

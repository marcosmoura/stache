# Hold-to-Quit

Read when changing or reviewing the Hold-to-Quit (`commandQuit`) module. It is a default-disabled module that swallows a Command-only `⌘Q`, shows a native progress HUD and asks the application that was frontmost at key-down to quit gracefully once the key has been held for `hold_duration`. **Verified by fakes, builds and clippy only: the real tap, HUD, display placement and graceful termination have not been exercised on a machine (see [Verification](#verification)).**

## Behavior

- **Config.** `commandQuit.toml` has `enabled` (default `false`), `hold_duration` in milliseconds (default `1500`, any value from `0` to `9223372036854775807`, the largest TOML integer) and `dismiss_delay` in milliseconds (default `1500`, same range; how long the HUD stays after an early release, `0` hides it at once), `position` (`"bottom"` default, `"top"`, `"left"`, `"right"` or `"center"`) and `animation` (`"fade"` default or `"slide"`); see [HUD placement and animation](#hud-placement-and-animation). No other key exists: no exclusion list, no force quit, no Settings screen. See [config](../architecture/config.md).
- **Controls.** Only the generic tray rows: config-backed Enable, session Pause/Resume, Retry for a failed start or stop, and the Accessibility permission request. The module declares `PermissionRequirement::shared_input(Accessibility)` while enabled, so startup, enable, reload, polling and activation only _check_; only the explicit tray request prompts. There is no CLI command, socket endpoint (not even read-only status) or window.
- **Hold.** A first, non-repeating physical keycode-12 down with exactly Command held is suppressed only when the runtime is accepting, the HUD is ready, and both frontmost gates agree: the module's own confirmed snapshot (not Finder, not Stache itself) and the shared input context (`Known`, no exemption bits, same bundle identifier). Otherwise `⌘Q` passes through untouched. A fresh HUD press identifier is minted for every physical press.
- **HUD.** The worker revalidates the exact captured instance on main (`preflight_frontmost`), asks for an optional display hint, then sends a non-waiting show. Only a matching `Shown` acknowledgement arms the hold; a pending show is expired by draining `HudEvents` in 10 ms slices bounded by the 2 s acknowledgement budget. The HUD hides on a quit request and every lifecycle change; an early release lingers (see [Release linger](#release-linger)).
- **HUD placement and animation.** `position` anchors the HUD inside the chosen display's visible frame, with the same margins and size limits as before: `bottom` and `top` are horizontally centered 48 pt from that edge, `left` and `right` are vertically centered 48 pt from that edge and `center` is centered both ways; the panel never leaves the visible frame, even on tiny frames. Every show fades the panel in over 200 ms (ease-out) and every hide fades it out over 150 ms (ease-in) with `NSAnimationContext` on the window's `animator()`; the AppKit window animation behavior stays `None`. `animation: "slide"` also moves the panel: it enters from outside the anchored edge by the panel size plus the 48 pt inset (bottom from below, top from above, left from the left, right from the right) and for `center` slides down from one panel height above (100% of the HUD height); a hide runs the same motion back. With Reduce Motion on, `slide` is a plain `fade` (cross-fades are the reduced-motion substitute); progress is unchanged. `Shown` is still acknowledged when the panel is ordered front, so the hold deadline and progress do not wait for the animation. The hide orders the panel out only in its completion handler and only while a per-panel generation token is current: a new show (or an order-out) in between wins, so a successor press is never hidden by a stale completion; the shown press is cleared when the hide starts, so a later freeze or hide for it is a no-op. A new press shown while the panel is still visible (for example during a release linger) does not blink: it keeps the current alpha and frame and animates to its final frame. Teardown (`release`) orders out at once with no animation. The Part 05 linger is unchanged: the frozen panel stays visible and still, and the animated hide runs when the linger ends. The worker reads `position` and `animation` per press, so a reload applies to the next press. Part 06 replaces the earlier "no decorative fade" rule of Part 02. The native animation is compile-checked and fake-modelled only (the fake hides immediately); the pure frame, layout and token logic is unit-tested (`hq_06_` tests).
- **Release linger.** When the user ends a press early (a tap, `⌘` or `Q` released before `hold_duration`, a Command release or added modifier, a frontmost activation, or a tap disable) the HUD stays visible for `dismiss_delay` so "Hold ⌘Q to quit `<App>`" can be read, then hides. The progress bar is frozen at the width it had on screen (`HudControl::freeze` computes the width from the recorded animation start, `from` and duration, sets it on the model and removes the animation); the panel is not hidden, moved or relabeled. The press itself is already cancelled and holds no authorization, so a lingering press can never quit anything. A new `⌘Q` press during the linger starts a fresh hold at once and the lingering press is hidden right after the new show is queued (a no-op when the new press is displayed, an order-out when its show was refused), so a refused successor never leaves a frozen panel behind. `dismiss_delay` `0` hides at once with no freeze, and an unrepresentable `now + dismiss_delay` lingers until the next press, stop, revision change or degrade, with no timer. The worker reads the armed value per press, so a reload applies to the next lingering end. Every other ending hides immediately: a successful quit, stop, a configuration revision change, accepting cleared, an application change detected by the worker, a HUD `Stale`/`Unavailable`/`Failed`, degraded mode and a newer press. A `Shown` that arrives after the release is frozen too, never tracked.
- **Show gate unchanged.** The HUD still refuses a press that is already cancelled when main runs the show, so a release that beats the show leaves nothing on screen and there is nothing to linger.
- **Quit.** At the checked deadline (`down + hold_duration`; an unrepresentable deadline is a cancellable indefinite wait; `0` proceeds only after `Shown`) the worker drains pending input once, so a release delivered at or before the deadline wins, then hides the HUD and calls `terminate_gracefully` exactly once on the captured instance. There is no `forceTerminate`, retry or retargeting: if the instance changed, was replaced or exited, nothing is sent. The outcome is reported truthfully: `Requested` is a request, not proof of exit; `Refused`, `NotRunning`, `Stale`, `Cancelled` and `Rejected` mean nothing was quit; `Uncertain` is never reported as `Refused`.
- **Cancellation.** Command release, an added Shift/Option/Control, a repeat whose flags no longer match (this is also the only way an added Fn is noticed: Fn is not a hold key, so it cancels only through a mismatching `Q` auto-repeat, never when repeat is off or the hold ends before the initial repeat delay), the key-up, a tap disable, a frontmost activation (including A→B→A), reconfigure, pause, stop and HUD failure cancel the press. The rest of that physical press (repeats and key-up) stays swallowed by the shared press ledger, even after the handler goes inert.
- **Reconfigure.** `reconfigure` ends with the only fallible step, `ApplicationObservation::accept`; a timeout rejects the candidate and leaves the old state. On success the press is cancelled and new presses pass until the worker sees the staged value published at a newer accepted revision, so an unpublished candidate never arms anything.
- **Idle.** An idle runtime has no timer, tick or poll: the worker parks until a claimed press, a configuration change or cancellation wakes it.
- **Degraded HUD.** If the HUD fails or becomes unavailable while running, the module stays `Running`, drops its input subscription (every press, and any Keybindings `⌘Q` binding, is restored), logs one warning and shows a `detail` on its status. Recovery is Pause then Resume, or disable then enable. There is no retry loop and no invisible interception. The detail is read at each host status publication, so it reaches the tray at the next publication (any command, a permission tick or an app activation), not instantly.
- **Start failure.** A failed prerequisite (frontmost lease, application observation, HUD install, policy acceptance, worker, input subscription) rolls back in reverse and is reported as `Failed(Start)`; the tray offers Retry. An unconfirmed frontmost does not fail start: new presses pass until it is confirmed.
- **Stop.** Clears accepting, cancels every press and the one-shot send authorization, drops the subscription, releases the HUD, stops the application observation, releases the frontmost lease and returns for the registry's worker join. A release that is not acknowledged is retained (the HUD by the factory's `HudHost`, the observation by `ApplicationControl`), blocks a second panel or observer, is retried by Retry and acknowledged at coordinated teardown (`NativeSlot::Hud`, `NativeSlot::ApplicationObservers`).

## Architecture

- `src/crates/modules/hold-to-quit/src/runtime.rs`: `HoldToQuitRuntime`, `HoldToQuitModule`, the worker, `HudHost`, and the injected `FrontmostLeaser`. `policy.rs` is the allocation-free callback decision and shared atomics. `test_support.rs` and `tests.rs` hold the fakes and suites.
- `src/crates/app/src/hold_to_quit.rs`: `compose`, `HoldToQuitFactory` and the two teardown owners; the host leases its [frontmost context publisher](../architecture/sdk.md#shared-input-inert-contract).
- Input is the single shared service at `host::input_priority::HOLD_TO_QUIT` (300, above MenuAnywhere 200 and Keybindings 100) with `WorkRequirement::None`, so it never consumes the Keybindings dispatcher's slots. The filter is `KeyDown | KeyUp | FlagsChanged` over keys 12, 54, 55, 56, 58, 59, 60, 61, 62 with `ModifierMatch::Exact(COMMAND)`.
- Pause, stop and degrade use the shared service's deferred tap removal, so the remaining auto-repeats of a claimed press are still swallowed after the subscription is gone.

## Limitations and intentional changes

- **Fn+⌘Q passes through.** The exact-Command reservation is what lets the Keybindings Carbon yield cover exactly `⌘Q`; legacy ignored Fn.
- **Keybindings `⌘Q` binding is yielded while the subscription is live**, even for presses Hold-to-Quit passes (Finder, Stache, unknown frontmost). Disabled, paused, stopped, failed or degraded Hold-to-Quit has no subscription, so the binding works. Whether a suppressing HID tap already prevents Carbon delivery is an unmeasured gate of Keybindings part 03.
- **Tap disable orphans.** After the OS disables the tap, the shared ledger drains and the remaining repeats and key-up of a claimed press pass through to the application; events already delivered while the tap was off cannot be recalled. Recovery needs a new physical press, and an old hold is never resumed.
- **Notification lag.** Activation notifications are not atomic with physical input. The callback relies on the last published snapshot; main revalidates the exact instance before the show and inside the send, which narrows but cannot close the interval between an OS focus change and the send. A release delivered after the worker's deadline check but before the send commit still prevents the send; one after the commit cannot undo it.
- **Reduce Transparency.** The HUD reports the accessibility setting but does not yet swap to an opaque surface (part 02).
- **Own `⌘Q` and logout.** This feature does not touch the separate gap in Stache's own `⌘Q`/logout coordinated teardown; it is not fixed here. Stache itself and Finder are exempt.
- **Not ported.** `forceTerminate`, the `stache://cmd-q/alert` event, the 16/100 ms polling timer and exclusion lists.

## Verification

Automatic coverage uses only fakes: the shared input service over its fake tap and clock, `FakeApplicationBackend` with barriers, `FakeHudBackend`, manual and never-draining executors, a pump thread for cross-thread acknowledgements and an injected module clock. They never install a tap, show a panel, terminate an application or prompt. Names carry the criterion (`hq_04_01_` … `hq_04_06_`, `hq_05_01_` … `hq_05_06_`). See [testing](../guides/testing.md).

**User-reported manual run (2026-11-07):** with Accessibility granted to Stache Next, holding ⌘Q in a disposable app showed the HUD and quit the app. Before the grant, the module did nothing and nothing explained why (a separate Accessibility gate spec is planned). The individual cases below were not reported separately. A second user-reported run the same day, on the Part 06 build with `position: "center"`, `animation: "fade"` and `dismiss_delay: 750`, confirmed the centered fade-in, the frozen bar on an early release, the 750 ms linger and the fade-out. The ad-hoc signed rebuild needed its Accessibility record reset (`tccutil reset Accessibility com.marcosmoura.stache.next`) and re-granted first.

**Otherwise unverified on a real machine:** event tap behavior under real input, HUD visibility (another app's full-screen Space, secure input), display and Space placement, click-through, a real graceful quit and the HID-versus-Carbon ordering. A manual run needs approval for that run, the Next identity and a disposable application with no unsaved work, such as TextEdit: tap versus hold, repeat and Command release, focus switch mid-hold, Finder pass-through, pause mid-hold (the deferred tap must swallow repeats), display, Space, focus and click-through. Quit only the disposable app, and record skipped cases as unverified.

For the old behavior, read the [archived legacy feature](../../_legacy/docs/features/hold-to-quit.md). The rewrite is specified in the [spec](../specs/2026-11-03-hold-to-quit/00-overview.md).

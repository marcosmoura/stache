## Requirements

### Lifecycle and readiness

1. Descriptor ID `commandQuit`; no provides, executables or surfaces. `required_permissions` returns `PermissionRequirement::shared_input(Permission::Accessibility)` while enabled, so startup, enable, reload, polling and activation only check; only the explicit tray request prompts. Factory construction, registration and configure are inert. Disabled holds no observation, HUD, host-context lease, subscription or worker. Controls stay generic: tray Enable (config-backed), session Pause/Resume, Retry, permission waiting and revocation.
2. The factory registers through `register_module_observed` and installs the module's `AcceptedWatch<CommandQuitConfig>`, as `KeybindingsFactory` does. It owns one `ApplicationControl` and the HUD backend/executor; each start builds a fresh `HudControl`/`HudEvents` pair (a released control is retired). A predecessor HUD or observation still `Retained` is kept by the factory and retried first; while still retained, start fails rather than creating a second panel or observer.
3. Start runs off-main in this order: allocate generation, inbox and cancellation state; acquire the host frontmost-context lease (requirement 4); `ApplicationControl::install` then `watch_frontmost` (observation before the first confirmed snapshot); `HudControl::install` (Running only after the acknowledged hidden panel); `accept()` for the accepted config; spawn the worker with `ModuleContext::spawn_worker`; subscribe the input handler last. Any prerequisite failure rolls back in reverse, leaves callbacks inert, keeps unacknowledged owners for retry and returns a typed `ModuleError`, so the registry reports `Failed(Start, …)` and the tray offers Retry (shipped rule in `tray.rs`). This is the shipped status model's form of decision 5's "Unavailable"; approved in overview open question 1. An unconfirmed frontmost does not fail start: new presses pass until confirmed.

### Host frontmost context

4. ([Overview](00-overview.md) decision 11.) `frontmost_context.rs` adds one host-owned frontmost publisher over its own `ApplicationControl`, publishing into `InputService::context_publisher()`. Lifecycle: a reference-counted lease. The first lease, taken by a consumer's start, installs the observation and watch; the last release stops them with acknowledgement. With Hold-to-Quit disabled and no other lessee, nothing runs. It is generic, so MenuAnywhere and Keybindings can lease it later. A lease failure is a start prerequisite failure. Retained cleanup is acknowledged under `NativeSlot::ApplicationObservers` during coordinated teardown.
   - Publication: `mark_stale` immediately when an activation is ingested; `publish_frontmost(FrontmostApp { bundle_id, exemptions })` after a confirmed refresh whose epoch is still current; `mark_unknown` for an unconfirmed result, a confirmed snapshot without a bundle identifier, a failed/rejected refresh, and on stop.
   - `host::input_context` documents the `ExemptionFlags` bits: `FINDER = ExemptionFlags(1 << 0)`, `CURRENT_PROCESS = ExemptionFlags(1 << 1)`. Remaining bits are reserved. An exempt application is still published `Known`, with its bits set.
   - **Missing in shipped part 03:** `FrontmostWatch` has no change notification, so the host cannot mark stale on activation without polling. Add, additively, `ApplicationObservation::watch_frontmost_observed(cancellation, listener)` with a `FrontmostListener { invalidated(epoch), published(&FrontmostSnapshot) }`. `invalidated` runs from the activation sink after the epoch bump. It is bounded, never dispatches to main and never waits beyond the publisher's own short locks. `published` runs on main after the epoch-checked publish, outside the publication cell lock, and once more with `Inactive` when the watch dies. `watch_frontmost` keeps its signature and behavior.

### Callback decision and physical pairing

5. One handler subscribes at `input_priority::HOLD_TO_QUIT` with `WorkRequirement::None`. The shared work owner is the Keybindings dispatcher, and Hold-to-Quit must not consume its slots. Filter: kinds `KeyDown | KeyUp | FlagsChanged`, keys `{12, 54, 55, 56, 58, 59, 60, 61, 62}` (Q plus left/right Command, Shift, Option and Control; not Caps Lock 57, which Keybindings' Caps handler owns), `ModifierMatch::Exact(ModifierFlags::COMMAND)`. `Exact` ignores Caps Lock and left/right. `FlagsChanged` for a named modifier key always reaches the handler (shipped filter rule), so Command release or an added Shift/Option/Control mid-hold is seen. `Exact` is required: the shipped reservation registry derives Carbon yields from this filter, and `AllOf` would also silence ordinary Cmd+Shift+Q-style bindings. **Deviation:** Fn+Cmd+Q does not match and passes through. Legacy ignored Fn; this is the cost of an exact reservation, is recorded in the feature doc and was approved (overview open question 2).
6. The callback reads only atomics, `FrontmostWatch::snapshot()` (nonblocking by contract) and `event.context()`. It does no logging, allocation, native or application query, main dispatch or blocking wait. Its only effects are atomic stores, `CallbackScope::set_press_state` and a non-blocking `try_send` into the module's bounded preallocated inbox. A first nonrepeat Q down is `Suppress` only if all of these hold. Otherwise it is `Pass`.
   - The runtime is accepting, and the armed revision equals the observed published revision.
   - The HUD is ready.
   - `FrontmostWatch::snapshot().eligible_application()` is `Some`.
   - `event.context().frontmost()` is `Known` with empty exemption bits and the same bundle identifier.
   - The inbox accepted the down.

   The SDK snapshot is a secondary, bundle-only gate; disagreement fails open. Finder, Stache itself and unknown, stale or unconfirmed state pass with no HUD and no terminate. `FlagsChanged` always returns `Pass`.

7. Press identity ([overview](00-overview.md) decision 12): on a claimed down the callback takes the next value of a module-owned monotonic `u64` counter as a fresh `hold_hud::PressId` and stores its raw value with `set_press_state`, so repeats and up map back to it without a lookup. The SDK `input::PressId` is `(stream, epoch)`. It repeats for successive presses of the same key in the same epoch, so it cannot name a HUD show or a `PressAuthorization`. The down captures the exact `ApplicationId` and activation epoch from the snapshot it decided on, the monotonic down time (one clock read) and the armed config.
8. Pairing is the shipped ledger's job: a passed down never acquires a suppressor mid-press, and a repeat never starts a press. Repeats and up of a claimed press stay suppressed through the up, including after the handler goes inert (inert tombstone). In the callback, Q-up, loss of Command-only flags (a `FlagsChanged` whose flags are not exactly Command, or a repeat whose flags no longer match) and `on_cancel(press)` (tap disabled) immediately set the press's cancel flag and cancel any published `PressAuthorization`, then wake the worker. These are atomics plus `PressAuthorization::cancel`, which is gate-free. Frontmost epoch change, reconfigure, HUD failure, pause and stop cancel the same way from their own paths. Release and cancel must reach the one-shot authorization before any later send commit, without the callback blocking or allocating. The worker re-checks the flag after it publishes an authorization.
9. A full inbox fails open for a new down. For a claimed press, the cancel flag is still set, so cancellation is never lost to queue capacity. After a tap disable the shipped service has drained the ledger and advanced the epoch. Orphan repeats and up then pass (shipped). This is a known limitation, because events already reached applications while the tap was disabled. Recovery needs fresh confirmation and a new physical press, and never resumes an old hold.
10. **Missing in the shipped service (overview decision 10):** `InputService::unsubscribe` removes the suppressing tap as soon as the last handler leaves, even while the ledger holds a `Suppressed` tombstone. When Hold-to-Quit is the only suppressing subscriber, pausing or stopping mid-hold would let the remaining Cmd+Q auto-repeats reach the frontmost app. Minimal additive change: when the last handler unsubscribes while suppressed tombstones exist, logical unsubscribe and reservation removal (restoring Carbon yields) stay immediate, but native tap removal is deferred. The removal runs once the last tombstone is consumed by its up, a tap-disable drains the ledger, or the input owner shuts down under coordinated teardown, whichever is first. New first downs pass while deferred. The tap callback only flags that removal is due; the acknowledged removal runs off the tap thread through the existing control path. `UnsubscribeReport` gains a deferred variant. No timer and no tap callback wait.

### Conflict with Keybindings Carbon hotkeys

11. `subscribe_handler` registers the filter as a HID reservation at priority 300. The shipped registry then derives a yield for any overlapping Keybindings Carbon reservation (priority 100). The Carbon dispatch path checks `try_dispatchable` and fails closed, so one physical Cmd+Q cannot run both a binding and Hold-to-Quit, whichever backend sees it first. No separate yield call is needed and none may be added. Unsubscribing restores the binding. While the subscription is live, a Cmd+Q binding stays yielded even for presses Hold-to-Quit passes (Finder, self, unknown). Disabled, paused, stopped, failed or HUD-degraded Hold-to-Quit has no subscription, so the binding works. Keybindings part 03's HID-versus-Carbon measurement remains unverified. This part neither repeats it nor relies on it.

### Hold, HUD and issuance

12. The worker waits in one place: its inbox, woken by callback sends, an `AcceptedWatch::on_change` wake, a cancellation listener and the next deadline. An idle runtime has no timeout, polling or tick. On a claimed down it moves to `AwaitingShow`:
    1. It computes the deadline with checked `down + Duration::from_millis(hold_duration)`. An unrepresentable deadline is a cancellable indefinite wait.
    2. It calls `preflight_frontmost(app)`. Anything but `Eligible` cancels the press.
    3. It calls `display_for(app)` for an optional hint. Failure keeps the HUD's own fallback.
    4. It sends `HudControl::show(HudRequest::new(handle, press, hold_duration).with_label(name).with_elapsed_ms(now - down).with_authorization(..))`. The `HudAuthorization` predicate checks the press cancel flag and `FrontmostWatch::is_epoch_current(captured)`.
13. `show` never waits, and a missing acknowledgement becomes `Unavailable(TimedOut)` only when `HudEvents` is polled. While a show is pending, the worker therefore waits on its inbox in `CANCELLATION_QUANTUM` slices and drains `HudEvents::try_recv` after each wake. Slicing is bounded by the 2 s acknowledgement budget and stops once the show resolves. Only a `Shown` event whose `press` matches a still-live press moves to `Tracking`. The worker then creates `PressAuthorization::new(press, app, accepted)` and arms the deadline. The down time stays the origin; zero and already-elapsed durations proceed only after `Shown` and current-state checks. `Stale` for a live press cancels it. `Unavailable` or `Failed` cancels the press and enters HUD-degraded mode (requirement 16). A late `Shown` for a dead press is ignored and hidden.
14. At the deadline the worker first drains the inbox and `HudEvents`. A release or cancel whose callback time is ≤ the deadline wins ties. Input not yet delivered cannot be known; document that latency and part 03's notification race. Then, once only, the worker checks the same generation, armed revision, live press and matching `Shown`. It calls `HudControl::hide` and then `terminate_gracefully(accepted, app, &authorization)`, which runs the main preflight and the one-shot commit at the send. It never substitutes the current app, kills by PID, forces, retries or issues from the callback. Release before the commit means no send. Release after the commit cannot undo it. Report `GracefulOutcome` truthfully: `Requested` is not exit, and `Uncertain` is never `Refused`. Late results are generation-tagged and cannot touch a successor. The HUD hides on request, release and cancel. The rest of the physical press stays paired (requirement 8).

### Reconfigure and accepted publication

15. Use the shipped `AcceptedWatch` contract as documented in [SDK](../../architecture/sdk.md#accepted-configuration). The registry publishes only after `reconfigure` succeeds, and unchanged config is a no-op.
    - In `reconfigure`, the last fallible step is `ApplicationObservation::accept()`. Its `TimedOut` rejects the candidate, leaving the old token, config, readiness and press untouched.
    - On success, `reconfigure` clears `accepting`, cancels the press and stages the candidate, keeping the input subscription and ledger tombstones (enabled→enabled).
    - The worker re-arms only after `AcceptedWatch::read()` shows the same typed value at a newer revision. The callback compares atomics, never the watch, because `read` takes the cell lock. The `on_change` wake plus re-read leaves no lost-wake window.
    - A paused reload stages only the next start. Disable goes through stop.

### Stop, degraded mode and ownership

16. HUD-degraded mode, for runtime HUD failure after Running: the runtime stays `Running`, drops its input subscription (all presses pass and any Cmd+Q binding is restored), logs one warning and sets `ModuleStatusView::detail` through `ModuleFactory::project_status`. Recovery is generic Pause→Resume, or disable then enable. No retry loop, endpoint or HUD-less interception. Approved in overview open question 1.
17. Stop: token cancellation comes first (SDK). Then:
    1. Clear `accepting`, set every press cancel flag, cancel the authorization and wake the inbox.
    2. Drop the subscription (requirement 10 keeps the tombstone's tap).
    3. Hide and `release` the HUD.
    4. `stop` the applications observation.
    5. Release the host-context lease.
    6. Return for the registry's worker join.

    It never waits on main for a worker that waits on main. `terminate_gracefully` is bounded by its 2 s budget and cannot send once the authorization is cancelled. Cleanup uses the shipped per-hop budgets and runs even when already cancelled. The first failure is preserved, and retained owners stay inert and block duplicate successors (requirement 2). Retry and stop are idempotent and never report success on timeout. `NativeSlot::Hud` gets an owner that acknowledges a factory-retained HUD and retries its release. A committed native send may still finish.

## Acceptance criteria

- [x] HQ-04-01: Inert default-disabled factory; generic Enable, Pause/Resume, Retry and user-only permission; start prerequisite failure is a typed `Failed(Start)` with full rollback; runtime HUD failure is degraded pass-through with no subscription. No extra CLI, IPC or UI.
- [x] HQ-04-02: Nonblocking, allocation-free callback decisions over the Exact Command-only keycode-12 filter, exemptions and both frontmost gates; ledger pairing holds under worker delay, inbox overflow, tap interruption and Command release before Q-up; HUD `PressId` is fresh per physical press.
- [x] HQ-04-03: Only a matching `Shown` arms checked full-u64 deadlines; at-most-once exact-instance `terminate_gracefully`; release/deadline/send barriers prove cancellation and truthful `GracefulOutcome`s; pending shows expire via `HudEvents` draining.
- [x] HQ-04-04: Frontmost change or burst, reconfigure, pause/stop and late HUD/native results cannot revive or retarget a press. A rejected candidate (including `accept` timeout) preserves old state; new presses arm only after the matching `AcceptedWatch` publication, without lost wakes.
- [x] HQ-04-05: Cancellation precedes joins; blocked main or issuance cleanup returns bounded truthful errors with inert retained owners and no duplicate HUD, observer or successor mutation; idle worker does not poll.
- [x] HQ-04-06: The HID reservation at `HOLD_TO_QUIT` yields an overlapping Keybindings Carbon Cmd+Q reservation in both registration orders, restores it on unsubscribe, and does not yield Cmd+Shift+Q; no private tap, framework or Keybindings-module dependency.
- [x] HQ-04-07: Feature, testing, new-module, SDK, overview, index and roadmap docs describe verified shipped behavior, limitations (Fn, tap-disable orphans, notification lag, yielded binding while live) and manual coverage honestly, without claiming the own-Cmd-Q/logout gap is fixed.
- [x] HQ-04-08: The host frontmost-context lease starts with its first lessee and stops with its last; it marks stale on activation ingestion, publishes `Known` with documented exemption bits after confirmed refresh and marks unknown otherwise; `watch_frontmost` is unchanged.
- [x] HQ-04-09: The suppressing tap outlives the last handler only while a suppressed tombstone exists and is removed with acknowledgement at that tombstone's up, a tap-disable or owner shutdown; logical unsubscribe and yield restoration stay immediate.

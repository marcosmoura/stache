# 04 — Tiling coupling

Read when implementing after parts 01–03 and separate approval. Paths are under `src/crates/`. This part contains the blink fix. Still behind `native-borders`; production keeps JankyBorders.

## Scope

New `modules/tiling/src/borders/{model.rs,engine.rs}` (pure border model and the engine that diffs it into overlay batches), `actor/mod.rs` (feed the engine after each published turn, next to `border_focus` at `actor/mod.rs:1044–1063`, `border_focus` at `:1079`), `actor/frames.rs` and `animation/worker.rs` (frame events), the `HideApp`/`UnhideApp`/`Focus` arms of the effect runner (`actor/mod.rs:314–331`), `tracking.rs` (compose the engine instead of `BordersControl` when the feature is on) and `app/src/host.rs` (compose the overlay adapter under the feature). Studied for approach (decision 5): JankyBorders `src/events.c` (`window_modify_handler`, `space_handler`, `front_app_handler`) and `src/windows.c` (`windows_window_hide`/`windows_window_unhide`, `windows_determine_and_focus_active_window`): JankyBorders reacts to the window server after the fact; Stache instead orders border changes around its own effects.

## Requirements

- **Model.** A pure `border_model(&TilingState, &BordersConfig) -> BorderModel` lists, per exact `WindowInstance`, whether it is bordered, its frame, focused flag and appearance. Bordered means decision 2: tracked and managed, tiled or floating, on a visible workspace, not ignored (tiling `ignore` and `borders.ignore` rules, the system skip lists of `policy::blacklist`, matched per resolved OQ-6 against the application's bundle id and localized name, not the executable name), not minimized, fullscreen or hidden (`ObservedWindow`, `state/mod.rs:469–484`), not a suspended slot member or inactive tab (`state/slots.rs`), with a known `cg_window_id` and a frame. Focused window: `focused_state` (legacy precedence); others: `unfocused` (resolved OQ-3: overrides color only the focused window). Every border uses the active state's width (resolved OQ-1). A disabled state means no overlay for that window.
- **Diff, not rebuild.** The engine keeps one overlay handle per bordered window and sends only differences: `Show` for new, `Hide`/`Release` for gone, appearance changes for focus flips (recolor only, cross-faded per [part 03](03-animations.md) when a transition is configured), `Move` for frame changes. A configuration reload recomputes appearances in place.
- **Frame source.** The border frame is the frame Tiling last wrote or confirmed for the window's current plan: a direct write's target when it is dispatched, each animation frame when it is written (same tick), and the readback or observed frame once known (a refused or partial write corrects the border to the observed frame). A frame event for an older plan sequence than the engine's current one for that window is ignored.
- **`BorderFrames` seam.** The frame paths report `(window, plan_sequence, frame, kind)` through one bounded, non-blocking `BorderFrames` trait: from the shipped [animation part 02](../2026-11-09-tiling-animation/02-async-frame-pipeline.md) pipeline: direct writes at `FrameControl::submit_direct` (`actor/frames.rs:225`, target on dispatch, readback from its reply at `actor/frames.rs:239–249`), animated frames from the per-tick batch dispatch `Animator::send` (`animation/worker.rs:653–700`, on the animation worker thread) and their acknowledgements (`on_ack`/`frame_answered`, `animation/worker.rs:705`, `:750`), and the settled frame from `complete` (`animation/control.rs:173`). The frame path never waits for borders.
- **Hide before the application hides.** Before the effect runner issues `HideApp` for an application, the engine hides that application's overlays and waits for the main-thread acknowledgement for at most `BORDER_HIDE_WAIT` (proposed 32 ms, two frames at 60 Hz). On timeout the hide proceeds and a counter records a late border hide; the hide is never cancelled or delayed further for borders. Windows leaving the visible workspace without an application hide (same application on two workspaces) are hidden in the same turn before their frame write.
- **Show only after visible.** A window that becomes bordered by a reveal (workspace switch, display return, unhide, external show) stays hidden until all hold: its application is observed shown (`Observation::Shown`, `visibility.rs:381`, folded in `observe` at `visibility.rs:697–701`, or never hidden), its reveal frame write has completed (the `revealed` set, `state/frames.rs:158–165`, or a fresh snapshot after an external show), and then one display frame has passed. Only then is `Show` sent. This ordering is the blink fix; whether one frame suffices for every application is a native gate item.
- **External hide and show.** A user ⌘H is observed after the fact; overlays of that application hide in the turn the `Hidden` observation arrives (bounded lag, documented). A user unhide or Cmd-Tab follows the show rule above.
- **Focus and raise.** Focus changes recolor overlays in place. When Tiling focuses or raises a window (`Effect::Focus`), its overlay is re-ordered above it after the raise; when another bordered window is observed focused, the same re-order runs. Without [part 06](06-live-follow.md)'s reorder notifications, a raise Tiling did not see may leave a border under another window until the next focus event (documented limit).
- **Tabs.** A slot's border follows its active member; on handover the old member's overlay is released and the new member gets one after the show rule. `slot_held` keeps the existing overlay in place.
- **Spaces and fullscreen.** Fullscreen windows have no border in the model. Space changes, Mission Control and fullscreen transitions are owned by [part 05](05-spaces-mission-control.md); this part exposes the engine hooks it needs (hide all, suspend shows, re-confirm on resume) and its show rule is the one part 05 reuses on resume.
- **Failure.** Overlay refusal, a missing `cg_window_id` or an ordering failure affects that border only, with a status diagnostic. The engine never submits Tiling inputs that change layout, focus or visibility.

# 06 — Live follow during user drags and resizes

Read when implementing after part 05 and separate approval. Paths are under `src/crates/`. Still behind `native-borders`.

## Scope

New `macos/src/skylight/window_events.rs` (gated private notifications, `dlsym`-resolved, reusing part 05's registration helper in `skylight/space_events.rs`) with a fake; the shared display-link adapter `macos/src/display_link.rs` shipped by [animation part 03](../2026-11-09-tiling-animation/03-display-pacing-size.md) (`FrameClock`, `FrameClockFactory`; reused, no second adapter); `modules/tiling/src/borders/engine.rs` (live mode) and `drag.rs` only to read the gesture state. Studied for approach (decision 5): JankyBorders `src/events.c` (`events_register`: `SLSRegisterNotifyProc` for move, resize, reorder, hide, unhide, close; ignoring its own windows by owner pid), `src/windows.c` (`windows_update_notifications`: `SLSRequestNotificationsForWindows` with the bordered window ids), `src/border.c` (`border_move`: reads the target bounds and moves the border in a transaction on a background queue), `src/animation.c` (display-link pacing).

## Requirements

- **Capability.** At engine start, resolve the needed private symbols (notification registration, per-window subscription, window bounds read) with runtime `dlsym` against SkyLight, the same policy as `macos/src/ax/window_id.rs`. Any missing symbol, a registration failure or a non-macOS-26 build makes live follow unavailable with the diagnostic `borders: live follow unavailable (<reason>); borders hide while a window moves`. Nothing else is disabled.
- **Owner confinement.** One owner thread `stache-tiling-borders-events` owns the registration and its run loop; callbacks only copy `(event, cg_window_id)` into a bounded latest-per-window slot and wake the follower; no allocation beyond fixed buffers, no lock held while calling out, no AX call. Events for windows that are not currently bordered, or owned by Stache, are dropped. Subscription is updated (bounded, coalesced) when the bordered set changes; the subscribed set never exceeds `MAX_OVERLAYS`.
- **Display-paced follow.** While at least one bordered window reports move or resize events, a display link for its display ticks; on each tick the follower reads the latest bounds of each moving window (one private bounds read per window per tick, never AX) and sends one coalesced `Move` batch to the overlay control. The link stops after a quiet period (proposed 100 ms without events); idle owns no link. Stop guarantees no callback after release (shared adapter rule from animation part 03).
- **Authority with Tiling.** Live bounds win only while no Tiling write for that window is in flight; a Tiling frame event ([part 04](04-tiling-coupling.md)) for the current plan always supersedes a live sample. Live follow never writes the target window, never feeds Tiling layout state and never changes Tiling's drag gesture outcome (`drag.rs` stays the only drag decision).
- **Hide and order events.** Private hide, unhide and reorder events, when available, only hide a border earlier (hide) or re-order it above its target (reorder). An unhide event never shows a border by itself; part 04's show rule and part 05's Space gate still decide. A live `Move` is computed under the current gate epoch, so it is dropped on main after a `HideAll` (part 05). Close events release the overlay.
- **Public fallback.** Without live follow: when Tiling observes a moved/resized sample for a bordered window that it did not cause (`events/geometry.rs` coalesced samples) or the drag gesture starts (mouse down on a bordered window), the border hides; it shows again at the next confirmed frame after the gesture ends (mouse up and settled snapshot) under part 04's show rule. No AX observation is added for borders.

## Tests

Default tests never call SkyLight or create a display link.

## Native gate (per-run approval)

Compile with symbols resolved on macOS 26; then on an owned test window: drag and resize for 30 s each at the display's refresh, record border lag per frame (border bounds vs target bounds read in the same tick), CPU and wakeups during and 10 s after; verify own-window filtering and that no event arrives after stop. Repeat with symbols forced absent to check the fallback.

- Fixes after native run 2 (2026-11-10, fakes-tested only, **no native run**).
  - **Only move and resize act.** `FollowCore::on_event` drops the private hide, unhide, reorder and close events (counted in `FollowCounters::ignored`, nothing reaches the sink). The constants, slot bits and subscriptions stay, documented "unverified, not acted on"; each kind has its own flag in `FollowTiming` (`act_on_hide`, `act_on_unhide`, `act_on_reorder`, `act_on_close`, all off) so a later verified run can enable one alone. Close falls back to Tiling's own destroy path (the model drops the window and its border is released); reorder falls back to the focus/raise re-order of part 04 (`note_raised`/`reorder_raised`). The engine-side handlers for these notes remain but are unreachable by default. The "Hide/order" paragraph of the implemented note above describes that dormant path.
  - **Tighter drag follow.** The first move or resize event of a window with no read in the current display period reads its bounds at once on the owner thread and sends the move without waiting for a display tick (`FollowCounters::immediate`). Further events in the same period only mark the window moving; the display tick (or, when a tick fell inside the period of an immediate read, the end of that period, through `next_deadline`) reads it next. A window is never read twice within one display period; the period is the shortest interval between two observed ticks of its display (the timer period, 16.667 ms, until one is measured). The quiet-period stop is unchanged and Tiling keeps authority (`FollowSink::authority` is asked before every read). Tests: `the_first_event_reads_at_once_and_reports_without_waiting_for_a_tick`, `further_events_in_the_same_period_coalesce_to_the_next_tick`, `a_window_is_never_read_twice_within_one_display_period`, `private_hide_unhide_reorder_and_close_are_ignored_by_default`, `each_unverified_event_acts_only_behind_its_own_flag` (these replace `a_moving_window_is_read_once_per_tick_with_its_latest_bounds` and `private_hide_reorder_close_and_unhide_are_forwarded_and_unhide_moves_nothing`).
  - **Main-thread side.** A `Move` that only translates the target (same size, same display scale, radii and paint, so the plan differs in the panel frame origin alone) sets only the panel's frame origin (`OverlayHost::translate`, `setFrameOrigin`) and skips the layer rebuild, the motion sync and the fade overrides. Any other move takes the full re-plan. Tests: `a_move_that_only_translates_sets_the_panel_origin_and_leaves_the_layers_alone`, `a_move_that_resizes_or_changes_the_display_scale_replans_the_layers`.
  - **Open.** Whether a drag now feels sticky is a native-check question; the remaining latency is the cost of one private bounds read plus the main-thread hop of the move.

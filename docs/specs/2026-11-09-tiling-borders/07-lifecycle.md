# 07 — Lifecycle, robustness and performance budget

Read when implementing after parts 01–06 and separate approval. Paths are under `src/crates/`. Still behind `native-borders`.

## Scope

`modules/tiling/src/module.rs` (start/stop/quarantine stages, `Teardown`), `tracking.rs` (engine composition and `configure`), `status.rs` (borders diagnostics, `borders_failure` at `status.rs:347`), `borders/engine.rs`, `macos/src/border_overlay/` (`release_all`, leak accounting). Studied for approach (decision 5): JankyBorders `src/main.c` and `src/windows.c` (`windows_remove_all`, `windows_recreate_all_borders`); yabai issue [#2835](https://github.com/koekeishiya/yabai/issues/2835) (leaked proxy windows) as the hazard to prevent.

## Requirements

- **Start.** Borders stay outside the numbered start stages, as today (`module.rs:23–26`): the engine starts only when the accepted configuration has `borders.enabled`, after Tiling is Running, and a failure to start degrades borders only. Disabled, the engine owns no overlay, thread, display link, subscription or timer.
- **Reload.** `enabled` false → true starts the engine; true → false releases every overlay; appearance-only changes update in place (parts 02–03; running animations are replaced, a `transition` change applies to the next focus change); ignore changes recompute the model.
- **Stop order.** Stop closes the borders engine right after the drag observer and before the frame drain (the current borders slot, `module.rs:536–551`): stop the live-follow owner, the Spaces owner (part 05) and the display link, then `release_all` on main and wait for its acknowledgement within `BORDERS_RELEASE_WAIT` (proposed 500 ms). Pause and disabling Tiling do the same.
- **No leak, no orphan.** Every overlay handle is accounted for in the engine ledger; after `release_all` the acknowledged count must equal the ledger count. A missing acknowledgement, a mismatch or a stuck live-follow or Spaces owner leaves `borders overlays` owed: the module is quarantined, start is refused, the exact handles are retained, and a later stop retries exactly that stage. No thread is detached. A periodic check is not added; leaks are prevented by ownership, not swept.
- **Crash safety.** Overlays are windows of the Stache process, so the window server removes them when the process exits or crashes; no persisted state or journal is kept. A panic in the engine (unwind builds) releases overlays on the next main-thread turn and reports a borders diagnostic; Tiling keeps running.
- **Main-thread health.** If main does not acknowledge an overlay batch within `BORDER_ACK_WAIT` (proposed 250 ms), later batches merge latest-wins (part 01) and status reports `borders: main thread busy`; nothing waits longer.
- **Budget (deterministic bounds).** At most `MAX_OVERLAYS` (64) overlays and one pending batch; at most one display link per display while something moves; zero Stache wakeups while idle, including while a `loop` rotation runs (no timers, every animation on the render server, part 03); memory per overlay bounded by its layers (no bitmap backing store), except a glow's band: one 9-slice tile bitmap independent of the window size (side `2m + n` pt at the display scale, `m` the panel margin, `n = ceil(2m + 2k + 2) - 2m`, `k = radius + core + 2 × blur`), stretched with `contentsCenter` and re-rendered only when width, corner radius, color or scale change, never on move or resize (a target narrower than `n` falls back to a panel-sized bitmap).

The module stop (always off main; `WouldBlockMain` is a missing acknowledgement, never a wait) calls `BorderLifecycle::settle`: wait for the actor's hand-over (at most two owner stop budgets), retry owners that were stuck, wait at most `BORDERS_RELEASE_WAIT` = 500 ms for the acknowledgement already in flight, compare. `begin_shutdown` (the host's invalidation, which precedes every module stop) sets `Inner.closing`; when the host is tearing the process down **and** the only thing owed is the missing acknowledgement (or a release job that could not be queued), the stage is cleared, traced, and reported as a note in the module detail ("border overlays were left to the window server at process exit: ..."), not as an owed stage: the outcome is `clean` while the record keeps the truth. A runtime stop (pause, disable, reload) never takes that branch: it is owed, quarantined, start is refused and a later stop waits for the very same ticket (no second release job). A stuck owner, a mismatch or a silent actor stay owed even at exit.
  - **Ledger rule.** `expected` = engine ledger entries holding a handle + `Release` commands dropped because the route was already closed (`BorderEngine::retire_ledger`). `ReleaseAck::handles` = handles reserved in the control when `release_all` was requested (shown, hidden-and-kept or pending) minus those whose `Release` is already queued. They must be equal. `ReleaseAck::closed` also counts pooled, ordered-out panels (in no ledger) and is reported, never compared. After a mismatch the retry releases again and any acknowledged release settles it (the control then holds nothing).
  - **Constants.** `BORDERS_RELEASE_WAIT` = 500 ms (`TilingTiming::borders_release_wait`), `BORDER_ACK_WAIT` = 250 ms, `OWNERS_STOP_WAIT` = 2 x `STOP_BUDGET` + 250 ms, `MAX_OVERLAYS` = 64 (unchanged). Diagnostics: `borders: main thread busy`, `borders: released N overlay handle(s) but the engine accounted for M`, `borders: the <owner> did not stop; it is retried by the next stop`, `borders: the border engine failed (panic); borders are off until the next restart`.
  - **Health and budget.** An overlay batch unacknowledged for `BORDER_ACK_WAIT` sets `main_busy` (status `borders: main thread busy`); later batches merge into the one pending batch; the only deadline the engine schedules for it is a look-again while the batch stays unacknowledged, so an idle engine (nothing pending, nothing moving, nothing unacknowledged) schedules none (`a_main_thread_held_past_the_ack_wait_...`).
